# Security Policy

## Supported Versions

| Version | Supported |
| ------- | --------- |
| 1.5.x   | Yes       |
| < 1.5   | No        |

`1.0.x` was a pre-release with no users and no upgrade path — a 1.0.x vault is not opened by 1.5, which only opens vaults it created (`CHANGELOG.md` § `[1.5.0]`).

## Reporting a Vulnerability

**Do not open a public issue for security vulnerabilities.**

Please report vulnerabilities through [GitHub Security Advisories](https://github.com/HarpocGH/harpoc/security/advisories/new).

### Response Timeline

- **Acknowledgement**: within 48 hours
- **Assessment**: within 7 days
- **Fix (critical)**: within 30 days
- **Fix (non-critical)**: within 90 days

We will coordinate disclosure with the reporter once a fix is available.

## Security Design Overview

Harpoc is a zero-knowledge secret vault designed so that secrets are never exposed to the AI model. Key security properties include:

- **Encryption**: All secrets are encrypted at rest using AES-256-GCM with unique per-secret Data Encryption Keys (DEK)
- **Key hierarchy**: 3-tier hierarchy — Master Key (derived via Argon2id) wraps a KEK, which wraps individual DEKs
- **Minimal in-process cryptography**: All cryptographic operations run on Node's built-in `node:crypto`, with Argon2id (a native KDF) the only exception — no third-party cryptographic library is loaded into the vault process. The SSH context's ephemeral in-process agent parses keys and generates signatures on `node:crypto` (unencrypted Ed25519/RSA/ECDSA keys; passphrase-protected PKCS#8/legacy-PEM keys are decrypted at **import** on the CLI — in memory, `node:crypto` only, the passphrase never persisted — while encrypted OpenSSH-format keys stay unsupported, since bcrypt-pbkdf would re-introduce third-party crypto; a combined certificate + encrypted-key bundle is refused before the passphrase prompt rather than silently reduced to the key alone); the private key stays in the vault process and only signatures cross the agent socket. The identity's public line is written to a per-invocation 0600 temp file and passed as ssh's IdentityFile — public material only, required because `IdentitiesOnly=yes` restricts ssh to file-backed identities; it also means ssh offers exactly the vault identity, never the host user's default `~/.ssh/id_*` keys. On Windows an MSYS/Cygwin ssh client is refused before the spawn (`SSH_CLIENT_UNSUPPORTED`): it cannot open the agent's named pipe and would fail in a way that reads as a remote refusal.
- **SSRF prevention**: Pre-flight DNS lookup with IP pinning blocks requests to private/internal network addresses
- **Audit trail**: Append-only by design; tamper-evident rather than database-enforced — detail fields are encrypted and bound to their row, and rows are HMAC-chained, so `harpoc audit verify` detects modification, interior deletion and detail-blob swaps — and erasure of the links themselves, since rows without a chain link are only accepted as a leading prefix of a pre-migration vault, never after a linked row. Every vault mutation commits **in the same SQLite transaction** as its audit entry: a crash cannot produce a completed-but-unaudited operation, and an unwritable audit log blocks the operation (fail-closed) rather than being skipped. `harpoc audit anchor` exports the chain tail; `verify --anchor` detects tail truncation and rollback **provided the anchor is stored off-host** — an attacker who can modify the vault database can likely also modify files beside it, so the vault cannot supply that independent trust domain itself
- **Audit attribution (by whom, through which interface)**: Every token-authenticated credential operation — including `secret.create` and the success row of every `use_secret` invocation, written inside the injectors — carries the requesting principal in the plaintext `principal_type`/`principal_id` columns (covered by the row HMAC chain), the session id, and the access interface (`rest`, `mcp` for stdio, `mcp-http`, `cli`) inside the encrypted detail. `cli` marks any CLI invocation carrying a scoped token (`--token` or `HARPOC_TOKEN`) — every command with a REST counterpart accepts one (`secret use/get/list/set/rotate/delete/allow/mcp-server/connection`, `policy grant/revoke/list`, `audit`, `oauth status/refresh`), each verified and scope-checked exactly as the REST API checks the matching route, and subject to per-secret access policies like any other token-bearing caller. Trusted-local operations (tokenless CLI, in-process SDK — master-password/session authenticated) keep NULL principal columns and no interface tag by design: the "whom" of the administration path is the vault owner. A stdio MCP server explicitly started `--allow-tokenless` is no longer one of them: since 2026-09-02 its operations are attributed to `user` / `tokenless-stdio` with `interface: "mcp"` in the detail. **NULL means trusted-local only for rows written from this release on** — rows from earlier releases predate attribution and are NULL regardless of caller. Vault-initiated MCP lifecycle rows (`mcp.crash` on an async child exit, `mcp.terminate` on seal/policy paths) are deliberately unattributed — no requesting principal exists; `mcp.spawn` is attributed to the invocation that triggered it. `harpoc audit` shows the principal column; the interface appears in the decrypted detail (`--json`)
- **Scope refusals are audited** (2026-09-23): every token-scope refusal on the REST API and the MCP server — a missing permission, a project mismatch, a secret-name pattern, and the governance routes' project-claim refusal — writes one `access.denied` row under the requesting principal naming the operation (`<METHOD> <path>`, or the tool or resource) and the reason before the refusal is answered; the CLI's `--token` path does the same, naming the command path as typed after `harpoc` (`secret list`, `audit verify`, …) (2026-11-12); a refusal is never silent; on the MCP server the row is written within the global rate-limit budget — a caller past it is answered `RATE_LIMIT_EXCEEDED` and writes no row (2026-09-24). Expiry and revocation (401) are not scope refusals.
- **Token revocation takes effect on running servers**: `harpoc auth revoke <jti>` is consulted on every access, not only at connection setup. The Streamable HTTP transport re-verifies the bearer token per request; the stdio transport verifies its launch token once at construction, so its scope guard re-consults the revocation store on every tool and resource call — the check runs ahead of the permission check, so a revoked `admin` token does not pass either. Without that, a revoked token kept its full scope for the life of the server it launched (up to the 24 h token TTL ceiling)
- **The tokenless waiver is on the record**: starting the stdio MCP server with `--allow-tokenless` writes a `server.start` audit event (`{ tokenless: true, transport: "stdio", tty_prompt }`) before the server is constructed — the warning on stderr is a log line, the audit row is the record. It is **fail-closed**: if the row cannot be written, the unrestricted server does not start. The row is unattributed (NULL principal columns, session id stamped) like every `server.start`; since 2026-09-02 every transport writes one — the token-bearing stdio start with the token's subject, each HTTP or REST listener with its bound port — and a graceful shutdown writes the matching `server.stop`, so the waiver is the `tokenless: true` row among them. The operations an unrestricted server performs are attributed to `user` / `tokenless-stdio` rather than to a NULL principal, so they never blend into the CLI's rows.
- **Audit reads are scoped, not just permission-checked**: the audit surfaces (`GET /api/v1/audit`, MCP `secret://vault/audit/recent`) require `admin`, and additionally honour the token's other two scope dimensions — a row about a secret outside the token's project or name patterns is dropped at the engine, so a scoped admin token cannot read another secret's handles, principals or configuration changes, nor use `?secret_id=` as an oracle for them. Rows without a `secret_id` (vault lifecycle, token issuance, server start) carry no per-secret metadata and stay visible. The CLI and an unrestricted admin token see the whole log
- **Per-secret access policies (engine-enforced)**: Stored policy rows restrict which principals may perform which operations on which secrets. A principal is a type — `agent`, `tool`, `user` (the token's subject under its issued `principal_type` claim, default agent) or `project` (derived from the token's `project` claim, never issuable directly) — plus an identifier; a row grants a permission set (`list` gates enumeration, `read` gates metadata and value reads, `use` gates `use_secret`, `rotate` gates rotation and pending-value set, `revoke` gates revocation; `admin` implies all) with an optional expiry. Enforcement is **explicit-grant** at the engine, before anything is decrypted, injected or mutated: a token-derived caller acts on a secret only through a matching, unexpired grant to one of its principals, and a secret with no rows is reachable by no agent- or tool-type token (the token's own 3-dimensional scope is still checked first at the interface; the trusted path and admin-scoped `user`-type tokens are exempt). Denials are audited under the operation's event type with the requesting principal. **Secret-scoped configuration is gated too**: reading a secret's injection policy, MCP-server config, connection config or policy rows requires `read`, changing the MCP-server or connection config requires `rotate`, changing the injection policy requires `admin` (it widens where the credential may go), and granting or revoking a policy row itself requires `admin` — otherwise a principal denied `rotate` could still rewrite the allowlists that bound where the credential may be injected, or loosen its `response_mode`, and a principal denied `read` could still enumerate allowlisted hosts, downstream commands and grants. **Enumeration is gated too**: every listing surface — `GET /secrets`, `GET /health/expiring`, `list_secrets`, `check_secret_health` and the MCP secrets/health/projects resources — drops a secret unless the caller holds `list` (or `admin`) on it, so the metadata row a denied `read` refuses cannot be recovered from a listing; a grant of only `use` therefore does not make the secret discoverable, and the aggregates (counts, expiring sets, project census) are computed over the filtered set. Filtering is silent toward the caller, but each enumeration the engine runs writes one `vault.read` row that records how many entries it returned and how many the filter withheld, never a name (2026-11-12). Out of scope by design: `create` is **not** a per-secret permission (a policy row attaches to an existing secret, so `grantPolicy` refuses it) and is governed by token scope alone. A caller holding none of `read`/`list`/`admin` on a secret receives `SECRET_NOT_FOUND` (404), byte-identical to an unknown handle, so a secret's existence is not observable to a token without a grant; the audit row still records `ACCESS_DENIED` with the real secret id. The one accepted exception is the policy-write (`admin`) checks — `POST /secrets/:handle/policies`, `PUT /agents/:name/secrets/:handle/permissions`, `PUT /secrets/:handle/injection-policy` — which keep `ACCESS_DENIED` on a real handle so the matrix editor's `harpoc policy grant …` remedy survives; an admin-scoped agent- or tool-type token can therefore still tell a real name from a wrong one on those three routes, and on nothing else. Callers on that trusted path — CLI, in-process SDK, and stdio MCP explicitly launched with `--allow-tokenless` (the warned-about local full-access mode; a launch token is otherwise required at stdio startup, `TOKEN_REQUIRED`) — authenticate via master password/session file and are not subject to per-secret policies (the administration-versus-operation split)
- **A downstream child never outlives the credential**: a stdio MCP server the vault spawned holds the plaintext in its environment for as long as it runs, so revoking a secret, its expiry, a rotation, a configuration change and every seal path (lock, destroy, session expiry, key wipe) terminate that connection, audited as `mcp.terminate`. A revocation performed from _another_ process (the CLI, while a server is running) cannot reach that server's in-memory registry — there the teardown happens when the server next tries to use the secret and is refused, which is also when the credential would otherwise have been used again
- **Execution-layer injection**: Secrets are injected at the execution layer across eleven contexts — an HTTP request, a spawned subprocess's environment, a downstream MCP server, a database connection, a Git operation, an SSH session, an SMTP mail session, an IMAP mail session, a WebSocket connection, an SFTP transfer, or a docker-registry operation — and never returned to the LLM context. Per-secret allowlists bound where a credential may be injected: a deny-by-default URL allowlist for HTTP, WebSocket, MCP-over-HTTP and Git-HTTPS, a fail-safe command allowlist for process execution (with an explicit acknowledgement gate for known interpreter binaries and, since 2026-09-04, for exec wrappers — binaries whose argv is itself a command), and a deny-by-default host allowlist for database, SMTP, IMAP, SSH, SFTP, Git-SSH and docker-registry targets. Endpoint authentication is pinned per secret: database TLS/CA policy and SSH host keys
- **Contexts do not leak into one another**: the Git and SSH contexts require their binary in the secret's command allowlist — that entry is what pins `git`/`ssh` to a resolved absolute path — but the allowlist is a single field and the caller chooses the context per invocation. The process context therefore **refuses any binary that has a dedicated context of its own** (`DEDICATED_CONTEXT_REQUIRED`, audited before any spawn, no environment opt-out), matched against the resolved symlink-followed path. Without that refusal, a caller holding only `use` on a Git- or SSH-configured secret could run the same binary through the process context, where the vault inspects no argument — `git -c 'alias.x=!<command>' x` and `ssh -oProxyCommand=<command> host` are arbitrary execution with the credential in the child's environment, and no configuration could enable the Git or SSH context without also granting it. Interpreters are deliberately handled by the acknowledgement gate instead: allowlisting `bash`/`node`/`npx` is already an explicit, audited administrator decision, whereas `git` and `ssh` carried no such acknowledgement
- **Git-over-HTTPS target control extends past the URL string**: the credential is bound to the host the vault validated — the askpass helper compares the host git names in the prompt and refuses anything else, including a prompt naming no recognizable URL — redirect following is disabled (`http.followRedirects=false`), and `--recurse-submodules`/`--recursive` are denied. Otherwise a `30x` from the validated host, or a `.gitmodules` entry in the cloned repository, moves the credential prompt to a host the vault never resolved, validated or allowlisted. Denied-argument matching also accounts for git's own option abbreviation (`--templ=` reaches `--template`), so the clone-time hook-execution options cannot be smuggled in under a shortened name. A hook already present in a caller-supplied working tree is a separate vector: every git run forces `core.hooksPath` to an empty vault-authored directory, so `post-merge`, `pre-push` and a template's `post-checkout` never execute with the credential in their environment (2026-09-04, N11).
- **A fetch and an ls-remote keep the git context's guarantees** (2026-11-10): both run their credential-bearing step in a relay repository the vault writes for the call and re-validates before and after it, under the configuration every git run carries — `core.hooksPath` at an empty vault-authored directory, `credential.helper` and `core.fsmonitor` neutralised, no system or global configuration — and the same denied arguments under git's own abbreviation: `--upload-pack`, which names a program to run, on both as on every operation; on a fetch the options that would move the checked-out branch's ref under its work tree (`-u` / `--update-head-ok`), take refspecs from other remotes or from standard input (`--multiple`, `--all`, `--stdin`), choose destinations past the vault's own (`--refmap`) or write the caller's configuration (`--set-upstream`, and `--filter`, whose partial clone would later fetch without the credential). A fetch's refspecs name the remote's branches and tags only and the vault chooses where they land; the step that writes into the caller's tree runs without the credential, with an empty `--refmap=` so that no fetch refspec of the tree's configuration adds a destination, and writes the remote-tracking refs of the tree's one remote for that repository — under `refs/prefetch/` instead when the caller passes git's own `--prefetch` — and the tags; no hook of the tree runs in either step, a `reference-transaction` hook, which git runs for every ref update, included. The repository rides behind `--` by the vault's own check, not git's: a repository that begins with `-` is refused, since a caller's trailing option that takes a value could take the vault's `--` as that value and leave the repository to be parsed as an option; and an scp-form repository whose user part holds a colon — which git splits at that colon while the vault read the host after the `@` — is no SSH repository to the vault (`GIT_UNSUPPORTED_TRANSPORT`); both on all five operations since 2026-11-10. For a git-over-SSH use the host the allowlist judged and the audit row names is the host the vault's ssh dials and checks the host key of: the vault hands it to ssh as `HostName`, ahead of every other option, so whatever destination git derives from the address — by its bracket rule, by percent-decoding an `ssh://` URL before it looks for the authority's end, and ssh by splitting at the last `@` — names the user and the port at most; a host that is not a host name — ASCII letters, digits, `.`, `_` and `-`, beginning with a letter or a digit, 255 characters at most — or the IPv6 literal of an `ssh://` URL is refused (`INVALID_GIT_CONFIG`) before the allowlist is consulted, its text never written into a row; on all five operations since 2026-11-10 (until then a crafted address could make the vault's ssh try another host than the one judged). The user of the address is judged after the host and before the allowlist (since 2026-11-11): a name of letters, digits, `.`, `_` and `-` that begins with a letter or a digit, else `INVALID_GIT_CONFIG`, as is an `ssh://` address that carries a password. Hooks stay disabled in the credential step by design: a hook there runs caller-controlled code with the credential in its environment, which is what N11 and the relay close; under deployment model B an agent's own `git` runs its own hooks under its own UID, outside the vault. Every refusal the git context makes before git runs — a denied argument, a positional, a refspec, a working directory it refuses or requires, an operation it does not know, an `ssh` binary missing from its PATH — writes a failed `secret.use` row carrying the operation and the error code, never the refused argument, refspec or path, on all five operations (until 2026-11-10 such a refusal on a clone, pull or push left no row). What stays open: an `ls-remote` returns refnames and object ids the remote chose — untrusted text in the model's context, redacted for the credential and capped like every git result, never an instruction the vault acts on; a fetch writes remote-chosen ref names into the tree's remote-tracking namespace and its tags, as a direct `git fetch` would; a `[remote "<repository>"]` section of the tree's own configuration still shapes the credential-free local step as git lets a remote's section shape a fetch (its `url`, `uploadpack`, `prune`, `tagOpt`) — the tree owner's configuration, with no credential in that step; the host allowlist of a git-over-SSH use is host-only: the port, the user and the path are the ones git and ssh read from the address, by rules of their own — a `[host]:port` line of the secret's known-hosts pin binds the port, a bare-host line admits every port whose key matches; and a concurrent writer running as the vault's OS user can still reach the credential through the relay's configuration between the re-validation and git's read, as for every git operation.
- **Injector errors are redacted too**: a thrown error is a model-visible channel — the MCP SDK turns it into the tool result text and the REST error handler returns the message — so error text carrying attacker-influenced strings (a refused redirect target chosen by the endpoint that just received the credential, a driver message quoting a connection string) passes through credential redaction on the way out, and refusals name only a target's origin rather than its full URL. Redaction covers JSON object **keys** as well as values, since the party naming keys in a proxied MCP result or a SQL column alias is not the vault
- **Network isolation** (opt-in, per secret): with `network_isolation` on the injection policy, every child process spawned with the secret (process, Git, SSH and SFTP contexts, and stdio MCP downstream servers) runs without network access — loopback included, since the vault's own REST/MCP listeners live there. Linux delivers it via `unshare -rn` (unprivileged user + network namespaces) or, when `unshare` is absent or refused, via bubblewrap (`bwrap --dev-bind / / --unshare-net --die-with-parent`, a fresh namespace with an empty loopback of its own, the root bound with device access — a plain `--bind` mounts `nodev`, and the ssh-family clients open `/dev/null` at startup; bwrap stays as a monitor and takes the payload down with it) — note that stock Ubuntu 24.04+ restricts unprivileged user namespaces via AppArmor, which both tiers' probes detect, so uses are refused until the restriction is relaxed or a profile grants `userns` to the wrapper — and macOS via `sandbox-exec` with a constant deny-network profile; every tier is probed live at first use, and only a successful probe is cached — a transient probe failure re-probes on the next use instead of permanently disabling isolation. Windows is unsupported by design (real per-process isolation requires an AppContainer native addon). **Fail closed**: a platform that cannot deliver demanded isolation refuses the use with `NETWORK_ISOLATION_UNAVAILABLE` before any process is spawned, and the denial is audited — there is no silent degrade and no environment-variable opt-out. The wrapper is vault-authored, resolved from pinned absolute paths, and applied after command-allowlist resolution; agent input never reaches it. Setting the flag terminates any live stdio MCP downstream child already holding the secret (audited `mcp.terminate`) and the next use respawns it wrapped in the same isolation wrapper; a policy tightened from a separate process takes effect at that server's next invocation attempt — the live connection records the posture it was spawned with, and a demanded dimension it lacks terminates it before the respawn. Every process/git/ssh/sftp use — including security denials such as host-key mismatches — is audited with its isolation state and, on a row whose spawn returned a result, its mechanism (sftp's rows since 2026-10-14) — including, since 2026-09-05, the `mcp.spawn` row of a stdio downstream (`isolation_mechanism`).
- **Filesystem isolation** (opt-in, per secret): with `fs_isolation` on the injection policy, every child process spawned with the secret (process, Git, SSH and SFTP contexts, and stdio MCP downstream servers) is denied filesystem writes. Linux delivers it via `setpriv` chained with a Landlock ruleset (util-linux ≥ 2.40) or, behind it, via bubblewrap's read-only root bind (`bwrap --ro-bind / / --dev /dev --die-with-parent`, the tier that carries the flag on Ubuntu 24.04 LTS), macOS via a `sandbox-exec` deny-write profile whose last rule allows the literal `/dev/null`; writes to `/dev/null` are exempt on every mechanism (the earlier macOS asymmetry closed 2026-09-05). Windows is unsupported by design. **Fail closed**: a platform that cannot deliver demanded isolation refuses the use with `FS_ISOLATION_UNAVAILABLE` before any process is spawned, and the denial is audited — no silent degrade, no environment-variable opt-out; only `secret allow --no-fs-isolation` (or the REST PUT) lifts it. Setting the flag terminates any live stdio MCP downstream child already holding the secret (audited `mcp.terminate`, reason `fs_isolation_enabled`); if a policy update enables both `network_isolation` and `fs_isolation` together, the network-isolation reason takes precedence and exactly one terminate is emitted. The next stdio MCP use of the secret respawns the child wrapped (the `mcp.spawn` row carries `fs_isolation_mechanism`); only a host that cannot deliver the isolation refuses it with `FS_ISOLATION_UNAVAILABLE`. Combined with network isolation, Linux chains both primaries into one spawn (`unshare -rn -- setpriv ... --`) or, when either fell to the second tier, takes one `bwrap` wrapper for both, and macOS uses a single combined `sandbox-exec` profile denying both network and writes. Every process/git/ssh/sftp use is audited with `fs_isolation` (posture) and, when a wrapper actually ran, `fs_isolation_mechanism` (`landlock` / `sandbox-exec` / `bwrap`)
- **Strict tree exit** (opt-in, per secret): with `strict_tree_exit` on the injection policy, nothing a process-mediated child started outlives the call. Windows delivers it through the vault's own job wrapper (`harpoc-job.exe --strict`, a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` job the wrapper holds and no member can break away from): the child's normal exit closes the job on every survivor, and a host whose wrapper is unavailable refuses the use fail-closed with `STRICT_TREE_EXIT_UNAVAILABLE` rather than falling back to the `taskkill` tier; POSIX sends `SIGKILL` to the child's own process group after its exit — a descendant that called `setsid` is outside it, the same limit the timeout path has. Without the flag a normal exit leaves survivors exactly as before, on every platform.
- **HTTP response mode**: A per-secret `response_mode` bounds what an HTTP invocation returns. `status_only` returns only the status code (plus an admin-allowlisted header set) and never reads the response body — the response-echo channel is removed structurally, not filtered. The default `filtered` redacts the credential and its base64/base64url/hex/percent encodings, each of them also when JSON-escaped on the wire — any valid escaping, not just the convention V8 emits, since a response body is normally JSON and PHP, Python and Go each escape differently; per-invocation overrides may only tighten the policy mode, never loosen it
- **Session-file protection**: The session file's key is wrapped at rest with an OS-user-bound platform key store — DPAPI (Windows), the Keychain (macOS), Secret Service or the kernel `@u` keyring (Linux desktop/headless tiers) — so a session file copied off the host is inert. Reads fail closed: a tampered blob, a foreign user, or a scheme mismatch invalidates the session and requires a fresh `harpoc unlock`; kernel-keyring keys die at reboot, which likewise forces a fresh unlock rather than degrading. A write-time keystore failure fails the unlock with `SESSION_KEYSTORE_UNAVAILABLE` — nothing is written, and `HARPOC_SESSION_KEYSTORE=off` is the explicit opt-out named in the message; a `none`-tagged file is refused wherever a keystore protector is configured (since 2026-09-04, R8) — and the file is created owner-only (0600) in all cases — as are the vault directory (0700) and the database itself (0600) on POSIX, so the encrypted store is not left readable to every local account by the umask; on Windows the session file's ACL is reduced to the current user through `icacls` invoked with arguments, never a shell string, and a failure to do so is reported rather than swallowed. The key-store bridges are OS-shipped or distro-standard binaries invoked from pinned paths with key material on stdin/stdout only — no native addon, nothing on an argument vector. A `session.json.lock` directory serialises the slide, the fresh write and the erase across processes, so a `harpoc lock` can no longer be resurrected by a concurrent expiry slide.
- **Listener host allowlist and the reverse-proxy stance** (2026-09-04, D61): both HTTP listeners validate `Host` and `Origin` against the operator's `--allowed-host` set (loopback names always allowed on a loopback bind) ahead of authentication, and a non-loopback bind is refused without the flag; there is no native TLS — terminate it at a reverse proxy that preserves `Host`, and note that forwarded headers are never trusted (the audit trail records the proxy).
- **Governance is vault-wide** (2026-09-04, N12): a token carrying a `project` claim is refused on every governance route, command and engine method — per-secret scoping and vault-wide administration do not mix.
- **Dependencies are audited and kept current** (2026-09-30): `pnpm audit` lists no advisory at the current tree — the 95 advisories over sixteen modules it listed on 2026-09-30 were closed the same day (the deferred items closure's phase 3, `docs/implementation-plan-deferred-items-phase3-2026-09-30.md`); the four runtime dependencies (`hono`, `@hono/node-server`, `undici`, `mysql2`) carry declared floors at their patched versions in every manifest that declares them, and `.github/dependabot.yml` proposes weekly updates (minor and patch releases grouped, majors separately, the workflow actions beside) — every dependency change goes through the full gates and both workflows before it lands. The audit is re-run at every release commit; Dependabot alerts are a repository setting the posture does not rely on.

For a summary of the security model, see the [Security Model](README.md#security-model) section of the README.

## Deployment model B

The design overview above holds in both deployment models; they differ in which OS identities the vault and its agents run under (the recipe and the commands: [Deployment models](README.md#deployment-models)).

- **What model B is** (2026-11-05): the vault process runs as a dedicated system user `harpoc` — the vault directory `/var/lib/harpoc` `0700`, the runtime directory `/run/harpoc` `0750 harpoc:harpoc-clients` with one `02750` consumer directory per agent user — and every agent runs under an OS user of its own, a member of `harpoc-clients`, that reaches the vault only over REST or MCP over HTTP with a token. `deploy/linux/install-two-identity.sh` creates the layout; the `ci.yml` ubuntu legs run it and pin the claims below with a two-user integration suite (`two-identity.test.ts`).
- **What it closes**: the agent is no longer code under the vault's OS user. An agent user cannot read the vault directory, the database or the session file (the same-UID read of the session file — and the key-encryption key it unwraps — is what model A cannot prevent); `secret get --value` is reachable only through `GET /api/v1/secrets/:handle/value`, whose `read` scope a use-only token lacks (refused `403` at the scope check, with an `access.denied` row); and `/proc/<pid>/environ` of a child the vault spawns runs under `harpoc` and is unreadable across UIDs (a `PTRACE_MODE_READ_FSCREDS` check that a different, unprivileged UID fails). The same reads succeed for the vault's own UID — model A's exposure, now confined to `harpoc`.
- **What it does not close**: the confused deputy — an agent uses every secret its grant allows, inside the allowlists, as far as the credential's own permissions reach; root and any code under the `harpoc` UID, which read the unlocked key-encryption key as before; physical access — which the sealed unlock key relies on, since whoever boots the machine unseals it; and the agent's own processes — their `/proc`, their environment and their loopback traffic are the agent's to read, other agent users see none of them, root sees all. The REST and MCP listeners are loopback TCP, reachable by every local user: the bearer token is the authentication on every request, and the consumer directory's mode is a second factor on the egress proxy's `proxy.sock` and the only factor on the agent socket's `ssh-agent.sock`, which takes no token; the proxy's TCP listener is token-only. Model B is single-host.
- **The interpreter corollary**: the `process` context runs its child as `harpoc`, so a secret whose command allowlist holds an acknowledged interpreter or exec wrapper (`secret allow --acknowledge-interpreter`) runs agent-authored programs under the vault's UID — **model B collapses to model A for that secret**. For agent-owned work a consumer must not use the `process` context at all; it stays for vault-owned work.
- **The egress credential proxy** (the base-URL form; CONNECT mode next): `server start --proxy` gives an agent's own HTTPS clients a credential they never hold. The client carries a placeholder (`harpoc:<name>`) and its use-scoped token; the proxy swaps the real value in at the egress hop after the caller's `use` grant, the secret's proxy opt-in and its URL allowlist, refuses a placeholder bound for an origin outside the allowlist before contacting it, and audits one `secret.use` row per brokered request — the method, the origin and the path, never a body, a query or a header value. It widens the trust boundary as every egress credential proxy does: the proxy is the vault and sees each brokered request and response in the clear. `response_mode` cannot shape a proxied stream, so the proxy's redaction of brokered responses — the swapped value and its basic-auth base64 form, matched as literal bytes across chunk boundaries, with an uncompressed response requested upstream — is best-effort exact-value redaction, defence in depth and never a guarantee: a compressed or otherwise encoded copy of the value passes it. What the proxy path claims is the vault's: the agent's process never holds the credential. The TCP listener is token-only; the `proxy.sock` in a consumer directory adds the directory's mode as a second factor; clients that honour only `HTTPS_PROXY` take CONNECT mode (next).
- **CONNECT mode and the Harpoc CA** (`harpoc proxy ca init`, 2026-11-09): for a client that honours only `HTTPS_PROXY` the proxy answers `CONNECT`, ends the client's TLS with a leaf for the tunnel's host issued by a Harpoc CA, and handles the requests inside as above. This is the trust-boundary expansion at its widest: the vault reads in the clear everything a consumer sends through a tunnel, brokered or not — the proxy is the vault, and its client's TLS ends there rather than at the host. The containment is the CA's scope: a root, whose key is discarded at creation and which the consumers trust alone, signs one intermediate name-constrained to the hosts the operator lists (RFC 5280 `permittedSubtrees`, the absent name form excluded), so a leaked intermediate impersonates those hosts and their subdomains alone — to the client stacks that honour name constraints, which every stack measured does (Java 8 only on an intermediate, hence the two tiers; the README's table) — and the proxy refuses a CONNECT to any other host before any TLS. The intermediate's key is kept by the vault — the certificate secret `secret://harpoc-ca`, KEK-encrypted at rest and in the daemon's memory while it runs — and is never written to a file, logged, returned or brokered; each leaf's key lives in the daemon alone, for 7 days at most. The documented fallback, an unconstrained CA for a client that rejects a constrained one (none measured does), lets its leaked key impersonate every host to the clients that trust it for as long as it is valid — at most 30 days, created only by an explicit `--unconstrained`, with no revocation endpoint; the proxy still tunnels the listed hosts alone, so the key is its whole residual. What it does not close: root and code under the `harpoc` UID read the intermediate's key as they read the key-encryption key; the daemon holds that signing key from its start until it exits — a lock seals the vault and drains the leases but leaves the proxy's copy (CONNECT then fails at authentication), and only stopping the daemon drops it; a client that ignores name constraints trusts a leaked intermediate for every host; and caller authentication is the token alone — CONNECT, like every TCP path, is token-only, the token crossing the loopback in the CONNECT request's `Proxy-Authorization` and living in the client's environment when it sits in `HTTPS_PROXY`.
- **The agent socket** (`server start --ssh-agent`): an agent's own `ssh` and `git` over SSH authenticate with a key the agent never holds. The vault serves each consumer one `ssh-agent.sock` in its consumer directory, offering the keys of the secrets the consumer holds a `use` grant on and that are opted in with `secret allow --ssh-agent-socket`, and releases signatures only — the private key never leaves the vault process. It signs only on a connection the client bound with `session-bind@openssh.com` (the server's host-key signature over the session identifier, verified on `node:crypto`), only that session's authentication request, and only for a host whose key the secret pins (`secret connection --known-host`) and whose name its host allowlist admits; each signature and each refusal is a `secret.use` row naming the host and the key type (a request past a rate budget, the consumer's or the key's, or on a sealed vault is refused without one), never key material, a signature or a session identifier. What it does not close: the resource — a key valid for several repositories on one host signs for each, and choosing the key per repository is the consumer's `Host` alias; agent forwarding, which is refused rather than bound to the remote hop, a refused bind leaving the connection unable to bind or list, so `ssh -A` through the socket signs nothing there (a bastion is reached with `ssh -J` instead, each hop a direct session the socket signs for when the secret pins and allowlists it); and its reach — every process in the consumer's group can have it sign while it runs, the directory's mode being its only factor (the ssh-agent protocol, RFC 9987, carries no token).
- **The unlock key** (`server start --unlock-credential` / `--unlock-key-file`): the daemon comes back after a reboot with no person and no password on disk. A second slot wraps the key-encryption key with AES-256-GCM under a random 256-bit unlock key — no key derivation, so the database alone gives a reader no more than before — and the key is sealed by a mechanism the vault never learns about; the reference sealer is systemd's credential store (`deploy/linux/enroll-unlock-key.sh` — `systemd-creds encrypt`, the TPM2 and the host key by default — and `LoadCredentialEncrypted=` in `deploy/systemd/harpoc.service`), which hands the key to the unit's user alone. Enrolment and revocation need the password; each unlock from the key writes the `vault.unlock` row with `method: "credential"`; a wrong key counts against the lockout the password shares; the key reaches no message, row or output. What it does not close: physical access — whoever has the machine boots it and the credential unseals; a modified boot of the same machine, since the recipe sets no PCR policy; `host` mode, as safe as the root-readable host key; `--unlock-key-file` without a sealer, a password file by another name.
- **The memory session and token rotation** (`server start --session memory`, `--issue-token`): a daemon in the memory session holds the keys of its unlock in its own memory alone — started from the unlock key it writes no session file, started after an administrator's unlock it reads that file once and leaves it — so no session clock seals it and no administrator's unlock or lock reaches it: the bounded lifetime of an unlocked vault becomes bounded by the daemon's uptime and an explicit lock (`POST /api/v1/vault/lock` with an admin-scoped token, or `SIGTERM`). Every model B flag requires it, refused `SESSION_MODE_CONFLICT` before the vault opens otherwise. With `--issue-token` the daemon issues each consumer's token into the consumer directory — `0640`, the consumer's group through the set-group-ID directory, written under a temporary name and renamed — at the start and again at half its lifetime (at most 24 hours); every mint writes the `token.create` row with `rotation: true`, naming the `jti` and the principal and never the token, and a revoked token, or a deactivated or deleted agent, is not re-minted (a failed `token.create` row records the refusal). What it does not close: root and code under the `harpoc` UID read the keys in the daemon's memory for as long as it runs, as they read the unlocked key-encryption key before; a token file read by anyone but its consumer stays valid until that token's expiry, rotated or not — rotation bounds a token's lifetime, revocation still ends it; and a revoked consumer gets a fresh token at the daemon's next start unless its agent is deactivated or its spec removed.
- **Model B on Windows** (2026-11-08): the vault runs as the local account `harpoc`, started at boot by a scheduled task (`deploy/windows/register-service.ps1` grants that account the right to log on as a batch job, which the task needs to start — the one user right the recipe sets; the task's start is measured on the `windows-latest` runner on demand and at real boots of two Windows Server 2025 machines (2026-11-12: a restart; and, registered with `-Proxy`, `-SshAgent` and `-IssueToken`, two restarts and a start from the deallocated state), see `README.md`, "What the Windows deployment does not close"), and each agent as a local account of its own; the vault directory `%ProgramData%\harpoc\vault` and the runtime directory `%ProgramData%\harpoc\run` grant full control to the vault account, SYSTEM and Administrators alone, and each consumer directory adds read for its agent (`deploy/windows/install-two-identity.ps1`; `server start --runtime-dir` refuses any other access list: the directory's owner must be the vault account, SYSTEM or Administrators, and its access list may grant only those three and, on a consumer directory, the consumer's own local account read-and-execute at most; since 2026-11-11 the directory of an `--issue-token` file is judged the same way under every flag, with the token's own agent in the consumer's place, except that an agent name which resolves to no local account is accepted when the list grants nobody else (a consumer directory is refused then); `%ProgramData%\harpoc\run` is the default under `--ssh-agent`). What it closes, as on Linux: an agent account cannot open the vault directory or the session file, and cannot read the memory or the environment of the vault process or of a child it spawns — opening another account's process for `PROCESS_VM_READ` is checked against that process's access list, which comes from its creator's token, and only `SeDebugPrivilege` opens it regardless (cited from Microsoft's documentation; the `windows-latest` evidence job measures the command-line channel — the agent account's process listing shows the vault process's command line, its paths, ports and each `--issue-token` spec with the consumer, its token file, the names of the secrets it may use, scope and lifetime, but never a secret, since none is ever passed on a command line — and cites the environment block's protection rather than reading it); the unlock key is sealed with DPAPI in the `CurrentUser` scope under the vault account (`--unlock-key-dpapi`), never `LocalMachine`, so the sealed file opens nothing for another account. What it does not close: Administrators and SYSTEM, who read everything as root does on Linux — `SeDebugPrivilege` is the Administrators' by default; whoever can run code as the vault account, anyone holding its password among them, unseals the key, which DPAPI binds to the account's credentials on that machine and not to a boot measurement — no TPM binding; the agent socket's named pipe is reachable as its access list allows — the daemon replaces the list after it opens the pipe (the vault account, SYSTEM and Administrators, and the consumer's account for reading and writing) and refuses to start if it cannot, and a process that creates the pipe's name while the daemon is down makes the start refuse — and that list is its only factor, the ssh-agent protocol carrying no token; and the egress proxy and the REST API, loopback TCP and token-only, with no socket as a second factor on Windows.
- **Identity tokens are not brokered**: an agent's own identity (a chat-channel bot token, a model-provider OAuth token) must be presented by the agent process and cannot be hidden from it; model B keeps third-party secrets away from the agent, not the agent's identity.

## Known Accepted Risks

- **Memory wiping**: JavaScript does not guarantee immediate memory clearing of strings. Wiping of sensitive material in memory is best-effort. Process-mediated injection necessarily passes the credential through a JavaScript string (the subprocess environment) and the child's kernel environment, both outside the vault's zeroization discipline.
- **Injection trust boundary**: Injection assumes a trusted local host. The execution layer that performs injection must be protected from unauthorized access. Process-mediated injection spawns subprocesses without a shell in a clean environment, but the spawned process runs with the credential in its environment.
- **Process output-channel leakage**: Output sanitization redacts the credential and its common encodings (base64/base64url/hex/percent, each also when JSON-escaped) from captured stdout/stderr, but is best-effort. A crafted command can still exfiltrate the credential via an arbitrary encoding, character-by-character chunking, or an indirect file write. Two further residuals are characterized rather than closed: the escape matcher decodes only a single escape layer on its own, but `redactSecretEncodings` wraps it in a structural pass that parses the surrounding JSON document and descends into string leaves that are themselves JSON, to at most four levels of parse depth — not four `JSON.parse` calls in total: a document with many sibling leaves at one level costs one parse per leaf, so the actual call count scales with the document's shape. Total work nonetheless stays bounded, because the leaves at each level are disjoint substrings of their parent — parsing them can never re-scan the same characters twice — so the text parsed across all four levels combined is at most a small constant multiple of the body's own size, and the body itself is already bounded by the descent's size guard (below). Four levels of depth is enough to close the gap for a credential nested as deep as five JSON documents (the document naming it directly, wrapped in as many as four further envelopes). A credential wrapped a sixth document deeper, or carried in a body over the descent's size guard (roughly 4 million characters, not bytes), is still not matched; and the matcher takes the escape reading at a backslash without backtracking, so a value containing a literal backslash adjacent to ambiguous text can still be missed. The fail-safe command allowlist bounds which binaries can be run at all — and an allowlisted binary that is itself a general-purpose instruction vehicle removes that bound, which is why known interpreters are acknowledgement-gated and binaries with a dedicated context are refused outright in the process context; opt-in per-secret network isolation closes the child's own network egress (loopback included) on Linux and macOS, and opt-in per-secret filesystem isolation (`fs_isolation`) closes the specific residual below it — a child denied all filesystem writes (Linux `setpriv`+Landlock or bwrap's read-only bind; macOS `sandbox-exec`; `/dev/null` exempt everywhere) cannot write the value to a file at all, cooperating reader or not. What neither isolation closes: a channel outside the child's own network sockets and file writes — an inherited file descriptor, a debugger or tracer attached from outside the sandbox — is not addressed by either control, and both are opt-in per secret, so a secret without the flag set is unaffected. On Windows both isolations are unsupported by design (an AppContainer would require a native addon): a policy demanding either refuses every process-mediated use there rather than running un-isolated.
- **`full` response mode**: Setting a secret's `response_mode` to `full` disables the vault-layer redaction of that credential (including OAuth access tokens resolved for injection) from HTTP responses — an echoing endpoint then hands the raw value back to the caller. It is settable only via the trusted admin path (CLI/REST, never an MCP tool) and cannot be requested per-invocation unless the policy already allows it. The pattern-based interface guard at the REST/MCP boundaries remains active; CLI and SDK-direct callers receive the truly raw response. Note that REST `PUT .../injection-policy` replaces the whole policy — a client omitting any of the thirteen policy fields is refused `400` naming it; every policy write is audited with its effective mode.
