# Security Policy

## Supported Versions

| Version | Supported |
| ------- | --------- |
| 1.0.x   | Yes       |
| < 1.0   | No        |

## Reporting a Vulnerability

**Do not open a public issue for security vulnerabilities.**

Please report vulnerabilities through [GitHub Security Advisories](https://github.com/HarpocGH/harpoc/security/advisories/new).

### Response Timeline

- **Acknowledgement**: within 48 hours
- **Assessment**: within 7 days
- **Fix (critical)**: within 30 days
- **Fix (non-critical)**: within 90 days

We will coordinate disclosure with the reporter once a fix is available.

## Security Design Overview

Harpoc is a zero-knowledge secret vault designed so that secrets are never exposed to the AI model. Key security properties include:

- **Encryption**: All secrets are encrypted at rest using AES-256-GCM with unique per-secret Data Encryption Keys (DEK)
- **Key hierarchy**: 3-tier hierarchy — Master Key (derived via Argon2id) wraps a KEK, which wraps individual DEKs
- **Minimal in-process cryptography**: All cryptographic operations run on Node's built-in `node:crypto`, with Argon2id (a native KDF) the only exception — no third-party cryptographic library is loaded into the vault process. The SSH context's ephemeral in-process agent parses keys and generates signatures on `node:crypto` (unencrypted Ed25519/RSA/ECDSA keys; passphrase-protected PKCS#8/legacy-PEM keys are decrypted at **import** on the CLI — in memory, `node:crypto` only, the passphrase never persisted — while encrypted OpenSSH-format keys stay unsupported, since bcrypt-pbkdf would re-introduce third-party crypto; a combined certificate + encrypted-key bundle is refused before the passphrase prompt rather than silently reduced to the key alone); the private key stays in the vault process and only signatures cross the agent socket. The identity's public line is written to a per-invocation 0600 temp file and passed as ssh's IdentityFile — public material only, required because `IdentitiesOnly=yes` restricts ssh to file-backed identities; it also means ssh offers exactly the vault identity, never the host user's default `~/.ssh/id_*` keys
- **SSRF prevention**: Pre-flight DNS lookup with IP pinning blocks requests to private/internal network addresses
- **Audit trail**: Append-only by design; tamper-evident rather than database-enforced — detail fields are encrypted and bound to their row, and rows are HMAC-chained, so `harpoc audit verify` detects modification, interior deletion and detail-blob swaps — and erasure of the links themselves, since rows without a chain link are only accepted as a leading prefix of a pre-migration vault, never after a linked row. Every vault mutation commits **in the same SQLite transaction** as its audit entry: a crash cannot produce a completed-but-unaudited operation, and an unwritable audit log blocks the operation (fail-closed) rather than being skipped. `harpoc audit anchor` exports the chain tail; `verify --anchor` detects tail truncation and rollback **provided the anchor is stored off-host** — an attacker who can modify the vault database can likely also modify files beside it, so the vault cannot supply that independent trust domain itself
- **Audit attribution (by whom, through which interface)**: Every token-authenticated credential operation — including `secret.create` and the success row of every `use_secret` invocation, written inside the injectors — carries the requesting principal in the plaintext `principal_type`/`principal_id` columns (covered by the row HMAC chain), the session id, and the access interface (`rest`, `mcp` for stdio, `mcp-http`) inside the encrypted detail. Trusted-local operations (CLI, in-process SDK, stdio MCP explicitly started `--allow-tokenless` — master-password/session authenticated) keep NULL principal columns and no interface tag by design: the "whom" of the administration path is the vault owner. **NULL means trusted-local only for rows written from this release on** — rows from earlier releases predate attribution and are NULL regardless of caller. Vault-initiated MCP lifecycle rows (`mcp.crash` on an async child exit, `mcp.terminate` on seal/policy paths) are deliberately unattributed — no requesting principal exists; `mcp.spawn` is attributed to the invocation that triggered it. `harpoc audit` shows the principal column; the interface appears in the decrypted detail (`--json`)
- **Token revocation takes effect on running servers**: `harpoc auth revoke <jti>` is consulted on every access, not only at connection setup. The Streamable HTTP transport re-verifies the bearer token per request; the stdio transport verifies its launch token once at construction, so its scope guard re-consults the revocation store on every tool and resource call — the check runs ahead of the permission check, so a revoked `admin` token does not pass either. Without that, a revoked token kept its full scope for the life of the server it launched (up to the 24 h token TTL ceiling)
- **The tokenless waiver is on the record**: starting the stdio MCP server with `--allow-tokenless` writes a `server.start` audit event (`{ tokenless: true, transport: "stdio", tty_prompt }`) before the server is constructed — the warning on stderr is a log line, the audit row is the record. It is **fail-closed**: if the row cannot be written, the unrestricted server does not start. Like the other console-launched operations it is unattributed (NULL principal columns, session id stamped). Read the scope precisely: **only the tokenless waiver produces this event.** A token-bearing stdio start, a Streamable HTTP session, the REST API and the OAuth refresh daemon write no `server.start` row — their operations carry per-access attribution instead. So the absence of `server.start` rows means no unrestricted server started, with the same caveat as every other chain property: interior deletion is detected by `audit verify`, tail truncation only against an off-host anchor
- **Audit reads are scoped, not just permission-checked**: the audit surfaces (`GET /api/v1/audit`, MCP `secret://vault/audit/recent`) require `admin`, and additionally honour the token's other two scope dimensions — a row about a secret outside the token's project or name patterns is dropped at the engine, so a scoped admin token cannot read another secret's handles, principals or configuration changes, nor use `?secret_id=` as an oracle for them. Rows without a `secret_id` (vault lifecycle, token issuance, server start) carry no per-secret metadata and stay visible. The CLI and an unrestricted admin token see the whole log
- **Per-secret access policies (engine-enforced)**: Stored policy rows restrict which principals may perform which operations on which secrets. A principal is a type — `agent`, `tool`, `user` (the token's subject under its issued `principal_type` claim, default agent) or `project` (derived from the token's `project` claim, never issuable directly) — plus an identifier; a row grants a permission set (`list` gates enumeration, `read` gates metadata and value reads, `use` gates `use_secret`, `rotate` gates rotation and pending-value set, `revoke` gates revocation; `admin` implies all) with an optional expiry. Enforcement is **presence-gated restriction** at the engine, before anything is decrypted, injected or mutated: a secret carrying at least one active policy row requires the token-derived caller to hold a matching grant; a secret with no rows stays governed by the token's own 3-dimensional scope (which is always checked first at the interface). Denials are audited under the operation's event type with the requesting principal. **Secret-scoped configuration is gated too**: reading a secret's injection policy, MCP-server config, connection config or policy rows requires `read`, changing any of them requires `rotate`, and granting or revoking a policy row itself requires `admin` — otherwise a principal denied `rotate` could still rewrite the allowlists that bound where the credential may be injected, or loosen its `response_mode`, and a principal denied `read` could still enumerate allowlisted hosts, downstream commands and grants. **Enumeration is gated too**: every listing surface — `GET /secrets`, `GET /health/expiring`, `list_secrets`, `check_secret_health` and the MCP secrets/health/projects resources — drops a policy-gated secret unless the caller holds `list` (or `admin`) on it, so the metadata row a denied `read` refuses cannot be recovered from a listing; a grant of only `use` therefore does not make the secret discoverable, and the aggregates (counts, expiring sets, project census) are computed over the filtered set. Filtering is silent — enumeration writes no audit row, as before. Out of scope by design: `create` is **not** a per-secret permission (a policy row attaches to an existing secret, so `grantPolicy` refuses it) and is governed by token scope alone; a secret's _existence_ remains observable to any token whose name pattern reaches it. Callers on that trusted path — CLI, in-process SDK, and stdio MCP explicitly launched with `--allow-tokenless` (the warned-about local full-access mode; a launch token is otherwise required at stdio startup, `TOKEN_REQUIRED`) — authenticate via master password/session file and are not subject to per-secret policies (the administration-versus-operation split)
- **A downstream child never outlives the credential**: a stdio MCP server the vault spawned holds the plaintext in its environment for as long as it runs, so revoking a secret, its expiry, a rotation, a configuration change and every seal path (lock, destroy, session expiry, key wipe) terminate that connection, audited as `mcp.terminate`. A revocation performed from _another_ process (the CLI, while a server is running) cannot reach that server's in-memory registry — there the teardown happens when the server next tries to use the secret and is refused, which is also when the credential would otherwise have been used again
- **Execution-layer injection**: Secrets are injected at the execution layer across six contexts — an HTTP request, a spawned subprocess's environment, a downstream MCP server, a database connection, a Git operation, or an SSH session — and never returned to the LLM context. Per-secret allowlists bound where a credential may be injected: an optional URL allowlist for HTTP, a fail-safe command allowlist for process execution (with an explicit acknowledgement gate for known interpreter binaries), and a host allowlist for database/SSH/Git targets (fail-safe for SSH and Git-over-SSH). Endpoint authentication is pinned per secret: database TLS/CA policy and SSH host keys
- **Contexts do not leak into one another**: the Git and SSH contexts require their binary in the secret's command allowlist — that entry is what pins `git`/`ssh` to a resolved absolute path — but the allowlist is a single field and the caller chooses the context per invocation. The process context therefore **refuses any binary that has a dedicated context of its own** (`DEDICATED_CONTEXT_REQUIRED`, audited before any spawn, no environment opt-out), matched against the resolved symlink-followed path. Without that refusal, a caller holding only `use` on a Git- or SSH-configured secret could run the same binary through the process context, where the vault inspects no argument — `git -c 'alias.x=!<command>' x` and `ssh -oProxyCommand=<command> host` are arbitrary execution with the credential in the child's environment, and no configuration could enable the Git or SSH context without also granting it. Interpreters are deliberately handled by the acknowledgement gate instead: allowlisting `bash`/`node`/`npx` is already an explicit, audited administrator decision, whereas `git` and `ssh` carried no such acknowledgement
- **Git-over-HTTPS target control extends past the URL string**: the credential is bound to the host the vault validated — the askpass helper compares the host git names in the prompt and refuses anything else, including a prompt naming no recognizable URL — redirect following is disabled (`http.followRedirects=false`), and `--recurse-submodules`/`--recursive` are denied. Otherwise a `30x` from the validated host, or a `.gitmodules` entry in the cloned repository, moves the credential prompt to a host the vault never resolved, validated or allowlisted. Denied-argument matching also accounts for git's own option abbreviation (`--templ=` reaches `--template`), so the clone-time hook-execution options cannot be smuggled in under a shortened name
- **Injector errors are redacted too**: a thrown error is a model-visible channel — the MCP SDK turns it into the tool result text and the REST error handler returns the message — so error text carrying attacker-influenced strings (a refused redirect target chosen by the endpoint that just received the credential, a driver message quoting a connection string) passes through credential redaction on the way out, and refusals name only a target's origin rather than its full URL. Redaction covers JSON object **keys** as well as values, since the party naming keys in a proxied MCP result or a SQL column alias is not the vault
- **Network isolation** (opt-in, per secret): with `network_isolation` on the injection policy, every child process spawned with the secret (process, Git and SSH contexts) runs without network access — loopback included, since the vault's own REST/MCP listeners live there. Linux delivers it via `unshare -rn` (unprivileged user + network namespaces; note that stock Ubuntu 24.04+ restricts unprivileged user namespaces via AppArmor, which the probe detects — uses are then refused until the restriction is relaxed), macOS via `sandbox-exec` with a constant deny-network profile; both are probed live at first use, and only a successful probe is cached — a transient probe failure re-probes on the next use instead of permanently disabling isolation. Windows is unsupported by design (real per-process isolation requires an AppContainer native addon). **Fail closed**: a platform that cannot deliver demanded isolation refuses the use with `NETWORK_ISOLATION_UNAVAILABLE` before any process is spawned, and the denial is audited — there is no silent degrade and no environment-variable opt-out. The wrapper is vault-authored, resolved from pinned absolute paths, and applied after command-allowlist resolution; agent input never reaches it. Setting the flag terminates any live stdio MCP downstream child already holding the secret (audited `mcp.terminate`); a policy tightened from a separate process takes effect at that server's next invocation attempt — the in-memory connection registry is per-process. Every process/git/ssh use — including security denials such as host-key mismatches — is audited with its isolation state and mechanism
- **HTTP response mode**: A per-secret `response_mode` bounds what an HTTP invocation returns. `status_only` returns only the status code (plus an admin-allowlisted header set) and never reads the response body — the response-echo channel is removed structurally, not filtered. The default `filtered` redacts the credential and its base64/base64url/hex/percent encodings; per-invocation overrides may only tighten the policy mode, never loosen it
- **Session-file protection**: The session file's key is wrapped at rest with an OS-user-bound platform key store — DPAPI (Windows), the Keychain (macOS), Secret Service or the kernel `@u` keyring (Linux desktop/headless tiers) — so a session file copied off the host is inert. Reads fail closed: a tampered blob, a foreign user, or a scheme mismatch invalidates the session and requires a fresh `harpoc unlock`; kernel-keyring keys die at reboot, which likewise forces a fresh unlock rather than degrading. A write-time keystore failure falls back to the file-permission-only session with a CLI warning (`HARPOC_SESSION_KEYSTORE=off` is the explicit opt-out), and the file is created owner-only (0600) in all cases — as are the vault directory (0700) and the database itself (0600) on POSIX, so the encrypted store is not left readable to every local account by the umask; on Windows the session file's ACL is reduced to the current user through `icacls` invoked with arguments, never a shell string, and a failure to do so is reported rather than swallowed. The key-store bridges are OS-shipped or distro-standard binaries invoked from pinned paths with key material on stdin/stdout only — no native addon, nothing on an argument vector

For a summary of the security model, see the [Security Model](README.md#security-model) section of the README.

## Known Accepted Risks

- **Memory wiping**: JavaScript does not guarantee immediate memory clearing of strings. Wiping of sensitive material in memory is best-effort. Process-mediated injection necessarily passes the credential through a JavaScript string (the subprocess environment) and the child's kernel environment, both outside the vault's zeroization discipline.
- **Injection trust boundary**: Injection assumes a trusted local host. The execution layer that performs injection must be protected from unauthorized access. Process-mediated injection spawns subprocesses without a shell in a clean environment, but the spawned process runs with the credential in its environment.
- **Process output-channel leakage**: Output sanitization redacts the credential and its common encodings (base64/hex/percent) from captured stdout/stderr, but is best-effort. A crafted command can still exfiltrate the credential via an arbitrary encoding, character-by-character chunking, or an indirect file write. The fail-safe command allowlist bounds which binaries can be run at all — and an allowlisted binary that is itself a general-purpose instruction vehicle removes that bound, which is why known interpreters are acknowledgement-gated and binaries with a dedicated context are refused outright in the process context; opt-in per-secret network isolation closes the child's own network egress (loopback included) on Linux and macOS. What isolation does **not** close: the child can still write the value to a file that a cooperating other process — the agent among them — reads and exfiltrates later; that channel's reader is outside the child, so no child-side control can remove it. On Windows network isolation is unsupported by design (an AppContainer would require a native addon): a policy demanding it refuses every process-mediated use there rather than running un-isolated.
- **`full` response mode**: Setting a secret's `response_mode` to `full` disables the vault-layer redaction of that credential (including OAuth access tokens resolved for injection) from HTTP responses — an echoing endpoint then hands the raw value back to the caller. It is settable only via the trusted admin path (CLI/REST, never an MCP tool) and cannot be requested per-invocation unless the policy already allows it. The pattern-based interface guard at the REST/MCP boundaries remains active; CLI and SDK-direct callers receive the truly raw response. Note that REST `PUT .../injection-policy` replaces the whole policy — a client omitting `response_mode` resets it to the `filtered` default; every policy write is audited with its effective mode.
