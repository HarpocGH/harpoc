# Security Policy

## Supported Versions

| Version | Supported |
| ------- | --------- |
| 1.5.x   | Yes       |
| < 1.5   | No        |

`1.0.x` was a pre-release with no users and no upgrade path — a 1.0.x vault is not opened by 1.5, which only opens vaults it created (`CHANGELOG.md` § `[1.5.0]`).

## Reporting a Vulnerability

**Do not open a public issue for security vulnerabilities.**

Please report vulnerabilities through [GitHub Security Advisories](https://github.com/HarpocGH/harpoc/security/advisories/new).

### Response Timeline

- **Acknowledgement**: within 48 hours
- **Assessment**: within 7 days
- **Fix (critical)**: within 30 days
- **Fix (non-critical)**: within 90 days

We will coordinate disclosure with the reporter once a fix is available.

## Security Design Overview

Harpoc is a zero-knowledge secret vault designed so that secrets are never exposed to the AI model. Key security properties include:

- **Encryption**: All secrets are encrypted at rest using AES-256-GCM with unique per-secret Data Encryption Keys (DEK)
- **Key hierarchy**: 3-tier hierarchy — Master Key (derived via Argon2id) wraps a KEK, which wraps individual DEKs
- **Minimal in-process cryptography**: All cryptographic operations run on Node's built-in `node:crypto`, with Argon2id (a native KDF) the only exception — no third-party cryptographic library is loaded into the vault process. The SSH context's ephemeral in-process agent parses keys and generates signatures on `node:crypto` (unencrypted Ed25519/RSA/ECDSA keys; passphrase-protected PKCS#8/legacy-PEM keys are decrypted at **import** on the CLI — in memory, `node:crypto` only, the passphrase never persisted — while encrypted OpenSSH-format keys stay unsupported, since bcrypt-pbkdf would re-introduce third-party crypto; a combined certificate + encrypted-key bundle is refused before the passphrase prompt rather than silently reduced to the key alone); the private key stays in the vault process and only signatures cross the agent socket. The identity's public line is written to a per-invocation 0600 temp file and passed as ssh's IdentityFile — public material only, required because `IdentitiesOnly=yes` restricts ssh to file-backed identities; it also means ssh offers exactly the vault identity, never the host user's default `~/.ssh/id_*` keys. On Windows an MSYS/Cygwin ssh client is refused before the spawn (`SSH_CLIENT_UNSUPPORTED`): it cannot open the agent's named pipe and would fail in a way that reads as a remote refusal.
- **SSRF prevention**: Pre-flight DNS lookup with IP pinning blocks requests to private/internal network addresses; git over HTTPS is handed the judged addresses too, and a git older than 2.37, which would ignore them, is refused for a host the vault resolves; on Windows a pull, a push and a fetch need git 2.37.1 or later, judged with the patch number, since there the vault reads no owner and no access list and git's own ownership check stands in the owner's place, nothing in the modes' place (**The repository the git context serves**, below) (2026-11-23); an allowlisted `HTTPS_PROXY` resolves the target itself; a repository host that begins with `-` or `+`, and an IP version the judged addresses lack, are refused so that the pin cannot be dropped; the pin's entry needs libcurl 7.59.0 or later (7.57.0 for a bracketed IPv6 address), and a git from 2.37 to 2.47 built against an older libcurl — possible in principle — cannot be told from its version, is not refused and may resolve the name itself (inferred, not measured)
- **Audit trail**: Append-only by design; tamper-evident rather than database-enforced — detail fields are encrypted and bound to their row, and rows are HMAC-chained, so `harpoc audit verify` detects modification, interior deletion and detail-blob swaps — and erasure of the links themselves, since a row without a chain link is a break wherever it stands, a leading one included — every row of a vault this release opens carries one (a vault created before the chain, migration 010, does not open). Every vault mutation commits **in the same SQLite transaction** as its audit entry: a crash cannot produce a completed-but-unaudited operation, and an unwritable audit log blocks the operation (fail-closed) rather than being skipped. `harpoc audit anchor` exports the chain tail; `verify --anchor` detects tail truncation and rollback **provided the anchor is stored off-host** — an attacker who can modify the vault database can likely also modify files beside it, so the vault cannot supply that independent trust domain itself
- **Audit attribution (by whom, through which interface)**: Every token-authenticated credential operation — including `secret.create` and the success row of every `use_secret` invocation, written inside the injectors or, for the SMTP, IMAP, WebSocket, SFTP and docker-registry contexts, an ssh bootstrap and an SFTP render, by the engine (2026-11-25) — carries the requesting principal in the plaintext `principal_type`/`principal_id` columns (covered by the row HMAC chain), the session id, and the access interface (`rest`, `mcp` for stdio, `mcp-http`, `cli`, `proxy`, `ssh_agent`) inside the encrypted detail. `cli` marks any CLI invocation carrying a scoped token (`--token` or `HARPOC_TOKEN`) — every command with a REST counterpart accepts one (`secret use/get/list/set/rotate/delete/allow/mcp-server/connection`, `policy grant/revoke/list`, `audit`, `oauth status/refresh`), each verified and scope-checked exactly as the REST API checks the matching route, and subject to per-secret access policies like any other token-bearing caller. Trusted-local operations (tokenless CLI, in-process SDK — master-password/session authenticated) keep NULL principal columns and no interface tag by design: the "whom" of the administration path is the vault owner. A stdio MCP server explicitly started `--allow-tokenless` is no longer one of them: since 2026-09-02 its operations are attributed to `user` / `tokenless-stdio` with `interface: "mcp"` in the detail. **NULL means trusted-local only for rows written from this release on** — rows from earlier releases predate attribution and are NULL regardless of caller. Vault-initiated MCP lifecycle rows (`mcp.crash` on an async child exit, `mcp.terminate` on seal/policy paths) are deliberately unattributed — no requesting principal exists; `mcp.spawn` is attributed to the invocation that triggered it. `harpoc audit` shows the principal column; the interface appears in the decrypted detail (`--json`)
- **Scope refusals are audited** (2026-09-23): every token-scope refusal on the REST API, the MCP server and the egress proxy, and the CLI's `--token` scope refusal — a missing permission, a project mismatch, a secret-name pattern, and the governance routes' project-claim refusal — writes one `access.denied` row under the requesting principal naming the operation (`<METHOD> <path>`, the egress proxy's `<METHOD> <origin><path>`, or the tool or resource) and the reason before the refusal is answered; the CLI's `--token` row names the command path as typed after `harpoc` (`secret list`, `audit verify`, …) (2026-11-12); a refusal is never silent; on the MCP server the row is written within the global rate-limit budget — a caller past it is answered `RATE_LIMIT_EXCEEDED` and writes no row (2026-09-24). Expiry and revocation (401) are not scope refusals. The REST interface prints each request's method and path in its `[audit]` line and records them in a scope refusal's row; a path segment that holds a token-shaped text is written as `<token>` and a control character as its percent-escape, every other segment as the server reads it — a secret does not belong in a request path. The egress proxy also writes one `access.denied` row for three refusals of an authenticated consumer that are no scope refusal (2026-11-18): a CONNECT to a host outside the Harpoc CA's names (`PROXY_CONNECT_DENIED`, the operation `CONNECT <host>:<port>`; for the first refusal of that host and port in the principal's budget window, below), a request with two or more placeholders (`PROXY_PLACEHOLDER_DENIED`) and a request without a placeholder whose target the SSRF floor refuses (`SSRF_BLOCKED`), the last two naming `<METHOD> <origin>` — each with `reason: "proxy"` and the refusal's code, the operation cut at 300 characters, before the `403`; a row that cannot be written answers in the refusal's place (`503 VAULT_LOCKED`). Each principal's refusals are budgeted: 60 in the 60 seconds from its first — those three, the scope refusal and a refusal of the engine's lease (such as an unknown handle, a missing grant or an origin outside the allowlist), not `INVALID_INPUT` and not a failure with a status of 500 or above such as a sealed vault or a failed OAuth refresh. A refused CONNECT writes its row and is charged only for the first refusal of its host and port in the window (2026-11-19): a repeat inside the window is answered `403` `PROXY_CONNECT_DENIED` with no row, no charge and no line on the daemon's standard error, so the log shows that a host was refused in that window, not how often, and each spelling of an IP literal counts as a host of its own. The refusal that spends the budget writes one more `access.denied` row (`RATE_LIMIT_EXCEEDED`), and `server start --proxy` prints `[harpoc] egress proxy: RATE_LIMIT_EXCEEDED` once for it (2026-11-19); from then until the 60 seconds end every proxy request of the principal is refused `429` `RATE_LIMIT_EXCEEDED` right after its authentication, with no row and no printed line.
- **Token revocation takes effect on running servers**: `harpoc auth revoke <jti>` is consulted on every access, not only at connection setup. The Streamable HTTP transport re-verifies the bearer token per request; the stdio transport verifies its launch token once at construction, so its scope guard re-consults the revocation store on every tool and resource call — the check runs ahead of the permission check, so a revoked `admin` token does not pass either. Without that, a revoked token kept its full scope for the life of the server it launched (up to the 24 h token TTL ceiling)
- **The tokenless waiver is on the record**: starting the stdio MCP server with `--allow-tokenless` writes a `server.start` audit event (`{ tokenless: true, transport: "stdio", tty_prompt }`) before the server is constructed — the warning on stderr is a log line, the audit row is the record. It is **fail-closed**: if the row cannot be written, the unrestricted server does not start. The row is unattributed (NULL principal columns, session id stamped) like every `server.start`; since 2026-09-02 every transport writes one — the token-bearing stdio start with the token's subject, each HTTP or REST listener with its bound port — and a graceful shutdown writes the matching `server.stop`, as do a start that fails after a listener came up and a listener that fails after its bind (`trigger` `start_failed`, `listener_failed`), so the waiver is the `tokenless: true` row with `transport: "stdio"` among them (an agent-socket listener's `server.start` carries `tokenless: true` as well, with `transport: "ssh-agent"`). The operations an unrestricted server performs are attributed to `user` / `tokenless-stdio` rather than to a NULL principal, so they never blend into the CLI's rows.
- **Audit reads are scoped, not just permission-checked**: the audit surfaces (`GET /api/v1/audit`, MCP `secret://vault/audit/recent`) require `admin`, and additionally honour the token's other two scope dimensions — a row about a secret outside the token's project or name patterns is dropped at the engine, so a scoped admin token cannot read another secret's handles, principals or configuration changes, nor use `?secret_id=` as an oracle for them. Rows without a `secret_id` (vault lifecycle, token issuance, server start) carry no per-secret metadata and stay visible, except a failed row of a per-secret event type or `access.denied`, and every `vault.read` row, which a scoped reader does not see; a token issuance row names the token's subject, project, scope and jti, never its name patterns. The CLI and an unrestricted admin token see the whole log
- **Per-secret access policies (engine-enforced)**: Stored policy rows restrict which principals may perform which operations on which secrets. A principal is a type — `agent`, `tool`, `user` (the token's subject under its issued `principal_type` claim, default agent) or `project` (derived from the token's `project` claim, never issuable directly) — plus an identifier; a row grants a permission set (`list` gates enumeration, `read` gates metadata and value reads, `use` gates `use_secret`, `rotate` gates rotation and pending-value set, `revoke` gates revocation — save that an ssh bootstrap's end, and a use that meets a bootstrap's mark its own engine does not hold, end the secret for a caller that holds `use` alone, with a `secret.revoke` row whose `reason` is `ssh_bootstrap` (2026-11-24; **The ssh bootstrap**, below) —; `admin` implies all) with an optional expiry. Enforcement is **explicit-grant** at the engine, before anything is decrypted, injected or mutated: a token-derived caller acts on a secret only through a matching, unexpired grant to one of its principals, and a secret with no rows is reachable by no agent- or tool-type token (the token's own 3-dimensional scope is still checked first at the interface; the trusted path and admin-scoped `user`-type tokens are exempt). Denials are audited under the operation's event type with the requesting principal. **Secret-scoped configuration is gated too**: reading a secret's injection policy, MCP-server config, connection config or policy rows requires `read`, changing the MCP-server or connection config requires `rotate`, changing the injection policy requires `admin` (it widens where the credential may go), and granting or revoking a policy row itself requires `admin` — otherwise a principal denied `rotate` could still rewrite the allowlists that bound where the credential may be injected, or loosen its `response_mode`, and a principal denied `read` could still enumerate allowlisted hosts, downstream commands and grants. **Enumeration is gated too**: every listing surface — `GET /secrets`, `GET /health/expiring`, `list_secrets`, `check_secret_health` and the MCP secrets/health/projects resources — drops a secret unless the caller holds `list` (or `admin`) on it, so the metadata row a denied `read` refuses cannot be recovered from a listing; a grant of only `use` therefore does not make the secret discoverable, and the aggregates (counts, expiring sets, project census) are computed over the filtered set. Filtering is silent toward the caller, but each enumeration the engine runs writes one `vault.read` row that records how many entries it returned and how many the filter withheld, never a name (2026-11-12). Out of scope by design: `create` is **not** a per-secret permission (a policy row attaches to an existing secret, so `grantPolicy` refuses it) and is governed by token scope alone. A caller holding none of `read`/`list`/`admin` on a secret receives `SECRET_NOT_FOUND` (404), byte-identical to an unknown handle, so a secret's existence is not observable to a token without a grant; the audit row still records `ACCESS_DENIED` with the real secret id. The one accepted exception is the policy-write (`admin`) checks — `POST /secrets/:handle/policies`, `PUT /agents/:name/secrets/:handle/permissions`, `PUT /secrets/:handle/injection-policy` — which keep `ACCESS_DENIED` on a real handle so the matrix editor's `harpoc policy grant …` remedy survives; an admin-scoped agent- or tool-type token can therefore still tell a real name from a wrong one on those three routes, and on nothing else. Callers on that trusted path — CLI, in-process SDK, and stdio MCP explicitly launched with `--allow-tokenless` (the warned-about local full-access mode; a launch token is otherwise required at stdio startup, `TOKEN_REQUIRED`) — authenticate via master password/session file and are not subject to per-secret policies (the administration-versus-operation split)
- **A downstream child never outlives the credential**: a stdio MCP server the vault spawned holds the plaintext in its environment for as long as it runs, so revoking a secret, its expiry, a rotation, a configuration change and every seal path (lock, destroy, session expiry, key wipe) terminate that connection, audited as `mcp.terminate` where the close is graceful, while a seal path's hard kill writes no row (what a seal path does not end: **A lock under a use in flight**, below). A revocation performed from _another_ process (the CLI, while a server is running) cannot reach that server's in-memory registry — there the teardown happens when the server next tries to use the secret and is refused, which is also when the credential would otherwise have been used again; a downstream MCP server configuration removed by another process ends the live child at the next `mcp` use of that secret on the daemon; until then the idle sweep bounds it. Every seal path likewise ends a running SFTP render: it aborts the render's `ssh` child and writes the render's rows with `error: "VAULT_LOCKED"` before the keys are zeroed (2026-11-25)
- **A lock under a use in flight** (2026-11-25): every wipe of the keys — a lock, a destroy, a session's end, an unlock over an unlocked engine, the seal after a failed session write — writes the rows of the calls it finds in flight, then seals the session's audit logger, which zeroes the audit chain key, and only then zeroes the keys, so no row is written under a zeroed key: a sealed logger writes nothing and answers `VAULT_LOCKED`, a mutation whose row shares its transaction rolls back, and an OAuth refresh or a lazy expiry that ends after the wipe stores nothing. A `use_secret` call — save an ssh bootstrap and an SFTP render, which keep their own answers to a lock — from its decrypt, or for an OAuth secret the token read that may refresh, until it returns, a proxied resolve from its decrypt until its lease opens and an agent-socket signature from its decrypt until its row answer `VAULT_LOCKED` with exactly one failed `secret.use` row, `error: "VAULT_LOCKED"`, under the secret the call judged and the session it began in; a call whose row was written before the wipe returns what it had. A call the wipe meets before its decrypt answers `VAULT_LOCKED` with no row, as on a locked vault, and a call that outlives the wipe and the next unlock writes nothing into the new session. The wipe ends the child of a `process`, `ssh`, `sftp` transfer (`upload`, `download`, `list`), `git` or `docker_registry` use — git starts no later step — and of an ssh bootstrap, and a stdio MCP child still in its handshake; an `http`, `websocket`, `database`, `smtp` or `imap` use that has not begun to send — the vault's last test before the credential enters a request or a connection not yet passed — sends nothing, an `mcp` use over http that opens its connection sends no request of its handshake that meets the wipe at its test, and the wipe closes its client; and the MCP connection registry starts no connection during the graceful close a lock, a destroy and the session monitor make before they wipe, nor after the wipe. What it does not close: an `http`, `websocket`, `database`, `smtp` or `imap` use that has begun to send — its connect, TLS handshake or authentication under way, an http redirect's next hop, an MCP request's connect past its test — is not cut: the remote side may complete it, the result is discarded, and the value stays in memory until the remote side settles or the context's own deadline ends it. A row that cannot be written leaves its call without a row, and the wipe goes on. The row holds what the engine holds at the decrypt — a use's `handle` and `context`, the proxy's request, the signature's `context` and `key_type` — not the target an injector would have named, and it says that the vault sealed under the call, not whether the call took effect. A refresh token the provider rotated in a request that returns after the keys are gone is lost, and the secret needs its authorization again. On a Windows host without the job wrapper a child dies through `taskkill`, which the wipe starts and does not wait for, so it may run on for up to ten seconds; a docker use's daemon may finish what its ended CLI began. An MCP child already in a graceful close at the wipe — a terminate for a rotation, a changed configuration or the idle bound — ends by that close's own escalation, `SIGTERM` two seconds and `SIGKILL` four seconds after the close began where it has not exited by then, and where the wipe is the daemon's stop it is not signalled at all; where neither the job wrapper nor a POSIX strict tree exit applies, the hard kill reaches the direct process alone, so a process it started can outlive it. A lock that lands after a refusal's row and before the call returns can answer first: a bootstrap mark's refusal then answers `VAULT_LOCKED`, its row in the trail; and an ssh bootstrap's `began` row stands without an outcome row, its mark left for the next use that reaches it (**The ssh bootstrap**, below). A proxied resolve or a signature whose decrypt ends while `lock()` waits to wipe — the state sealed, the keys still live — answers `VAULT_LOCKED` and leaves no row, while a use there writes its row under the live key and returns.
- **Execution-layer injection**: Secrets are injected at the execution layer across eleven contexts — an HTTP request, a spawned subprocess's environment, a downstream MCP server, a database connection, a Git operation, an SSH session, an SMTP mail session, an IMAP mail session, a WebSocket connection, an SFTP transfer, or a docker-registry operation — and never returned to the LLM context. Per-secret allowlists bound where a credential may be injected: a deny-by-default URL allowlist for HTTP, WebSocket, MCP-over-HTTP and Git-HTTPS, a fail-safe command allowlist for process execution (with an explicit acknowledgement gate for known interpreter binaries and, since 2026-09-04, for exec wrappers — binaries whose argv is itself a command), and a deny-by-default host allowlist for database, SMTP, IMAP, SSH, SFTP, Git-SSH and docker-registry targets — save the ssh bootstrap, whose one host, port and user and whose host keys are its block's alone, neither the host allowlist nor the connection config's known-hosts pin read for it (2026-11-24), and the SFTP render, whose host is judged under the delivering key's host allowlist and whose host keys are its entry's own, the connection config's known-hosts pin not read for it (2026-11-25). Endpoint authentication is pinned per secret: database TLS/CA policy and SSH host keys. From 2026-10-15 until 2026-11-23, in no released version, the ssh, sftp and git-over-ssh contexts passed `GlobalKnownHostsFile=none`; an OpenSSH client before 8.5 reads a file of that name in its working directory, which for the ssh and sftp contexts is the vault process's own — for a server an agent's harness starts, commonly a directory the agent writes to — so a planted `none` holding a host's key made ssh accept that host (measured on 8.4p1). The three contexts now hand ssh an empty global known-hosts file of the vault's own, written beside the pinned one, on every platform (2026-11-23)
- **Contexts do not leak into one another**: the Git, SSH, SFTP and docker-registry contexts require their binary in the secret's command allowlist — that entry is what pins `git`/`ssh`/`sftp`/`docker` to a resolved absolute path; an SFTP render needs `ssh`, not `sftp`, on the delivering key's (2026-11-25) — but the allowlist is a single field and the caller chooses the context per invocation. The process context therefore **refuses any binary that has a dedicated context of its own** (`DEDICATED_CONTEXT_REQUIRED`, audited before any spawn, no environment opt-out; `sftp` and `docker` since 2026-11-18), matched against the command's name as found on the path, before links are followed, its name once they are followed, and the name of every allowlist entry that resolves to the same file (2026-11-19): a `docker` that is a link to `snap` or `podman` is refused under its own name, and on a host where `docker` is a snap a secret whose allowlist lists `docker` runs neither `docker` nor `snap` nor any other snap command in the process context — at the cost that a secret listing `docker` and `podman` on a host where `docker` is a link to `podman` cannot run `podman` there. A hard link under another name is out of the gate's reach, as a renamed copy is. Without that refusal, a caller holding only `use` on a secret configured for one of those contexts could run the same binary through the process context, where the vault inspects no argument — `git -c 'alias.x=!<command>' x`, `ssh -oProxyCommand=<command> host` and `sftp -oProxyCommand=<command> host` are arbitrary execution with the credential in the child's environment, `docker run -e <variable>` hands it to a container of the caller's choosing, and no configuration could enable one of those contexts without also granting it. Interpreters are deliberately handled by the acknowledgement gate instead: allowlisting `bash`/`node`/`npx` is already an explicit, audited administrator decision, whereas `git`, `ssh`, `sftp` and `docker` carried no such acknowledgement. A secret whose policy holds an SFTP render entry is refused every action but the render, the process context's among them (`RENDER_ONLY_KEY`, 2026-11-25; **The SFTP render**, above)
- **Git-over-HTTPS target control extends past the URL string**: the credential is bound to the host the vault validated — the askpass helper compares the host git names in the prompt and refuses anything else, including a prompt naming no recognizable URL — redirect following is disabled (`http.followRedirects=false`), and `--recurse-submodules`/`--recursive` are denied. Otherwise a `30x` from the validated host, or a `.gitmodules` entry in the cloned repository, moves the credential prompt to a host the vault never resolved, validated or allowlisted. Denied-argument matching also accounts for git's own option abbreviation (`--templ=` reaches `--template`), so the clone-time hook-execution options cannot be smuggled in under a shortened name. A hook already present in a caller-supplied working tree is a separate vector: every git run forces `core.hooksPath` to an empty vault-authored directory, so `post-merge`, `pre-push` and a template's `post-checkout` never execute with the credential in their environment (2026-09-04, N11).
- **A fetch and an ls-remote keep the git context's guarantees** (2026-11-10): both run their credential-bearing step in a relay repository the vault writes for the call and re-validates before and after it, under the configuration every git run carries — `core.hooksPath` at an empty vault-authored directory, `credential.helper` and `core.fsmonitor` neutralised, `safe.bareRepository=explicit` on every step but the version read (2026-11-23), no system or global configuration, and none of git's repository variables from the environment, whatever `env_allowlist` names (2026-11-23) — and the same denied arguments under git's own abbreviation: `--upload-pack`, which names a program to run, and `--no-upload-pack`, which would cancel the vault's own `--upload-pack=git-upload-pack` on a local step (2026-11-23), on both as on every operation; on a fetch the options that would move the checked-out branch's ref under its work tree (`-u` / `--update-head-ok`), take refspecs from other remotes or from standard input (`--multiple`, `--all`, `--stdin`), choose destinations past the vault's own (`--refmap`) or write the caller's configuration (`--set-upstream`, and `--filter`, whose partial clone would later fetch without the credential); on a clone `--bare`, `--naked`, `--mirror`, `--reference`, `--reference-if-able`, `--shared` and `-s`, and on a pull `--edit`, `-e` and an interactive rebase (`--rebase=interactive`, `--rebase=i`, `-ri`) (2026-11-23). A fetch's refspecs name the remote's branches and tags only and the vault chooses where they land; the step that writes into the caller's tree runs without the credential, with an empty `--refmap=` so that no fetch refspec of the tree's configuration adds a destination, and writes the remote-tracking refs of the tree's one remote for that repository — under `refs/prefetch/` instead when the caller passes git's own `--prefetch` — and the tags; no hook of the tree runs in either step, a `reference-transaction` hook, which git runs for every ref update, included. The repository rides behind `--` by the vault's own check, not git's: a repository that begins with `-` is refused, since a caller's trailing option that takes a value could take the vault's `--` as that value and leave the repository to be parsed as an option; and an scp-form repository whose user part holds a colon — which git splits at that colon while the vault read the host after the `@` — is no SSH repository to the vault (`GIT_UNSUPPORTED_TRANSPORT`); both on all five operations since 2026-11-10. For a git-over-SSH use the host the allowlist judged and the audit row names is the host the vault's ssh dials and checks the host key of: the vault hands it to ssh as `HostName`, ahead of every other option, so whatever destination git derives from the address — by its bracket rule, by percent-decoding an `ssh://` URL before it looks for the authority's end, and ssh by splitting at the last `@` — names the port at most (the user, where the address names one, is handed to ssh as `User` beside `HostName`; an `ssh://` address that names none but holds an `@`, written plainly or as `%40`, is refused); a host that is not a host name — ASCII letters, digits, `.`, `_` and `-`, beginning with a letter or a digit, 255 characters at most — or the IPv6 literal of an `ssh://` URL is refused (`INVALID_GIT_CONFIG`) before the allowlist is consulted, its text never written into a row; on all five operations since 2026-11-10 (until then a crafted address could make the vault's ssh try another host than the one judged). The user of the address is judged after the host and before the allowlist (since 2026-11-11): a name of letters, digits, `.`, `_` and `-` that begins with a letter or a digit, else `INVALID_GIT_CONFIG`, as is an `ssh://` address that carries a password. Hooks stay disabled in the credential step by design: a hook there runs caller-controlled code with the credential in its environment, which is what N11 and the relay close; under deployment model B an agent's own `git` runs its own hooks under its own UID, outside the vault. Every refusal the git context makes before a step of the operation runs — a denied argument, a positional, a refspec, a working directory it refuses or requires, an operation it does not know, an `ssh` binary missing from its PATH — writes a failed `secret.use` row carrying the operation and the error code, never the refused argument, refspec or path, on all five operations (until 2026-11-10 such a refusal on a clone, pull or push left no row). What stays open: an `ls-remote` returns refnames and object ids the remote chose — untrusted text in the model's context, redacted for the credential and capped like every git result, never an instruction the vault acts on; a fetch writes remote-chosen ref names into the tree's remote-tracking namespace and its tags, as a direct `git fetch` would; outside a daemon a `[remote "<repository>"]` section of the tree's own configuration still shapes the credential-free local step as git lets a remote's section shape a fetch (its `url`, `prune`, `tagOpt`; its `uploadpack` no longer, the vault passing its own, and in a daemon such a section refuses the fetch, since 2026-11-23) — the tree owner's configuration, with no credential in that step; the host allowlist of a git-over-SSH use is host-only: the port and the path are the ones git and ssh read from the address, by rules of their own — a `[host]:port` line of the secret's known-hosts pin binds the port, a bare-host line admits every port whose key matches; the user is the one the vault judged, handed to ssh beside the host; and a concurrent writer running as the vault's OS user can still reach the credential through the relay's configuration between the re-validation and git's read, as for every git operation.
- **The ssh bootstrap** (2026-11-24): the `ssh` action's `operation: "bootstrap"` brings a freshly installed host — one user, a password, no key the vault could log in with — under an agent's key for an agent that holds nothing but a `use` grant on the secret: the vault logs in once with the password the owner stored, appends a public key the administrator listed to the user's `~/.ssh/authorized_keys` and, where the administrator allowed it, installs a passwordless sudoers rule for that user; nobody types the password after it was stored, nothing the host wrote is returned, and the secret serves this one operation and is ended as soon as the password may have reached a host on which the agent may hold a login. Without the secret's bootstrap block every bootstrap is refused, and the `ssh` action without `operation` stays the command action it was. **The block** (README § "SSH Bootstrap" carries the commands): the injection policy's `ssh_bootstrap`, set with `secret allow --bootstrap-host`, `--bootstrap-port` (default 22), `--bootstrap-user`, `--bootstrap-host-key`, `--bootstrap-key`, `--bootstrap-sudoers` / `--no-bootstrap-sudoers` and cleared with `--clear-bootstrap`, every given part judged before the vault opens and merged with the stored block, the two key flags repeatable and each replacing its stored list, names one host — a name of letters, digits, `.`, `_` and `-`, one whose last label is a number only as an IPv4 address in plain dotted form —, its port and its user, the host's public keys, read at its console and never with `ssh-keyscan` over the network, which records whatever key answers there, the public keys a bootstrap may install, each list 1 to 16 lines of `<type> <base64>` and nothing else — host keys `ssh-ed25519`, `ecdsa-sha2-nistp256`, `ecdsa-sha2-nistp384`, `ecdsa-sha2-nistp521` or `ssh-rsa`, installable keys those, `sk-ssh-ed25519@openssh.com` and `sk-ecdsa-sha2-nistp256@openssh.com`, no certificate —, and the opt-in to the rule `#<uid> ALL=(ALL:ALL) NOPASSWD: ALL`. The block alone names the target: neither the host allowlist nor the connection config's known-hosts pin is read for a bootstrap. `ssh` must be on the secret's `command_allowlist`, and the value must be the user's password, one line of UTF-8 text without a NUL byte, 1 to 1023 bytes (`INVALID_SSH_CONFIG` otherwise, before anything is sent). Setting the block needs `admin`, as every policy field does; it is refused on a secret that is not an `api_key` and beside `proxy` or `ssh_agent_socket` (`INVALID_INPUT`: `ssh_bootstrap needs a secret of type api_key`, `ssh_bootstrap cannot stand beside proxy`, `ssh_bootstrap cannot stand beside ssh_agent_socket`, each with a failed `policy.grant` row); a policy write that holds it ends the secret's live stdio MCP child (`mcp.terminate`, reason `ssh_bootstrap_enabled`), and its `policy.grant` row records the block with every key as its SHA-256 fingerprint. The administrator reads the host's key and sees that the account's password has not expired at the host's console, then stores the password, sets the block and grants `use`, in that order: the block says nothing about a use before it was set. **The call**: the agent sends host, user, an optional port, `public_key` and an optional `sudoers` — no command and no `timeout_ms`; the budget is the vault's, 120 seconds for the call and 15 for the connection — and gets a status and no output, `{ type: "ssh_bootstrap", key: "installed" | "present", sudoers: "written" | "present" | "not_asked" }` (`present` where the key's line, or the rule, was there already), or a code. Before the decrypt, each with a failed `secret.use` row: no block, a host, user or port that is not the block's as the block spells it, a key the block does not list, compared by type and key bytes, or the sudoers flag without the opt-in (`SSH_BOOTSTRAP_NOT_ALLOWED`, 403); a bootstrap's mark on the secret (below); a vault host on Windows (`Unsupported ssh client: the ssh bootstrap is not served on a Windows vault host`); `ssh` not on the allowlist (`COMMAND_NOT_ALLOWED`); an `ssh` older than OpenSSH 8.4, or whose version cannot be read, the version read from one `ssh -V` child that carries no credential and runs outside the isolation (`SSH_CLIENT_UNSUPPORTED`). A malformed action is refused `INVALID_INPUT` before the handle is read, and a vault locked meanwhile answers `VAULT_LOCKED`, both without a row. The decrypt is of the secret those checks judged. **The connection**: one spawn of the allowlisted `ssh` under the secret's isolation settings — no shell, the remote command one argument —, with password login as its one method, strict host-key checking against a known-hosts file written from the block's keys beside an empty global one of the vault's own, and no configuration file, agent, identity, forwarding, terminal or escape character. The password is in the environment of the `ssh` child, and of an isolation wrapper in front of it — never in an argument or a file —, and ssh takes it for its login only from the answer of the vault's own askpass helper, which inherits that environment, which ssh starts with the null device as its input and which answers one argument, exactly the prompt `<user>@<host>'s password: `, writing a word drawn for the call to ssh's error stream before the password, so that the vault knows the password was handed over — the host never sees the word —; with the sudoers flag the password also travels on ssh's standard input, behind a framing line and the key line, to the script, which hands it to `sudo -S` through a builtin `printf`, on the host never in a process's arguments or environment. The remote command is the vault's own script for `/bin/sh`, one constant line pinned by its digest, with nothing the agent sent in it; the helper's two files are the vault's, written into a temporary directory before the spawn and removed when the call settles. The vault host needs OpenSSH 8.4 or later; the target needs password login, an account whose login shell takes a POSIX `sh` command line (tcsh and csh do not) and its system programs under `/usr/sbin`, `/usr/bin`, `/sbin` or `/bin`, and for the sudoers rule `sudo` or `sudo-rs` with `visudo` there, a user that `sudo` lets run `/bin/sh` as root with its password, a sudoers configuration that includes `/etc/sudoers.d` and parses, and a `/bin/sh` whose `printf` is a builtin (dash, bash, busybox ash, ksh93 and zsh; not mksh, posh or yash). **The mark and the end**: before the spawn the call commits a mark on the secret — a row of `vault_meta`, which a backup carries — with a `secret.use` row that says the bootstrap began, in a transaction that reads the secret's status again; the outcome's `secret.use` row — `done`, `refused`, `unconfirmed` or `not_spawned`, whether the secret ended, the spawn's fields — commits with the mark's removal. The bootstrap's own rows name the host, the port, the user, the key's SHA-256 fingerprint and the sudoers flag, never the password, a key line or a line the host wrote. The secret is ended — status `revoked` and a `secret.revoke` row with `reason: "ssh_bootstrap"` under the caller's principal, which needs no `revoke` grant for it, committed in the outcome's transaction, then its live stdio MCP child ended — where a session ran and the script's last line says that the key is installed or present, where the vault cut the capture at its cap, where a session ran and anything else came back (no status line of the fixed set, a session cut, the budget spent) and where the helper answered and anything but ssh's own refusal followed (no refusal line, a kill at the budget, a second word): `SSH_BOOTSTRAP_UNCONFIRMED` (502, `SSH bootstrap unconfirmed: a bootstrap of this secret has no confirmed outcome, so the secret was ended; a key and a sudoers drop-in may be installed on the host`) wherever no status says installed or present. It stays where nothing was spawned (an isolation the host cannot deliver, a temporary file that cannot be written, an `ssh` that cannot be started), where the script's last line says that no key was installed (`SSH_BOOTSTRAP_STEP_FAILED`, 502, which names what became of the drop-in and the key, as `SSH bootstrap failed: no key was installed (sudoers: refused, key: not_attempted)` where `sudo` refused the rule; a call without `sudoers` can follow), where the helper did not answer (`SSH_CONNECT_FAILED`, `SSH_HOST_KEY_MISMATCH`, `SSH_PASSWORD_NOT_OFFERED`, and `SSH_PASSWORD_REFUSED` where the server asked a prompt the helper does not answer) and where it answered once and ssh exited 255 without output, its last line its own refusal for the vault's user and host (`SSH_PASSWORD_REFUSED`, 502, `SSH bootstrap refused: the server refused the stored password; repeating the bootstrap can lock the vault host out of the server`). A second call is refused `SECRET_REVOKED`. An outcome the vault cannot record — the vault locked while the call ran, also locked and unlocked again; the process stopped or killed; a failed commit — leaves the mark, and the secret's next use that reaches the mark, from any process, ends it `SSH_BOOTSTRAP_UNCONFIRMED`; a use that reaches the mark while the same engine's own bootstrap of the secret runs is refused `SSH_BOOTSTRAP_IN_FLIGHT` (409). **Nothing else is served**: a secret whose policy holds the block refuses every other action on the use path before the decrypt — `SSH_BOOTSTRAP_NOT_ALLOWED`, `Use refused: the secret holds an ssh bootstrap block and serves the ssh bootstrap alone`, with a failed `secret.use` row, its live stdio MCP child ended —; the egress proxy refuses it with the same code and row, before the secret's proxy opt-in is judged, and the agent socket lists none of its keys and refuses every signature with one, each refusal a failed `secret.use` row. A secret with a mark is ended by the next use that reaches the mark: while the block stands, a bootstrap that passes the block's tests; where the block was removed since, a use of another action, a request through the egress proxy or a signature for a key the socket has derived since its unlock. An administrator with `read` still reads the value. What it does not close: the password goes to the host the block names, and the block is the administrator's statement that no agent controls that host yet — a host an agent already controls receives the password: with the sudoers flag a start-up file of the account can read it from the session's input, and whoever is root there can take it from the server. A server that opens a session without asking for the password and writes nothing to standard output leaves no word of the helper and no output, whatever its exit code and whatever it writes, within the capture's cap, to the error stream: the call answers a code that keeps the secret, although with the sudoers flag the password was on that session's input. After an end without a clear outcome the key and the drop-in may be installed, and a password stored again for that host, with the block, goes to a host on which the agent may hold a login and root — look at `~/.ssh/authorized_keys` and `/etc/sudoers.d` at the console, or change the password on the host, before a new secret gets the block; the same holds after a restore, which brings an ended secret back with its block and its grant (**Backups**, below). A client that is killed, or a network that drops, while the script runs does not stop the script: the key and the drop-in can appear after the client is gone (measured with a killed client), and the call ends the secret as unconfirmed. Under deployment model B the password is in no process of the agent's user; under model A the ssh child and the helper are the agent's own, and so are their environment and their budget. An `ssh` child that the vault's kill did not end keeps the password in its environment until it exits; the helper's files are removed, best effort, when the call settles. Whoever sits on the network between the vault host and the target can cut a session at a moment of its choosing. The mark is per secret: two secrets that carry a block for one host and user are not kept apart. A bootstrap of the secret through a second process — the CLI beside a daemon, two servers on one vault —, or any use there that reaches the mark, ends the secret while the first call runs, and where two daemons serve one vault a consumer can do that on purpose; a second process that had already decrypted when the first call ended is stopped at its claim, which reads the secret's status again, and a call sent in the same moment as another to one engine decrypts before it is refused. A secret with a mark is not rescued by rotating it: its next use that reaches the mark ends it. On the agent socket a secret with a block or a mark is left out of the listing without a row, and a signature for a marked secret's key that the daemon has not derived since its unlock is answered `SECRET_NOT_FOUND` and ends nothing. A block set from another process than a daemon's — the CLI beside it — does not reach that daemon's live stdio MCP child of the secret, which keeps the value in its environment until the daemon refuses the secret's next use by another action, ends the secret, locks or ends the idle child. Through `harpoc-mcp --url`, and through the SDK's REST client at its default deadline, a bootstrap that runs longer than the client's 30 seconds answers the agent with a client timeout; the vault finishes, the outcome is in the audit trail, and the agent's next call reads `SSH_BOOTSTRAP_IN_FLIGHT` while it runs and `SECRET_REVOKED` where it ended the secret. The password stays valid on the host until someone changes it there, and the vault keeps its encrypted value as it does for every revoked secret. An account whose password has expired ends the secret and gains no key: the server accepts the password and then closes the session (measured with PAM on Ubuntu 24.04 and 26.04); storing the password again does not help. A password that holds ` (` followed by the first letters of the server's method list, or the list's last letters followed by `).`, makes ssh's refusal line unreadable after the redaction; a refused password then ends the secret as unconfirmed. An OpenSSH server from 9.8 drops the vault host for a while after a few refused logins; a wrong stored password then reads as no connection. "Installed" says that the key's line is in `~/.ssh/authorized_keys`: a home directory or a `~/.ssh` that others can write, or an `AuthorizedKeysFile` that is not the default, makes the server refuse the key all the same (measured for a home others can write); the script sets `~/.ssh` to `0700` and the file to `0600`, leaves the home directory as it is and does not check that the server's `AuthorizedKeysFile` is the default. "Written" says that the drop-in `/etc/sudoers.d/harpoc-<uid>` passed `visudo` and so did the whole configuration; that check does not judge the owner and mode of `/etc/sudoers` itself, and the script does not check that sudo will honour a drop-in that already holds the rule, nor that the configuration includes the directory. The drop-in names the user by uid, so a renamed user keeps it and a later user with that uid inherits it; a user who is root gets the word `present` for the sudoers flag and no drop-in; removing the key or the drop-in is the administrator's. Not served: a vault host on Windows; an OpenSSH client before 8.4 (AlmaLinux 8); a host that offers only keyboard-interactive; a stored value that is empty, holds a line break or a NUL byte, is no UTF-8 text or is longer than 1023 bytes; a key of the type `ssh-mldsa44-ed25519`; a host named with a numeric last label that is no plain dotted address; a host whose system programs are not under `/usr/sbin`, `/usr/bin`, `/sbin` or `/bin`. An account whose login shell does not take a POSIX `sh` line ends the secret without a key — tcsh and csh refuse the remote command before `sh` starts (measured) —, and so does a start-up file of the account that reads its standard input; a start-up file that prints after the script's last line — a `trap` on exit — ends the secret although the key is installed. The sudoers rule is refused, the key step not reached and the secret kept on a host whose `/bin/sh` has no builtin `printf` (mksh, posh, yash: measured) and on one whose sudoers configuration does not parse. - **The SFTP render** (2026-11-25): the `sftp` action's `operation: "render"` writes a host's credentials — an env file with a bot token and API keys, which the owner stored once — for an agent that holds nothing but `use` grants: the agent names a render entry of a delivering key, and the vault fills the template the key's administrator set with the values of the secrets the template names, each of which approved that entry as it stands, and writes the file at the entry's path on the entry's host, as the entry's login account; the agent sends no host, path or template and gets a status and no output, and no value reaches the agent's context or an audit row. A key with an entry serves the render and nothing else, and a key without one serves no render. **The entry** (README § "SFTP Render" carries the commands): the injection policy's `render`, `{ entries, approvals }`, whose entries `secret render set <handle>` adds or replaces and `secret render remove` removes, every part judged before the vault opens — a name; a host of the bootstrap's form and no loopback form, `localhost`, a name under `.localhost`, `127.0.0.0/8` or `0.0.0.0` (`Invalid host: the vault host's own loopback (localhost, 127.0.0.0/8, 0.0.0.0) is no render target`); a port (default 22); a user; a path in normal form — absolute, at most 4096 bytes, without a control or format character, a line or paragraph separator, an empty, `.` or `..` segment or a trailing `/`, its last segment at most 200 bytes and not of the render's temporary name form; 1 to 8 of the host's public keys of the bootstrap's host-key types, read at its console and never with `ssh-keyscan` over the network; and a template of at most 16 384 bytes of UTF-8 text without a NUL, whose slots are `{{secret://name}}` or `{{secret://project/name}}` with nothing else between the braces, any other `{{` refusing it, `}}` alone text, nothing expanded and nothing normalized, at most 16 slots, a repeated handle counted each time and judged, decrypted, charged and recorded once —; at most 16 entries, one per name. `render set` prints the entry's digest and, without `--url`, the key's id (`key: <id>`, on standard error), and where it replaces an entry with another digest `the entry's digest changed; approvals of the old digest no longer hold`. The delivering key is an SSH private key authorized for the entry's login account, a key of its own beside the everyday one, since it serves nothing else. `ssh` — not `sftp` — must be on its `command_allowlist` and the entry's host under its `host_allowlist`; the entry alone names the host keys, and the connection config's known-hosts pin is not read. Setting the field needs `admin`, as every policy field does; entries are refused beside approvals, `proxy`, `ssh_agent_socket`, `network_isolation` or an `ssh_bootstrap` block, and so is an entry whose host the host allowlist does not admit (`INVALID_INPUT`: `render entries cannot stand beside render approvals`, `render entries cannot stand beside proxy`, `render entries cannot stand beside ssh_agent_socket`, `render entries cannot stand beside network_isolation`, `render entries cannot stand beside ssh_bootstrap`, `a render entry's host is not in host_allowlist`, each with a failed `policy.grant` row); no slot's secret is looked up when an entry is stored. A write that gives the key its first entry ends its live stdio MCP child (`mcp.terminate`, reason `render_enabled`), and every `policy.grant` row records the entries with each host key as its SHA-256 fingerprint, the template as its slots and the entry's digest, and the approvals themselves. A template is no place for a secret: it is stored in the key's policy, which whoever holds `read` on the key reads. **The approval**: each secret a template names approves the entry on its own policy, which needs `admin` on it — `secret render approve <slot handle> --key <key handle> --entry <name>` reads the key's policy (with a token, under `read` on the key) and only then resolves the key's id, so that a caller who holds none of `read`, `list` and `admin` on the key is answered `SECRET_NOT_FOUND`, as for a key that does not exist; it shows the entry, its digest and the template on standard error with every control character but the line feed, every format character (Unicode's class Cf: the bidirectional marks, the zero-width and the tag characters among them) and the line and paragraph separators written as an escape and a backslash doubled, asks (`--confirm` skips the question) and stores `{ key, entry, digest }`; with `--key` and `--digest <hex>` the key's policy is read all the same, the entry not shown and the digest approved as given, and `--key-id <id> --digest <hex>`, which reads nothing of the key, serves an administrator who holds nothing on it and is the one form under `--url`; no entry is looked up when an approval is stored. The approval names the key by its id, so a key created again under the name is another key, and its digest is the SHA-256, in hex, of a length-prefixed encoding of a version tag and the entry's host, port, user, path, sorted host-key lines and template, so a change of any of them voids it until the entry is approved again as it stands. `secret render revoke` removes an approval (`--key` without `--url`, after the same read of the key's policy; `--key-id` also under `--url`, with no read of the key); `secret render list` prints a secret's entries, each with its slots and digest, and its approvals, without `--url` with the secret's id as `key_id`, `--template <name>` one template byte for byte, and `--key <key handle>`, without `--url`, marks `stale` each approval of that key whose entry is gone or whose digest changed. **The call**: the agent sends `{ type: "sftp", operation: "render", entry, timeout_ms? }` on the key's handle — no `host`, `user`, `port`, `remote_path` or `local_path` (refused before the handle is read and without a row, as any malformed action is: by the action schema over REST, over MCP and from the CLI, and `INVALID_INPUT` — `an sftp render takes no host, user, port, remote_path or local_path` — through the SDK's direct client); the budget is `timeout_ms`, 30 seconds by default and at most 300, with 15 seconds for the connection — and gets a status and no output, `{ type: "sftp_render", status: "written" }`, or a code. Before any decrypt, each refusal one failed `secret.use` row on the secret that refused — the render's own on the key `{ context: "sftp", host, port, user, operation: "render", entry, remote_path, error }`, without the target where the key holds no entry of that name, and on a slot `{ handle, context: "sftp", operation: "render", entry, key, error }`, `key` the key's handle —: the handle's own ladder, which writes the use path's row; no entry of that name (`RENDER_ENTRY_NOT_FOUND`, 404, `SFTP render refused: the secret's injection policy holds no render entry of that name`); the entry's host outside the key's host allowlist (`HOST_NOT_ALLOWED`, `Host not in secret allowlist`, naming no host); `ssh` not on the allowlist (`COMMAND_NOT_ALLOWED`); an `ssh` older than OpenSSH 8.4 or whose version cannot be read, read from one `ssh -V` child that carries no credential and runs outside the isolation (`SSH_CLIENT_UNSUPPORTED`, 501, `Unsupported ssh client: OpenSSH <version> is older than 8.4, which an sftp render needs`, `Unsupported ssh client: its version could not be read; an sftp render needs OpenSSH 8.4 or later`); another render to the same host, port and path in the same vault engine, whatever the key or the entry (`RENDER_IN_FLIGHT`, 409, `SFTP render in flight: another render to the same host, port and path is running`); then each distinct slot, in the order of its first occurrence, judged whole before the next — the token's project and name scope on its handle, its resolution, the `use` grant, a certificate the vault manages, an `oauth_token` (`RENDER_SLOT_UNSUPPORTED`, 400), its status, a bootstrap block or mark, render entries of its own, the key itself or `network_isolation` (`RENDER_SLOT_UNSUPPORTED`), and last the approval of the entry as this call loaded it (`RENDER_NOT_APPROVED`, 403) —, each refusal one failed row on the slot with its real code, without a secret id where its handle named none or its token scope refused it, with the side effects a use of that secret has (a lazy expiry's row, its live stdio MCP child ended, a bootstrap's mark that no bootstrap of the same engine holds ending the secret), and one answer to the caller whatever the slot and the reason, `RENDER_SLOT_REFUSED` (403, `SFTP render refused: a slot of the entry's template cannot be served to this call`), so that the agent learns neither a slot's handle nor whether it exists — the administrator reads the reason in the row, and `RENDER_SLOT_UNSUPPORTED` and `RENDER_NOT_APPROVED` are recorded, never answered; after the judgement the slot limiter, an engine bucket per caller and slot secret that holds 120 and refills at 120 a minute, charged for each slot that passed its judgement whatever the call's outcome after that, the trusted local path not counted, refused `RATE_LIMIT_EXCEEDED` without a row. A vault locked meanwhile answers `VAULT_LOCKED` without a row. **The values**: only then does the vault decrypt the key and each slot's value, each bound to the secret it judged (a slot whose handle has come to name another secret is `RENDER_SLOT_REFUSED`, its row `SECRET_REVOKED`), and check each value — 1 to 65 536 bytes of UTF-8 text without a NUL and, beside other text in the template, only of `A`–`Z`, `a`–`z`, `0`–`9` and `. _ ~ + / = : @ % -`, a template that is one slot and nothing else taking any such value (`RENDER_VALUE_UNSUPPORTED`, 400, `SFTP render refused: a value does not fit the template: every value is UTF-8 text without a NUL, 1 to 65536 bytes, and beside other text only of A-Z, a-z, 0-9 and . _ ~ + / = : @ % -`). The content is built in one buffer in the vault's memory and written over the standard input of one `ssh -s` child through the vault's own SFTP client, never into a file by the vault, never in an argument or an environment variable: the allowlisted `ssh`, spawned without a shell, with strict host-key checking against a known-hosts file written from the entry's keys (`[host]:port` for a port other than 22) beside an empty global one of the vault's own, no configuration file, the key through the ephemeral agent with only its public line in a file, no password, terminal, escape character, forwarding or local command, under the key's policy with `fs_isolation` and `strict_tree_exit` on where the key's or any slot's policy sets them. Over that pipe the vault asks for SFTP version 3; removes the path's stale temporary files, `.<last segment>.harpoc-<32 hex digits>.tmp` (a listing past 64 replies or 1 MiB is given up); opens a fresh such name exclusively with mode `0600`, sets `0600` and reads it back as an empty regular file of exactly that mode; writes in 32 768-byte requests, each answered before the next; syncs where the server announces `fsync@openssh.com`; closes; and renames over the path with `posix-rename@openssh.com`, so that each call publishes its own file alone — the rename is the server's: against OpenSSH's `sftp-server` the e2e suite's rows find a link at the path replaced, not followed, and a directory there failing the rename. A step the server refuses after the open, or a file that does not read back empty and `0600`, closes and removes the temporary file, best effort within the budget, while a reply out of step, the budget, a lock and the connection's end leave it; a reply over 262 144 bytes, an unknown reply, a wrong request id or a byte before the version's answer ends the render; the vault never asks for a file's content. Any failure of the write answers `RENDER_FAILED` (502, `SFTP render failed: the file is not confirmed written; the key's audit row holds the reason`), one fixed text whatever the remote host did, since the reason is the host's to choose; an isolation the host cannot deliver, a temporary file that cannot be written (`FILE_IO_ERROR`) or a key the vault's agent cannot load spawns nothing and answers its own code. ssh's error stream is captured, capped and redacted with the key and every value of three characters or more, read for ssh's host-key failure alone and never returned; each decrypted value's array and the content are zeroed when the call settles. **The rows**: from the first decrypt on, a call leaves exactly one `secret.use` row on the key and one on each distinct slot's secret, committed in one transaction whatever the outcome, a lock included — the key's `{ context: "sftp", host, port, user, operation: "render", entry, remote_path, slots, written, network_isolation, fs_isolation }` with the spawn's fields, each where the child's run set it, and on a failure `error` and, for `RENDER_FAILED`, `reason` (`connect`, `host_key`, `no_rename`, `protocol`, `open`, `mode`, `write`, `rename` or `timeout`), `written` being `yes`, `no` (no rename sent, or one the server refused) or `unconfirmed` (a rename sent and not answered); each slot's `{ context: "sftp", operation: "render", entry, key, host, port, user, remote_path, network_isolation, fs_isolation }` with the call's `success`, and `error` where that slot is what failed and, `VAULT_LOCKED`, after a lock. A lock's rows are written before the child settles, so the key's row then carries no spawn field. No row holds a value, a length or a digest of one, or the content. **Nothing else is served**: a secret whose policy holds an entry refuses every other action on the use path before the decrypt — the `ssh` context and its bootstrap, `sftp` `upload`, `download` and `list`, `git`, `process` and the rest — `RENDER_ONLY_KEY` (403, `Use refused: the secret holds a render entry and serves the sftp render alone`) with a failed `secret.use` row, its live stdio MCP child ended, ahead of the bootstrap block's refusal, so that no use of the key through the vault reads back what it rendered; the egress proxy refuses it with the same code and a failed `secret.use` row, before the secret's proxy opt-in is judged; the agent socket lists none of its keys, without a row, and refuses every signature with one, each refusal a failed `secret.use` row; and a render refuses it as a slot. An administrator with `read` still reads the value. Removing the last entry makes it an ordinary key again and voids nothing on the host — what it rendered stays readable to its login account —, and the `policy.grant` row shows the change. **The hosts**: the vault host needs OpenSSH 8.4 or later; a Windows vault host is served with the native Win32-OpenSSH client — the gate's live rows run a whole render through it under the vault's job wrapper and compare the file byte for byte wherever a leg has that client and an address of its own that is no loopback (so measured on the development host, OpenSSH for Windows 9.5p2 on Windows 11) —, an MSYS or Cygwin build refused as in the `ssh` context and a key or a slot that sets `fs_isolation` refused there, as every such use is on Windows. The target needs an SFTP subsystem that answers version 3 and announces `posix-rename@openssh.com` — the e2e suite's rows write through OpenSSH's `sftp-server` — (without it nothing is written, `reason: "no_rename"`); the key authorized for the entry's login account, whose login shell and start-up files print nothing before the subsystem starts (a byte ahead of the server's first answer ends the render, `reason: "protocol"`); and the file's directory, existing and writable by that account. The vault sets the file's mode, `0600`, and sends no owner: the file is the login account's, as the server creates it for that session (the e2e suite's closing row reads both by `stat`). What it does not close: an approval entrusts the value to the entry's host and its login account, and to whoever holds `admin`, `read` or `rotate` on the delivering key: whoever holds `admin` or `read` there can read the private key and log in as the file's owner, and whoever holds `rotate` can replace the key the render logs in with — an approval names the key secret's id and the entry, not the key's value, so it stays in force. Whoever has a shell as the file's owner reads the file: the vault refuses to be that shell for the delivering key, and an agent that reaches the account another way reads what it may render. Under deployment model B no value is in a process of the agent's user, while under model A the values are in processes of the agent's own user — the vault's own process, which decrypts them, and its `ssh` child, with the content on its input. A run cut by its budget, by a lock or by the connection's end, a reply out of step, a removal the server refuses and a vault that dies can leave the temporary file — mode `0600`, the login account's —, which the next render of that path removes where the directory lists within 64 replies and 1 MiB. Two vaults that render to one path at once can remove each other's temporary file: that render fails, and neither publishes the other's bytes. A value beside other text in a template is held to the class above, so a password with other characters is delivered as a file of its own — a template that is that one slot — or not at all. The slot limiter's bucket is the engine's own, beside each interface's bucket for the secret's direct use, so a caller's renders of a slot and its direct uses of that secret are counted apart. A vault process that dies between the write and the rows leaves the file and no row, and a failure after the rename was sent is recorded `unconfirmed`: the file may be in place. The vault sets the file's mode `0600` and no owner, so the file is the login account's alone: a service that runs as another account cannot read it. A host named by a name of the vault host's own that is no loopback form is not recognized as the vault host: the values would land on the vault host's disk, by the administrator's entry. The remote host learns the values: it is where they are sent. The key's text and a text copy of every value — the redaction list's among them — are strings, which the vault cannot zero, as in every ssh context. A remote host can make the key's row read `reason: "host_key"` by writing ssh's own host-key text to the error stream and closing before the temporary file is opened, so that reason can be the host's choice; the caller's answer is the same `RENDER_FAILED`. Through `harpoc-mcp --url`, and through the SDK's REST client at its default deadline, a render that runs longer than the client's 30 seconds — a render may run 300 — answers the agent with a client timeout while the vault finishes; the outcome is in the audit trail, and a call for the same host, port and path reads `RENDER_IN_FLIGHT` while it runs. `secret allow --clear` resets the whole policy and so drops a key's render entries, or a slot's approvals, with the rest of it. Two spellings of one host — a name and its address — are two holds: two renders of one path under two names of the host run at once, and each renames its own file alone. A failed commit of the rows after the write leaves the file and no row, and the caller is answered `INTERNAL_ERROR` (`the audit write failed unexpectedly`). A restore brings back every render entry and approval as the copy holds them, an approval revoked after the copy among them (**Backups**, below). Two values whose ends overlap inside one text leave a fragment of one after the redaction, which meets only ssh's error stream, never returned, and an error the render does not expect; a render's own error texts hold no byte that the remote host wrote. Not measured: a remote host on Windows.
- **Injector errors are redacted too**: a thrown error is a model-visible channel — the MCP SDK turns it into the tool result text and the REST error handler returns the message — so error text carrying attacker-influenced strings (a refused redirect target chosen by the endpoint that just received the credential, a driver message quoting a connection string) passes through credential redaction on the way out, and refusals name only a target's origin rather than its full URL. Redaction covers JSON object **keys** as well as values, since the party naming keys in a proxied MCP result or a SQL column alias is not the vault. An SFTP render's redaction list is the delivering key and every slot value of three characters or more, the longest applied first, and it meets ssh's error stream, which is never returned, and an error the render does not expect — a `VaultError` thrown where it awaits none — alone; the render's own refusals, and the error of a render that spawned nothing, hold no byte of the remote host's, none of the `ssh` child's output and no slot's value, and leave as they stand, as the ssh bootstrap's do: a redaction marker in a text the vault wrote would show where a value happens to be a word of it. Most are fixed texts; the others name what the vault host found — an MSYS or Cygwin client's the directory of the vault host's `ssh`, the version floor's the version `ssh -V` reported, an isolation or a strict tree exit the host cannot deliver its reason, a key the agent cannot load its fault, which for a key type or curve the vault does not serve names it as the key's file states it — and the key's own refusal at its decrypt names the caller's handle (2026-11-25)
- **Network isolation** (opt-in, per secret): with `network_isolation` on the injection policy, every child process spawned with the secret (process, Git, SSH and SFTP contexts, and stdio MCP downstream servers) runs without network access — loopback included, since the vault's own REST/MCP listeners live there. Linux delivers it via `unshare -rn` (unprivileged user + network namespaces) or, when `unshare` is absent or refused, via bubblewrap (`bwrap --dev-bind / / --unshare-net --die-with-parent`, a fresh namespace with an empty loopback of its own, the root bound with device access — a plain `--bind` mounts `nodev`, and the ssh-family clients open `/dev/null` at startup; bwrap stays as a monitor and takes the payload down with it) — note that stock Ubuntu 24.04+ restricts unprivileged user namespaces via AppArmor, which both tiers' probes detect, so uses are refused until the restriction is relaxed or a profile grants `userns` to the wrapper — and macOS via `sandbox-exec` with a constant deny-network profile; every tier is probed live at first use, and only a successful probe is cached — a transient probe failure re-probes on the next use instead of permanently disabling isolation. Windows is unsupported by design (real per-process isolation requires an AppContainer native addon). **Fail closed**: a platform that cannot deliver demanded isolation refuses the use with `NETWORK_ISOLATION_UNAVAILABLE` before any process is spawned (the git context first reads the allowlisted git's version with one `git version` child, which carries no credential and runs outside the isolation; the ssh bootstrap likewise reads the allowlisted ssh's with one `ssh -V` child before the decrypt, 2026-11-24), and the denial is audited — there is no silent degrade and no environment-variable opt-out. The wrapper is vault-authored, resolved from pinned absolute paths, and applied after command-allowlist resolution; agent input never reaches it. Setting the flag terminates any live stdio MCP downstream child already holding the secret (audited `mcp.terminate`) and the next use respawns it wrapped in the same isolation wrapper; a policy tightened from a separate process takes effect at that server's next invocation attempt — the live connection records the posture it was spawned with, and a demanded dimension it lacks terminates it before the respawn. Every process/git/ssh/sftp use — including security denials such as host-key mismatches — is audited with its isolation state and, on a row whose spawn returned a result, its mechanism (sftp's rows since 2026-10-14) — including, since 2026-09-05, the `mcp.spawn` row of a stdio downstream (`isolation_mechanism`); an SFTP render's refusals before its decrypts carry neither (2026-11-25).
- **Filesystem isolation** (opt-in, per secret): with `fs_isolation` on the injection policy, every child process spawned with the secret (process, Git, SSH and SFTP contexts, and stdio MCP downstream servers) is denied filesystem writes — the ssh bootstrap's password helper among them, whose two files are the vault's, written before the spawn and only read and executed by the child (2026-11-24). Linux delivers it via `setpriv` chained with a Landlock ruleset (util-linux ≥ 2.40) or, behind it, via bubblewrap's read-only root bind (`bwrap --ro-bind / / --dev /dev --die-with-parent`, the tier that carries the flag on Ubuntu 24.04 LTS), macOS via a `sandbox-exec` deny-write profile whose last rule allows the literal `/dev/null`; writes to `/dev/null` are exempt on every mechanism (the earlier macOS asymmetry closed 2026-09-05). Windows is unsupported by design. **Fail closed**: a platform that cannot deliver demanded isolation refuses the use with `FS_ISOLATION_UNAVAILABLE` before any process is spawned (the git context first reads the allowlisted git's version with one `git version` child, which carries no credential and runs outside the isolation; the ssh bootstrap likewise reads the allowlisted ssh's with one `ssh -V` child before the decrypt, 2026-11-24, and so does an SFTP render, 2026-11-25), and the denial is audited — no silent degrade, no environment-variable opt-out; only `secret allow --no-fs-isolation` (or the REST PUT) lifts it. Setting the flag terminates any live stdio MCP downstream child already holding the secret (audited `mcp.terminate`, reason `fs_isolation_enabled`); if a policy update enables both `network_isolation` and `fs_isolation` together, the network-isolation reason takes precedence and exactly one terminate is emitted — and a policy that also holds an ssh bootstrap block takes the reason `ssh_bootstrap_enabled`, still one terminate (2026-11-24), and one that gives the secret its first SFTP render entry, without a block, `render_enabled` (2026-11-25). The next stdio MCP use of the secret respawns the child wrapped (the `mcp.spawn` row carries `fs_isolation_mechanism`); only a host that cannot deliver the isolation refuses it with `FS_ISOLATION_UNAVAILABLE`. Combined with network isolation, Linux chains both primaries into one spawn (`unshare -rn -- setpriv ... --`) or, when either fell to the second tier, takes one `bwrap` wrapper for both, and macOS uses a single combined `sandbox-exec` profile denying both network and writes. Every process/git/ssh/sftp use is audited with `fs_isolation` (posture) and, when a wrapper actually ran, `fs_isolation_mechanism` (`landlock` / `sandbox-exec` / `bwrap`) — on an SFTP render the key's row, save the one a lock writes before the child settles; each slot's row carries `network_isolation` and `fs_isolation` alone, and a render's refusal before its decrypts neither (2026-11-25)
- **Strict tree exit** (opt-in, per secret): with `strict_tree_exit` on the injection policy, nothing a process-mediated child started outlives the call. Windows delivers it through the vault's own job wrapper (`harpoc-job.exe --strict`, a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` job the wrapper holds and no member can break away from): the child's normal exit closes the job on every survivor, and a host whose wrapper is unavailable refuses the use fail-closed with `STRICT_TREE_EXIT_UNAVAILABLE` rather than falling back to the `taskkill` tier; POSIX sends `SIGKILL` to the child's own process group after its exit — a descendant that called `setsid` is outside it, the same limit the timeout path has. Without the flag a normal exit leaves survivors exactly as before, on every platform.
- **HTTP response mode**: A per-secret `response_mode` bounds what an HTTP invocation returns. `status_only` returns only the status code (plus an admin-allowlisted header set) and never reads the response body — the response-echo channel is removed structurally, not filtered. The default `filtered` redacts the credential and its base64/base64url/hex/percent encodings, each of them also when JSON-escaped on the wire — any valid escaping, not just the convention V8 emits, since a response body is normally JSON and PHP, Python and Go each escape differently; per-invocation overrides may only tighten the policy mode, never loosen it
- **Session-file protection**: The session file's key is wrapped at rest with an OS-user-bound platform key store — DPAPI (Windows), the Keychain (macOS), Secret Service or the kernel `@u` keyring (Linux desktop/headless tiers) — so a session file copied off the host is inert. Reads fail closed: a tampered blob, a foreign user, or a scheme mismatch invalidates the session and requires a fresh `harpoc unlock`; kernel-keyring keys die at reboot, which likewise forces a fresh unlock rather than degrading. A write-time keystore failure fails the unlock with `SESSION_KEYSTORE_UNAVAILABLE` — nothing is written, and `HARPOC_SESSION_KEYSTORE=off` is the explicit opt-out named in the message; a `none`-tagged file is refused wherever a keystore protector is configured (since 2026-09-04, R8) — and the file is created owner-only (0600) in all cases — as are the vault directory (0700) and the database itself (0600) on POSIX, so the encrypted store is not left readable to every local account by the umask; on Windows the session file's ACL is reduced to the current user through `icacls` invoked with arguments, never a shell string, and a failure to do so is reported rather than swallowed. The key-store bridges are OS-shipped or distro-standard binaries invoked from pinned paths with key material on stdin/stdout only — no native addon, nothing on an argument vector. A `session.json.lock` directory serialises the slide, the fresh write and the erase across processes, so a `harpoc lock` can no longer be resurrected by a concurrent expiry slide.
- **Listener host allowlist and the reverse-proxy stance** (2026-09-04, D61): both HTTP listeners validate `Host` and `Origin` against the operator's `--allowed-host` set (loopback names always allowed on a loopback bind) ahead of authentication, and a non-loopback bind is refused without the flag; there is no native TLS — terminate it at a reverse proxy that preserves `Host`, and note that forwarded headers are never trusted (the audit trail records the proxy).
- **Governance is vault-wide** (2026-09-04, N12): a token carrying a `project` claim is refused on every governance route, command and engine method — per-secret scoping and vault-wide administration do not mix.
- **Dependencies are audited and kept current** (2026-09-30): `pnpm audit` lists no advisory at the current tree — the 95 advisories over sixteen modules it listed on 2026-09-30 were closed the same day (the deferred items closure's phase 3, `docs/implementation-plan-deferred-items-phase3-2026-09-30.md`); the four runtime dependencies (`hono`, `@hono/node-server`, `undici`, `mysql2`) carry declared floors at their patched versions in every manifest that declares them, and `.github/dependabot.yml` proposes weekly updates (minor and patch releases grouped, majors separately, the workflow actions beside) — every dependency change goes through the full gates and both workflows before it lands. The audit is re-run at every release commit; Dependabot alerts are a repository setting the posture does not rely on.
- **One dependency is patched** (2026-11-17): the `mongodb` driver takes the SCRAM iteration count from the server with no upper bound and derives the key on a worker thread that cannot be cancelled; the workspace patches it (`patches/mongodb@7.9.0.patch`) to refuse a count above 100 000 before the derivation, the ceiling `pg` ships by default. Without the patch a MongoDB server on a secret's host allowlist — or a party on the path under the TLS opt-out — could stall the vault process's DNS lookups, asynchronous file operations and key derivations with four uses (6.9 s measured at a count of 60 000 000) and hold a stop (10.2 s at 90 000 000) — measured on one Windows host with the adapter called directly; at 2 147 483 647, the largest count Node accepts, about 4.8 minutes by the measured rate, computed and not run (`docs/e2e/evidence/2026-11-17-scram-iterations-c7fbce2.txt`). The patch reaches a build made from this repository's lockfile with pnpm; nothing at run time checks that it is applied, the test suite does. A `mongodb` version move fails the install until the patch is re-made.

For a summary of the security model, see the [Security Model](README.md#security-model) section of the README.

## Deployment model B

The design overview above holds in both deployment models; they differ in which OS identities the vault and its agents run under (the recipe and the commands: [Deployment models](README.md#deployment-models)).

- **What model B is** (2026-11-05): the vault process runs as a dedicated system user `harpoc` — the vault directory `/var/lib/harpoc` `0700`, the runtime directory `/run/harpoc` `0750 harpoc:harpoc-clients` with one `02750` consumer directory per agent user — and every agent runs under an OS user of its own, a member of `harpoc-clients`, that reaches the vault only over REST or MCP over HTTP with a token. `deploy/linux/install-two-identity.sh` creates the layout; the `ci.yml` ubuntu legs run it and pin the claims below with a two-user integration suite (`two-identity.test.ts`).
- **What it closes**: the agent is no longer code under the vault's OS user. An agent user cannot read the vault directory, the database or the session file (the same-UID read of the session file — and the key-encryption key it unwraps — is what model A cannot prevent); `secret get --value` is reachable only through `GET /api/v1/secrets/:handle/value`, whose `read` scope a use-only token lacks (refused `403` at the scope check, with an `access.denied` row); and `/proc/<pid>/environ` of a child the vault spawns runs under `harpoc` and is unreadable across UIDs (a `PTRACE_MODE_READ_FSCREDS` check that a different, unprivileged UID fails). The same reads succeed for the vault's own UID — model A's exposure, now confined to `harpoc`.
- **What it does not close**: the confused deputy — an agent uses every secret its grant allows, inside the allowlists, as far as the credential's own permissions reach; root and any code under the `harpoc` UID, which read the unlocked key-encryption key as before; physical access — which the sealed unlock key relies on, since whoever boots the machine unseals it; and the agent's own processes — their `/proc`, their environment and their loopback traffic are the agent's to read, other agent users see none of them, root sees all. The REST and MCP listeners are loopback TCP, reachable by every local user: the bearer token is the authentication on every request, and the consumer directory's mode is a second factor on the egress proxy's `proxy.sock` and the only factor on the agent socket's `ssh-agent.sock`, which takes no token; the proxy's TCP listener is token-only. Model B is single-host.
- **The interpreter corollary**: the `process` context runs its child as `harpoc`, so a secret whose command allowlist holds an acknowledged interpreter or exec wrapper (`secret allow --acknowledge-interpreter`; `ssh-agent`, `podman`, `nerdctl` and `snap` among the exec wrappers since 2026-11-19 — an entry stored before its name joined that tier is not gated again and keeps running, and on a host where a command is a snap a new entry naming it needs the acknowledgement, since it resolves to `snap`) runs agent-authored programs under the vault's UID — **model B collapses to model A for that secret**. For agent-owned work a consumer must not use the `process` context at all; it stays for vault-owned work. An SFTP render names no local path and reads or writes no local file a caller names: its content is built in the vault's memory and handed to its `ssh` child, which runs as `harpoc` too, so under model B no value is in a process of the agent's user (2026-11-25). The local directories a secret lists carry the same kind of reach: the `sftp` child runs as `harpoc` too, the vault reads a mail attachment as `harpoc` (2026-11-19), and a directory a secret lists (`secret allow --local-dir`) hands a consumer granted `use` every file in it and in its subdirectories outside a git directory (2026-11-23), to read through an upload or an attachment and to overwrite through a download, with the vault user's access; a mail secret without a listed directory sends no attachment; since 2026-11-21 a path with a `..` segment is refused by its spelling, before any file-system call (`INVALID_INPUT`, `sftp local path must not hold a .. segment`; an attachment the list's message), and so is, since 2026-11-23, a path with a name a file system may read as `.git` (`.git` in any letter case, also with trailing dots or spaces, before a colon or with a code point HFS+ ignores inside it, and `git~` with digits; `INVALID_INPUT`, `sftp local path must not hold a .git segment`; an attachment the list's message; on Windows a `.git` name with a trailing dot or a colon meets the refusal of a name Windows reads differently first), and a download path that ends in a separator (`INVALID_INPUT`, `sftp download path must name a file`). A path the vault judges must resolve outside every git directory (2026-11-23): one whose resolved spelling holds a `.git` name, or that lies inside a directory with a git directory's shape — an entry `HEAD` beside `objects` and `refs`, or beside `commondir`, from the file's own directory up to the root — is refused as one outside the list, so the answer does not tell whether a link leads into one, and a listed directory spelled with a `.git` name admits nothing: neither context reads or writes a repository's `.git` entry or a file of its git directory, a file of a work tree beside its `.git` is served, and every path under a home directory that is itself a bare repository, or in a work tree whose top also holds `HEAD`, `objects` and `refs`, is refused. Whatever is listed, a path inside the floor is refused: the directories of the vault's database and session file (2026-11-18) and, in the daemon, every path `server start` declares — the runtime directory, the credentials directory under `--unlock-credential` and the backup directory, each with everything in it, and the files of `--unlock-key-file`, `--unlock-key-dpapi`, `--token-file` and each `--issue-token`, a declared path that does not exist yet covered through its nearest existing directory (2026-11-19). In the daemon — `server start`, one that serves only `--mcp` on its standard input included, and `harpoc-mcp --http` — every directory of the resolved path, from the root to the file's own directory, must also be held by the vault (2026-11-19): owned by `harpoc` or root and writable by nobody else, a root-owned sticky directory passing above the file's own directory when the entry below it is `harpoc`'s or root's, never as that directory; on Windows owned by the vault's account, SYSTEM, Administrators or TrustedInstaller, with no allow entry that lets another account replace an entry in it, nor on the file's own directory one that lets it add a file or write its attributes. A path that fails is refused as one outside the list (`LOCAL_PATH_NOT_ALLOWED`; an attachment `ATTACHMENT_REJECTED`). So no other account can replace the judged file, or a directory on its path, before the transfer opens it — `sftp` does so only after it has connected and authenticated — or plant a hard link in a listed directory; the cost is that in the daemon the `sftp` context and attachments serve files in directories of `harpoc`'s own — on Ubuntu and Debian a user's own directory is group-writable by default and is refused until its mode is changed, and on Windows a directory in which `Users` may add files, such as `C:\ProgramData` itself, is refused as a file's own directory. A local command and `harpoc-mcp` on its standard input skip that walk and keep the list and the floor: their caller is the vault user. - **The egress credential proxy** (the base-URL form; CONNECT mode next): `server start --proxy` gives an agent's own HTTPS clients a credential they never hold. The client carries a placeholder (`harpoc:<name>`) and its use-scoped token; the proxy swaps the real value in at the egress hop after the caller's `use` grant, the secret's proxy opt-in and its URL allowlist, refuses a placeholder bound for an origin outside the allowlist before contacting it, and audits one `secret.use` row per brokered request — the method, the origin and the path, never a body, a query or a header value; a request with two or more placeholders and a request without one whose target the SSRF floor refuses leave one `access.denied` row each, and a consumer's refusals are budgeted (**Scope refusals are audited**, above). It widens the trust boundary as every egress credential proxy does: the proxy is the vault and sees each brokered request and response in the clear. `response_mode` cannot shape a proxied stream, so the proxy's redaction of brokered responses — the swapped value and its basic-auth base64 form, matched as literal bytes across chunk boundaries, with an uncompressed response requested upstream — is best-effort exact-value redaction, defence in depth and never a guarantee: a compressed or otherwise encoded copy of the value passes it. What the proxy path claims is the vault's: the agent's process never holds the credential. The TCP listener is token-only; the `proxy.sock` in a consumer directory adds the directory's mode as a second factor; clients that honour only `HTTPS_PROXY` take CONNECT mode (next).
- **A plain upstream on loopback** (2026-11-21): a secret with `proxy: true` and an `http://` entry that spells `127.0.0.1` in full or `[::1]` (in any bracketed spelling of that address; port 80 written without a port) is served by the egress proxy over plain HTTP at that entry's port and path — a request outside a CONNECT tunnel whose request line did not name `https://`, while no `https://` entry of the secret names the host and port of the `https://` URL the request stands for and no CA is pinned (`http.ca_pem`); every other request, one without a placeholder included, goes out over TLS as before, and the row names the `http://` origin with `plain_http: true`. A request outside a tunnel takes `Proxy-Authorization: Basic base64(<user>:<token>)` as well as Bearer, the user ignored, and a `407` offers Basic first. What it does not close: nothing authenticates a plain upstream — whoever holds its loopback port receives the credential. A consumer with a shell can bind a free port — on Windows also the loopback address of a port that a service holds on every address — and a service the consumer runs itself receives the credential by construction. The same holds, and held before, for `use_secret`'s `http` action against an `http://` loopback entry, where `localhost` counts too.
- **CONNECT mode and the Harpoc CA** (`harpoc proxy ca init`, 2026-11-09): for a client that honours only `HTTPS_PROXY` the proxy answers `CONNECT`, ends the client's TLS with a leaf for the tunnel's host issued by a Harpoc CA, and handles the requests inside as above. This is the trust-boundary expansion at its widest: the vault reads in the clear everything a consumer sends through a tunnel, brokered or not — the proxy is the vault, and its client's TLS ends there rather than at the host. The containment is the CA's scope: a root, whose key is discarded at creation and which the consumers trust alone, signs one intermediate name-constrained to the hosts the operator lists (RFC 5280 `permittedSubtrees`, the absent name form excluded), so a leaked intermediate impersonates those hosts and their subdomains alone — to the client stacks that honour name constraints, which every stack measured does (Java 8 only on an intermediate, hence the two tiers; the README's table) — and the proxy refuses a CONNECT to any other host before any TLS, with one `access.denied` row for the first refusal of a host in a window (**Scope refusals are audited**, above). The intermediate's key is kept by the vault — the certificate secret `secret://harpoc-ca`, KEK-encrypted at rest and in the daemon's memory while it runs — and is never written to a file, logged, returned or brokered; each leaf's key lives in the daemon alone, for 7 days at most. The documented fallback, an unconstrained CA for a client that rejects a constrained one (none measured does), lets its leaked key impersonate every host to the clients that trust it for as long as it is valid — at most 30 days, created only by an explicit `--unconstrained`, with no revocation endpoint; the proxy still tunnels the listed hosts alone, so the key is its whole residual. What it does not close: root and code under the `harpoc` UID read the intermediate's key as they read the key-encryption key; the daemon holds that signing key from its start until it exits — a lock seals the vault and drains the leases but leaves the proxy's copy (CONNECT then fails at authentication), and only stopping the daemon drops it; a client that ignores name constraints trusts a leaked intermediate for every host; and caller authentication is the token alone — CONNECT, like every TCP path, is token-only, the token crossing the loopback in the CONNECT request's `Proxy-Authorization` and living in the client's environment when it sits in `HTTPS_PROXY`.
- **The agent socket** (`server start --ssh-agent`): an agent's own `ssh` and `git` over SSH authenticate with a key the agent never holds. The vault serves each consumer one `ssh-agent.sock` in its consumer directory, offering the keys of the secrets the consumer holds a `use` or `admin` grant on and that are opted in with `secret allow --ssh-agent-socket` and carry neither an ssh bootstrap block nor a bootstrap's mark (2026-11-24; **The ssh bootstrap**, above) nor an SFTP render entry (2026-11-25; **The SFTP render**, above), and releases signatures only — the private key never leaves the vault process. It signs only on a connection the client bound with `session-bind@openssh.com` (the server's host-key signature over the session identifier, verified on `node:crypto`), only that session's authentication request, and only for a host whose key the secret pins (`secret connection --known-host`) and whose name its host allowlist admits; each signature and each refusal is a `secret.use` row — the signature's naming the host and the key type, a refusal naming what was resolved when it was refused: the key's fingerprint for an unknown key or an unregistered or inactive consumer, the key type once the key is known, the host once a pin names one (a request past a rate budget, the consumer's or the key's, or on a sealed vault is refused without one) — never key material, a signature or a session identifier; a signature with the key of a secret that has gained an SFTP render entry since the daemon derived it is refused `RENDER_ONLY_KEY`, ahead of the opt-in (2026-11-25). A key's budget is shared: each key is used at most 120 times a minute across all its callers, so one caller allowed to use a key that others share can exhaust it for that minute. An SFTP render's slots have an engine bucket of their own, per caller and slot secret, which holds 120 and refills at 120 a minute and is charged for each slot of a call that passed its judgement, counted apart from each interface's bucket for that secret's direct use (2026-11-25; **The SFTP render**, above). What it does not close: the resource — a key valid for several repositories on one host signs for each, and choosing the key per repository is the consumer's `Host` alias; agent forwarding, which is refused rather than bound to the remote hop, a refused bind leaving the connection unable to bind or list, so `ssh -A` through the socket signs nothing there (a bastion is reached with `ssh -J` instead, each hop a direct session the socket signs for when the secret pins and allowlists it); and its reach — every process in the consumer's group can have it sign while it runs, the directory's mode being its only factor (the ssh-agent protocol, RFC 9987, carries no token).
- **The unlock key** (`server start --unlock-credential` / `--unlock-key-file`): the daemon comes back after a reboot with no person and no password on disk. A second slot wraps the key-encryption key with AES-256-GCM under a random 256-bit unlock key — no key derivation, so the database alone gives a reader no more than before — and the key is sealed by a mechanism the vault never learns about; the reference sealer is systemd's credential store (`deploy/linux/enroll-unlock-key.sh` — `systemd-creds encrypt`, the TPM2 and the host key by default — and `LoadCredentialEncrypted=` in `deploy/systemd/harpoc.service`), which hands the key to the unit's user alone. Enrolment and revocation need the password; each unlock from the key writes the `vault.unlock` row with `method: "credential"`; a wrong key counts against the lockout the password shares; the key reaches no message, row or output. What it does not close: physical access — whoever has the machine boots it and the credential unseals; a modified boot of the same machine, since the recipe sets no PCR policy; `host` mode, as safe as the root-readable host key; `--unlock-key-file` without a sealer, a password file by another name.
- **The memory session and token rotation** (`server start --session memory`, `--issue-token`): a daemon in the memory session holds the keys of its unlock in its own memory alone — started from the unlock key it writes no session file, started after an administrator's unlock it reads that file once and leaves it — so no session clock seals it and no administrator's unlock or lock reaches it: the bounded lifetime of an unlocked vault becomes bounded by the daemon's uptime and an explicit lock (`POST /api/v1/vault/lock` with an admin-scoped token, or `SIGTERM`). Every model B flag requires it, refused `SESSION_MODE_CONFLICT` before the vault opens otherwise. With `--issue-token` the daemon issues each consumer's token into the consumer directory — `0640`, the consumer's group through the set-group-ID directory, written under a temporary name and renamed — at the start and again at half its lifetime (at most 24 hours); every mint writes the `token.create` row with `rotation: true`, naming the `jti` and the principal and never the token, and a revoked token, or a deactivated or deleted agent, is not re-minted (a failed `token.create` row records the refusal). What it does not close: root and code under the `harpoc` UID read the keys in the daemon's memory for as long as it runs, as they read the unlocked key-encryption key before; a token file read by anyone but its consumer stays valid until that token's expiry, rotated or not — rotation bounds a token's lifetime, revocation still ends it; and a revoked consumer gets a fresh token at the daemon's next start unless its agent is deactivated or its spec removed.
- **Backups** (`server start --backup-dir`, `harpoc backup <file>`, 2026-11-19): the daemon copies the vault on a schedule into a directory that must be the daemon's user's own and closed to everyone else (`0700`; on Windows owned by the vault's account, SYSTEM or Administrators with no allow entry for anyone else, inherited and inherit-only entries included) and whose every directory above it, from the root down, links resolved first, must be the daemon's user's or root's and writable by nobody else, a root-owned sticky directory such as `/tmp` passing when the entry below it is theirs (on Windows owned by the vault's account, SYSTEM, Administrators or TrustedInstaller, with no allow entry that lets another account replace an entry in it) — an account that could replace a directory above the backup directory could put a directory of its own in its place during a run and receive the copy —, both judged before the vault opens and at every run, a run writing into the directory the links lead to, which must be closed in the same way; the unit and the Windows task use `/var/lib/harpoc/backups` and `%ProgramData%\harpoc\backups`, and a job of root's — on Windows an administrator's — takes the copies off the host: the pickup job copies, the vault prunes; it takes only names of the form `harpoc-<YYYYMMDD>T<HHMMSS>Z.db`, since a name that ends in `.tmp` is a run in progress, or one a kill cut short, and can still hold the unlock-key slot. Each run writes its `vault.backup` row before it copies, so the copy holds that row; a worker thread of the daemon, handed the two paths and no key, copies the live database with `VACUUM INTO` into a temporary file closed to everyone else before a byte is written (`0600`; on Windows the vault's account, SYSTEM and Administrators alone), deletes the unlock-key slot from the copy under an in-memory journal with `secure_delete` and checks its integrity; the copy's owner and mode — on Windows its access list — are read back, and it reaches its final name by a hard link, never over a name that exists; a failure removes the temporary file and writes a failed `vault.backup` row. `harpoc backup <file>`, on an unlocked session on the vault host, refuses before the vault opens a target directory that another account can change: on Windows one not closed to other accounts as the scheduled directory is, or one with a directory above it that is not held as the directories above the scheduled directory are, elsewhere one with a directory on its resolved path that is neither the user's nor root's or that someone else can write, a root-owned sticky directory such as `/tmp` passing only above the target's directory; the path is written and printed with its links resolved. Interrupted during the copy (`SIGINT`, `SIGTERM`, `SIGHUP`, and on Windows `SIGBREAK`, Ctrl-Break, since 2026-11-21), the command waits until the copy's running statement returns, removes its temporary file, writes the failed `vault.backup` row and exits 1; a signal that comes once the copy is written lets the run finish. A copy opens by the password alone; the old machine's sealed key does not open it — no copy holds an unlock-key slot, so a start with that key is refused `UNLOCK_KEY_NOT_ENROLLED` and a new key is enrolled and sealed after a restore — and the password must exist offline. A copy holds in clear what the database holds in clear — agents, token claims, policy principals, the audit table's plain columns, certificate PEMs, OAuth endpoints, `secrets.project` — and is material for guessing the password offline, which is why its directory is closed to everyone but the vault user and root (on Windows the vault's account, SYSTEM and Administrators). The Harpoc CA travels in the database, so after a restore the consumers keep their trust. What it does not close: a copy is the vault as it was — a restore brings back revoked tokens for at most 24 hours, revoked or deleted secrets, deactivated agents, removed grants, older policies and the lockout count of that moment; a secret an ssh bootstrap ended comes back with its block and its grant, and a copy taken while a bootstrap ran carries its mark, so that restored secret is ended by the next bootstrap its block admits — after a restore, end every secret that carries a bootstrap block, or change the password on its host (2026-11-24); a copy brings back every SFTP render entry and approval as it holds them, an approval revoked after the copy among them — after a restore, read each slot's approvals again (`secret render list`) (2026-11-25); the copies sit on the daemon's volume, and a full volume stops the audit log and with it the vault, fail-closed; a sealed daemon takes no backup until it is restarted; a copy in progress cannot be interrupted — a stop waits for it, the scheduler giving it 10 seconds and then giving the run up but still waiting until the copy's statement returns —, and no clock ends a copy (2026-11-21); a run cut by a kill or a crash — of the daemon (under the unit systemd's `SIGKILL` after its default 90 seconds, on Windows `Stop-ScheduledTask`) or of `harpoc backup` — can leave its temporary file, `harpoc-<YYYYMMDD>T<HHMMSS>Z.db.<12 hex digits>.tmp`, which can be a complete copy still holding the unlock-key slot, closed to other users like the live database: in the backup directory the next run or the next start removes it, beside an attended target only the next `harpoc backup` into that directory or the administrator by hand (`harpoc-*.db.*.tmp*`) — to be deleted before the directory's files are carried away; off Windows the judgements of a backup's directory and of the directories above it read owner and mode, so they do not see a macOS access list; a copy needs a file system with modes and hard links; two backups into one directory at the same moment fail one of them; and on Windows a pickup job that holds a copy open while the vault prunes makes that run report a failure, though the copy it wrote is complete.
- **Model B on Windows** (2026-11-08): the vault runs as the local account `harpoc`, started at boot by a scheduled task (`deploy/windows/register-service.ps1` grants that account the right to log on as a batch job, which the task needs to start — the one user right the recipe sets; the task's start is measured on the `windows-latest` runner on demand and at real boots of two Windows Server 2025 machines (2026-11-12: a restart; and, registered with `-Proxy`, `-SshAgent` and `-IssueToken`, two restarts and a start from the deallocated state), see `README.md`, "What the Windows deployment does not close"), and each agent as a local account of its own; the vault directory `%ProgramData%\harpoc\vault`, the backup directory `%ProgramData%\harpoc\backups` (2026-11-19) and the runtime directory `%ProgramData%\harpoc\run` grant full control to the vault account, SYSTEM and Administrators alone, and each consumer directory adds read for its agent (`deploy/windows/install-two-identity.ps1`; `server start --runtime-dir` refuses any other access list: the directory's owner must be the vault account, SYSTEM or Administrators, and its access list may grant only those three and, on a consumer directory, the consumer's own local account read-and-execute at most; since 2026-11-11 the directory of an `--issue-token` file is judged the same way under every flag, with the token's own agent in the consumer's place, except that an agent name which resolves to no local account is accepted when the list grants nobody else (a consumer directory is refused then); `%ProgramData%\harpoc\run` is the default under `--ssh-agent`). What it closes, as on Linux: an agent account cannot open the vault directory or the session file, and cannot read the memory or the environment of the vault process or of a child it spawns — opening another account's process for `PROCESS_VM_READ` is checked against that process's access list, which comes from its creator's token, and only `SeDebugPrivilege` opens it regardless (cited from Microsoft's documentation; the `windows-latest` evidence job measures the command-line channel — the agent account's process listing shows the vault process's command line, its paths, ports and each `--issue-token` spec with the consumer, its token file, the names of the secrets it may use, scope and lifetime, but never a secret, since none is ever passed on a command line — and cites the environment block's protection rather than reading it); the unlock key is sealed with DPAPI in the `CurrentUser` scope under the vault account (`--unlock-key-dpapi`), never `LocalMachine`, so the sealed file opens nothing for another account. What it does not close: Administrators and SYSTEM, who read everything as root does on Linux — `SeDebugPrivilege` is the Administrators' by default; whoever can run code as the vault account, anyone holding its password among them, unseals the key, which DPAPI binds to the account's credentials on that machine and not to a boot measurement — no TPM binding; the agent socket's named pipe is reachable as its access list allows — the daemon replaces the list after it opens the pipe (the vault account, SYSTEM and Administrators, and the consumer's account for reading and writing) and refuses to start if it cannot, and a process that creates the pipe's name while the daemon is down makes the start refuse — and that list is its only factor, the ssh-agent protocol carrying no token; and the egress proxy and the REST API, loopback TCP and token-only, with no socket as a second factor on Windows.
- **Identity tokens are not brokered**: an agent's own identity (a chat-channel bot token, a model-provider OAuth token) must be presented by the agent process and cannot be hidden from it; model B keeps third-party secrets away from the agent, not the agent's identity.

## Known Accepted Risks

- **Memory wiping**: JavaScript does not guarantee immediate memory clearing of strings. Wiping of sensitive material in memory is best-effort. Process-mediated injection necessarily passes the credential through a JavaScript string (the subprocess environment) and the child's kernel environment, both outside the vault's zeroization discipline.
- **Injection trust boundary**: Injection assumes a trusted local host. The execution layer that performs injection must be protected from unauthorized access. Process-mediated injection spawns subprocesses without a shell in a clean environment, but the spawned process runs with the credential in its environment.
- **Process output-channel leakage**: Output sanitization redacts the credential and its common encodings (base64/base64url/hex/percent, each also when JSON-escaped) from captured stdout/stderr, but is best-effort. A crafted command can still exfiltrate the credential via an arbitrary encoding, character-by-character chunking, or an indirect file write. Two further residuals are characterized rather than closed: the escape matcher decodes only a single escape layer on its own, but `redactSecretEncodings` wraps it in a structural pass that parses the surrounding JSON document and descends into string leaves that are themselves JSON, to at most four levels of parse depth — not four `JSON.parse` calls in total: a document with many sibling leaves at one level costs one parse per leaf, so the actual call count scales with the document's shape. Total work nonetheless stays bounded, because the leaves at each level are disjoint substrings of their parent — parsing them can never re-scan the same characters twice — so the text parsed across all four levels combined is at most a small constant multiple of the body's own size, and the body itself is already bounded by the descent's size guard (below). Four levels of depth is enough to close the gap for a credential nested as deep as five JSON documents (the document naming it directly, wrapped in as many as four further envelopes). A credential wrapped a sixth document deeper, or carried in a body over the descent's size guard (roughly 4 million characters, not bytes), is still not matched; and the matcher takes the escape reading at a backslash without backtracking, so a value containing a literal backslash adjacent to ambiguous text can still be missed. The fail-safe command allowlist bounds which binaries can be run at all — and an allowlisted binary that is itself a general-purpose instruction vehicle removes that bound, which is why known interpreters are acknowledgement-gated and binaries with a dedicated context are refused outright in the process context; opt-in per-secret network isolation closes the child's own network egress (loopback included) on Linux and macOS, and opt-in per-secret filesystem isolation (`fs_isolation`) closes the specific residual below it — a child denied all filesystem writes (Linux `setpriv`+Landlock or bwrap's read-only bind; macOS `sandbox-exec`; `/dev/null` exempt everywhere) cannot write the value to a file at all, cooperating reader or not. What neither isolation closes: a channel outside the child's own network sockets and file writes — an inherited file descriptor, a debugger or tracer attached from outside the sandbox — is not addressed by either control, and both are opt-in per secret, so a secret without the flag set is unaffected. On Windows both isolations are unsupported by design (an AppContainer would require a native addon): a policy demanding either refuses every process-mediated use there rather than running un-isolated.
- **`full` response mode**: Setting a secret's `response_mode` to `full` disables the vault-layer redaction of that credential (including OAuth access tokens resolved for injection) from HTTP responses — an echoing endpoint then hands the raw value back to the caller. It is settable only via the trusted admin path (CLI/REST, never an MCP tool) and cannot be requested per-invocation unless the policy already allows it. The pattern-based interface guard at the REST/MCP boundaries remains active; CLI and SDK-direct callers receive the truly raw response. Note that REST `PUT .../injection-policy` replaces the whole policy — a client omitting any of the sixteen policy fields is refused `400` naming it; every policy write is audited with its effective mode.
