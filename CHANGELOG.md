## [Unreleased]

### Added

- **URL allowlist patterns accept a bracketed IPv6 literal host** (`https://[::1]:8443/*`, `wss://[fc00::1]/*`), compared in the canonical form `URL.hostname` yields — under deny-by-default an IPv6-literal target would otherwise be unreachable (compromise audit R1, research refinement).
- **A `git` group on the connection config — `harpoc secret connection --git-ca <path>` pins a private CA for the Git-HTTPS transport.** A vault reaching an internal Git server behind a corporate or self-signed CA had no way to say so: `ConnectionConfig` carried `database`, `ssh` and `mail` only, and neither environment route helps — `GIT_SSL_CAINFO` through `env_allowlist` forwards a value from the _vault's own_ environment (a caller cannot set it) and is openssl-only, so Windows' schannel backend ignores it, while `-c` is on the git argument denylist precisely so a caller cannot author config. The pin is therefore **vault-authored**: the connection config gains an optional `git.ca_pem` (same KEK-encrypted blob, **no migration**), and the Git-HTTPS path writes the PEM to a 0600 temp file — through the same `mkdtempSync` → `writeFileSync` → `rmSync` helper the ssh identity file uses, disposed in the existing `finally` — then adds `-c http.sslCAInfo=<file> -c http.schannelUseSSLCAInfo=true` to its forced config, covering both curl backends. A caller's own `-c` stays denied, git's option-prefix expansion included, so the vault-authored pair is the only `-c` that reaches the child; `http.sslCAInfo` is a generic-key setting a URL-specific `http.<url>.sslCAInfo` could outrank in principle, but the child's environment starts empty — no `HOME`, no user gitconfig, only PATH/SystemRoot and admin-allowlisted names — which is the same footing the existing `http.followRedirects=false` control stands on. **Audit shape:** `ca_pinned: true` rides only the two rows the HTTPS path itself writes (the spawn-failure row and the result row); a refusal reached before the CA file exists — URL validation, the allowlists, a transport or argument refusal — carries no key, so an absent `ca_pinned` must **not** be read as "no CA configured". The `policy.grant` row for a connection-config write gains `has_git`. REST `PUT …/connection-config` and the SDK carry the group through the schema alone, and the CLI flag merges per field like `--mail-ca` (`--clear` resets it, the PEM is read from the path without validation — parity with its siblings) (D64).
- **`sanitized: true` on the `secret.use` audit row of a context whose output a redaction actually changed.** The vault redacts the injected credential and its base64/base64url/hex/percent encodings out of every context's output, but the trail said nothing about it: a reviewer could not tell a clean response from one the vault had to scrub, and the only signal was an in-memory counter at the interface boundary. Every context now folds the flag into its own row when its own redaction changed something, detected by byte identity (an unchanged input comes back byte-identical) rather than by re-scanning the output. The key is **absent when nothing changed** — and absent by policy under `response_mode: full`, which redacts nothing by design — so its presence is the whole signal; SMTP never carries it, its result holding no text from the endpoint. The flag rides the **post-spawn row**: a success, or a graceful non-throwing failure such as `PROCESS_TIMEOUT` whose captured output was redacted. **Refusal rows are never flagged** — a refusal carries its own `error`. There is deliberately no new audit event type: a second row per redaction would double the trail's volume for no extra information. Two internal shapes moved with it — the HTTP context now redacts **inside** its injector, ahead of its own row, rather than in the engine afterwards (every wire result is byte-identical), and `SpawnCapturedResult`, which `@harpoc/core` re-exports, gains a **required** `redacted: boolean`, so an external constructor of that type must add the field (E70).
- **`RESPONSE_TOO_LARGE` (HTTP 502, the 106th error code — up from 105) and a 4 MiB cap on HTTP response bodies.** The HTTP injector read whatever a target sent it: a hostile or merely broken endpoint could answer with a body of any size, which the vault buffered, redacted and carried — an unbounded cost on the one path an untrusted server controls. The injector now checks `Content-Length` before reading (cancelling the body when it is already over the cap) and streams the read through a shared capped-read helper, refusing at `MAX_HTTP_RESPONSE_BYTES` (4 194 304 bytes) with `Response body from <origin> exceeds the 4194304-byte limit` — the **origin** only, never the path or query — and the failed `secret.use` row carries `error: RESPONSE_TOO_LARGE`. **Refused, not truncated:** a mid-string cut can split an echoed credential into halves the redactor no longer matches, so a truncating cap would trade a memory bound for a leak. The cap is deliberately equal to the structural (nested-JSON) redaction pass's own size guard, so a body that passes the cap never skips that pass. `response_mode: status_only` is untouched — it never reads a body at all. The same helper closes the matching hole in the ACME client, whose 1 MiB cap trusted `Content-Length` and therefore bounded nothing on a chunked response; its refusal message is unchanged (E80, N6, E86a).
- **An ACME-issued certificate's account key is stored inside the same transaction as the certificate.** Issuance imported the certificate first and wrote the ACME account afterwards through a separate engine call, so a crash — or a session TTL expiring during a long order — between the two left a certificate whose account was simply gone: unaudited, and under `--auto-renew` a renewal that could never succeed. `importCertificate` now takes the account with the certificate (`acmeAccountJson`, legal only alongside `acmeIssued: true` — otherwise `INVALID_INPUT` "acmeAccountJson requires acmeIssued (an ACME issuance)" before any write), encrypts it under its own AAD and inserts it with the certificate row in one transaction. What is stored is the ACME **account** key and its account URL — the identity a renewal re-uses, not the certificate's own key. The `cert.issue` audit detail gains `acme_account: true|false`, and the separate write's `policy.grant { config: "acme_account" }` row is gone with it (see Removed); `getAcmeAccount` and its `secret.read` row are unchanged (E86b).
- **An optional `port` on the `ssh` and `sftp` actions** — both contexts always dialled 22, so a vault simply could not reach an SSH or SFTP service anywhere else. `use_secret` now accepts `action.port` (integer 1–65535) on both, the vault passes it as `ssh -p <port>` / `sftp -P <port>`, and `harpoc secret use --port` — whose help named the database and mail contexts — covers them; the MCP tool description names it too. **Pinning a non-default port:** OpenSSH looks a non-22 host key up under the bracketed `[host]:port` form first and, when no such entry exists, falls back to the bare-host line if its key matches (`found matching key w/out port` — verified against OpenSSH 9.6 and Win32-OpenSSH 9.5), so a pin stored with `harpoc secret connection --known-host` binds a non-22 port in either form; a bare line holding a different key is refused as an unknown host, and a `[host]:port` entry always outranks the bare one, which is the form to use when one host serves different keys on different ports. The vault deliberately never rewrites a stored pin, and the `--known-host` help says so. The host allowlist stays host-only (a port is not an authorization subject) and Git-over-SSH is untouched: it folds the same hardening args into `GIT_SSH_COMMAND` and derives its port from the repository URL. **Audit shape:** the `secret.use` detail carries `port` when an ssh action names one, and on **every** sftp row as `port: number | null` — an additive key on an existing row type, which a consumer parsing sftp details strictly must accept (D59).
- **A failed scheduled renewal writes a failed `cert.renew` audit row.** Only the success writer existed, so `server start --cert-renew` reported a failure on stderr and quarantined it with backoff while the trail an operator actually reviews stayed silent — a certificate could fail to renew for weeks and leave no auditable trace. `RenewalScheduler.tick()` now calls the new `VaultEngine.auditCertRenewFailure(secretId, error)` before `onRenewError`: one `cert.renew` row, `success: false`, `detail: { action: "scheduled_renewal", error: <code or INTERNAL_ERROR> }`, NULL principal — the scheduler is the trusted local path, like `server.start`. Every host gets the row, the CLI daemon and an SDK embedder alike. The write itself is fail-open (a vault sealing during shutdown must not kill the loop), and `harpoc cert renew` is unchanged — an operator-driven renewal is already audited by its own path (N5).
- **`tls_opt_out: true` on the `database` context's `secret.use` rows.** A per-secret `tls_mode: "disable"` is an audited decision where it is set, but the use rows it governed carried no mark, so a reviewer reading the trail could not tell an unencrypted database session from an encrypted one. The five database rows written once the TLS mode is known now carry the flag; the unsupported-engine, allowlist and SSRF refusal rows deliberately do not — they are written before a TLS mode is knowable (E81).
- **A second descendant sweep after a timed-out tree kill on Windows** — `taskkill /T` snapshots the child's descendants once, so a grandchild created between that snapshot and the kill survived with the injected credential still in its inherited environment. After the child exits, the vault now enumerates every process still naming it as parent (`Get-CimInstance Win32_Process`, through the OS-shipped Windows PowerShell host, System32-pinned like the DPAPI bridge), filters to those created after the child was spawned and before it exited (a process that later inherits the dead pid can only have newer children, and an orphan of an earlier holder of that pid is older than the child itself) and kills each with its own `taskkill /T /F`. Bounded (30 s since 2026-08-29; 15 s before) and best-effort: a failed sweep settles the spawn with what was captured, as a failed `taskkill` always did. Because the sweep — and the wait for `taskkill`'s own completion (10 s bound) before the 2 s settle backstop is armed — now sit inside the settlement, a timed-out win32 spawn whose kill does not take settles up to ~12 s after its timeout (was ~2 s), and up to 30 s (15 s before 2026-08-29) after the child's exit while a slow sweep runs; error path only. Timed-out win32 spawns only — the normal-exit path and POSIX (where the process-group signal already reaches the whole tree) are untouched, and the result shape gains no field.
- **`MISSING_DEPENDENCY` (HTTP 501, the 105th error code — up from 104)** — the SDK's `DirectClient` now reports an absent optional peer as a `VaultError` instead of Node's raw `ERR_MODULE_NOT_FOUND`. `@harpoc/oauth-proxy` and `@harpoc/cert-manager` are optional peers, dynamically imported inside the OAuth and certificate methods precisely so a consumer needing neither surface installs neither — which makes "the peer is not installed" an ordinary, expected outcome of calling one, yet it arrived as an untyped `Error` that no `VaultError`-shaped handler recognises, in the one case whose remedy is entirely mechanical. All three lazy load sites now route through a single internal `importPeer` helper that maps `ERR_MODULE_NOT_FOUND` / `MODULE_NOT_FOUND` onto `MISSING_DEPENDENCY`, naming the specifier to install. The wrap is deliberately narrow: it fires only when the message names the peer **in quotes**, which is how Node reports the module it could not resolve. An installed peer whose _own_ dependency is missing raises the same code while naming the peer as the importer path instead, and answering that with "install `@harpoc/oauth-proxy`" would send an embedder after a package they already have — so the transitive case is rethrown untouched, as is any message shape that does not quote at all.
- Web UI: OAuth **Refresh token** and certificate **Renew certificate** buttons on the secret detail page (renew uses the http-01 default port 80; non-default ports remain `harpoc cert renew --http-port`).
- Web UI: light theme — follows the OS preference, with a per-session override toggle in the nav (`sessionStorage` only).
- `harpoc server start --ui-token-ttl <minutes>` — shortens the Web UI launch token's validity (1–1440; requires `--ui`; values over the 24 h cap are refused, never clamped).
- **An authoritative agent registry, an issued-token registry and a permission matrix — the `harpoc agent` CLI group, `/api/v1/agents` and `/api/v1/tokens`, and the Agents / Permissions / Tokens web pages** (v1.4 agent governance; `design-v1.4-agent-governance.md`). Until now a "named agent" was nothing but the JWT `sub` string under `principal_type: agent`: nothing persisted an issued token (only the KEK-encrypted `token.create` audit detail), `revoked_tokens` was a bare JTI denylist, and `access_policies.principal_id` was a free string with no existence check, so a typo'd grant was silently inert. **The agent registry** (the new `agents` table) is now authoritative for `agent`-type principals — `createToken` refuses an unregistered or inactive agent before signing, `grantPolicy` refuses one after the existing `create` refusal and before the per-secret `admin` check, and both read the _effective_ type, so a token minted with no `principal_type` counts as an agent (see Changed for the breaking edge); `tool` and `user` principals stay free-string. An agent's **name is its principal id and is immutable** — a rename cannot reach signed `sub` claims and would split the audit history — while description and owner are editable metadata, and `last_active_at`, `active_tokens` and `grants` are **derived at read** (the first over a new `(principal_type, principal_id, timestamp)` audit index) rather than maintained, so governance costs nothing on the hot path. Lifecycle mirrors secret revoke/delete: `deactivate` is reversible, `delete` is hard and additionally removes the agent's policy rows, and both revoke every live token of the agent through the same `revoked_tokens` insert and expiry clamp `harpoc auth revoke` uses, each with its own `token.revoke` row carrying `reason: "agent_deactivated"` or `"agent_deleted"` — and because the stdio `ScopeGuard` re-consults the revocation store on every call, deactivating an agent is a **live kill switch** for a running MCP server rather than merely a block on new tokens. A repeated deactivate is idempotent (the first `deactivated_at` stays; the no-op is still audited). **The issued-token registry** (`issued_tokens`) holds claims metadata only — **never the JWT**: subject, principal type, agent, scope, project, secret-name patterns, the new optional `label`, issued-at and expiry. `createToken` writes that row and its `token.create` audit row in **one transaction** (token issuance is a database mutation from here on), and a token's status is derived at read — revoked → expired → active — from a `revoked_at` mirror column that `revokeToken` stamps inside its existing transaction, because `revoked_tokens` rows are pruned once their clamp expiry passes and a status derived from that table alone would later report a revoked token as merely expired. `verifyToken` never reads the registry: `revoked_tokens` remains the sole revocation truth, and tokens issued before the upgrade keep working until they expire. **The permission matrix** is one replace-semantics cell per (agent, secret) — `PUT /api/v1/agents/:name/secrets/:handle/permissions` — where the existing grant/revoke pair is two calls over a schema that permits duplicate rows: in one transaction it removes every row for that pair, inserts the new one when `permissions` is non-empty, and reports `gated_before` / `gated_after` so a caller learns when its own write flipped the secret's presence gate. Empty cells are never written, `create` stays ungrantable per secret, and `admin` stays the only implication. **REST** gains `/api/v1/agents/*` and `/api/v1/tokens/*` under the existing rate-limit → audit → auth middleware order, every route `admin`-scoped at the interface: `GET /agents` (`?status=active|inactive|all`), `POST /agents` (201), `GET`/`PUT`/`DELETE /agents/:name`, body-less `POST /agents/:name/deactivate` and `.../activate`, `GET /agents/:name/policies`, the matrix cell above (which additionally scopes on the secret it names) and `GET /tokens?status=&agent=` plus `DELETE /tokens/:jti`; `GET /api/v1/audit` gains `principal_type` and `principal_id` filters. Deliberately absent: any token-mint route — issuance stays CLI- and SDK-only, which is what keeps the thesis's structural/disciplinary split literally true — the `/agents/:name/tokens` and `/agents/:name/audit` convenience endpoints the roadmap sketched (the token filter and the audit principal filter carry the same data with two fewer routes), and any MCP tool or resource at all. **The CLI** gains the `harpoc agent` group — `register <name> [--description] [--owner]`, `list [--all]`, `show <name>`, `update <name>` (merges like `secret allow`: an omitted flag keeps the stored value, while `--clear-description` / `--clear-owner` reset it), `deactivate` / `activate`, `delete [--confirm]` (the confirmation names the token and grant counts it is about to revoke and remove) and `permissions <name> <handle> (--permissions <list> | --clear) [--expires <minutes>]`, which prints the gating flip on stderr when its write changes one — plus `harpoc auth list [--agent <name>] [--all]` over the issued-token registry and `harpoc auth token --label <text>`. Human output by default and exact JSON under `--json`, as everywhere; every new command takes `--token` / ambient `HARPOC_TOKEN` with the `admin` scope its REST counterpart enforces (the `token-parity.test.ts` map is extended), and `server start --ui`'s launch token now appears in the registry under the label `web-ui launch`. **The SDK** gains eleven parity methods on both clients — `registerAgent`, `listAgents`, `getAgent`, `updateAgent`, `deactivateAgent`, `activateAgent`, `deleteAgent`, `listAgentPolicies`, `setAgentPermissions`, `listTokens`, `revokeToken` — and `queryAudit` forwards the two principal filters; there is still no `createToken` on either client. **The web UI** grows from three pages to six: `#/agents` (table plus an inline register form) and `#/agents/<name>` (metadata editing, deactivate / activate / delete behind a count-naming confirmation, and Grants / Tokens / Recent-activity sections), `#/permissions` (the agents × secrets grid, with a cell editor of six permission checkboxes — `create` is not offered — an optional expiry and Save / Clear / Cancel: it predicts a gating flip client-side and asks for confirmation **before** the `PUT`, then states the engine's `gated_before` / `gated_after` result **after** it, because the prediction is advisory and the response is the truth), and `#/tokens` (status and agent filters, an expiry countdown that turns amber under an hour, and one-click revoke with a warning when the jti being revoked is the session's own token — decoded locally from the bearer the page already holds, no secret involved). The audit page gains principal-type and principal-id filter inputs, and the secret detail links its read-only policy list to the matrix prefiltered to that secret. Values stay write-only, `sessionStorage` stays the only storage, and the posture sweep covers the new files. **Substrate:** migration 012 (schema v11 → v12) creates both tables, two token indexes and the audit principal index, and **auto-registers every agent already named in `access_policies`** inside its own transaction, idempotently and fail-closed; three error codes — `AGENT_NOT_FOUND` (#102, 404), `AGENT_INACTIVE` (#103, 403), `AGENT_EXISTS` (#104, 409) → **104 codes**; five audit event types — `agent.register`, `agent.update`, `agent.activate`, `agent.deactivate`, `agent.delete` → **35 types**; and two optional detail fields on the token events (`label` on `token.create`, `reason` on `token.revoke`). Governance reads are unaudited on success, exactly like `listPolicies`; every governance mutation is audited inside its own transaction, denials included. Two operator notes ride the kill switch: it reaches only tokens the registry knows, so tokens issued **before** the upgrade — migration 012 backfills agents, not tokens — are neither listed by `harpoc auth list` nor revoked by deactivate or delete, and keep working until they expire (at most 24 h; `harpoc auth revoke <jti>` is the remedy, the JTI being in the `token.create` audit row's detail) — superseded 2026-08-27: the `principal_type` claim is now mandatory, so a pre-registry JWT is refused at verification (see Changed). And a revocation that arrives with a token is now **attributed**: `VaultEngine.revokeToken` takes an optional trailing caller, so `DELETE /api/v1/tokens/:jti` — and the UI's Revoke button through it — writes a `token.revoke` row carrying the requesting principal and the `rest` interface, while `harpoc auth revoke` and the in-process SDK stay caller-less trusted paths whose rows keep NULL principal columns. Contradictory CLI flag pairs are refused rather than resolved silently: `agent update --description` with `--clear-description`, `--owner` with `--clear-owner`, and `agent permissions --clear` with `--expires` each fail before the engine is touched. **No new npm dependency, and no change to the JWT claims, to `access_policies`' schema or to `verifyToken`.**
- **Five new `use_secret` injection contexts — SMTP, IMAP, WebSocket, SFTP and docker-registry — plus Redis and MongoDB database engines** (v1.3 extended injection contexts, thesis-aligned; `design-v1.3-contexts.md`). The action union widens from six context types to eleven. **SMTP** (`action.type: "smtp"`, request-mediated): an in-house submission client on `node:net`/`node:tls` only — no third-party mail library in the vault process — dials the mail server, authenticates (`username:password`, or **XOAUTH2** for an OAuth-type handle), and assembles and sends the MIME message itself (the client never authors MIME); the result reports the accepted-recipient count and the vault-generated Message-ID, and the message never comes back. AUTH bytes never cross a plaintext leg — `starttls` upgrades the socket before authenticating and a server that fails to advertise STARTTLS is refused before any credential byte is written. **IMAP** (`action.type: "imap"`, request-mediated, **implicit TLS only**): the same in-house client family, authoring structured operations (`search`/`fetch`/`store`/`move`/`copy`/`expunge`) rather than accepting a raw IMAP query string, with command injection impossible by construction (user data flows only through IMAP quoted strings or synchronizing literals, never onto the command line). **WebSocket** (`action.type: "websocket"`, request-mediated, on undici): the credential is applied at the upgrade handshake through the same injection config the HTTP context uses, `collect` bounds the frames gathered, and the pinned SSRF dispatcher and injection-config application are hoisted from the HTTP injector (one implementation, not a copy). **SFTP** (`action.type: "sftp"`, process-mediated): rides the same ephemeral in-process ssh-agent as the SSH context — the private key never touches disk — with strict host-key pinning; leading-`-`/control-character paths are refused at the schema boundary so an option flag can never be smuggled through a path. **Docker registry** (`action.type: "docker_registry"`, process-mediated): the vault spawns the `docker` CLI and injects the credential through a vault-authored credential helper (the credential reaches docker through the helper, never argv), and the generated `config.json` carries `credHelpers` only — never a static `auths` entry. **Redis and MongoDB** join the `database` context as two new engines behind a new `DbCommandAdapter` seam: the SQL engines take a `query`, Redis takes a string-array `command`, MongoDB a document `command` (mutually exclusive per engine, enforced at the schema boundary); both honor the connect-and-command timeout budget and TLS-by-default with the audited `disable` opt-out, exactly as the SQL engines do. Every one of the five contexts preserves the opacity invariant: no credential rides the result the agent receives (proven per-context in the integration posture sweep). Two new npm dependencies (`redis@^6.2.1`, `mongodb@^7.5.0`), both `core`-only; the `database` action's `query` field becoming schema-optional is internal — every existing `{engine: "postgresql"|"mysql", query, params}` call remains valid and required (see Changed). The thesis Ch. 6 e2e harness gains a `context-opacity` scenario (six baseline-vs-Harpoc opacity arms, one per new context) and four fleet backends (a mail server, `redis:7`, `mongo:7`, `registry:2`); the full Linux + Docker fleet run stays **owed at the next Linux session** (the harness's D8 convention — non-Linux verifies scenario collection only). **No new migration, no new audit event type.**
- **Two new per-secret injection-policy fields for the mail contexts** — `smtp_recipient_allowlist` (default `[]`) bounds SMTP recipients by exact address or `*@domain` pattern: absent, any recipient is allowed for a body-only send; configured, every `to`/`cc`/`bcc` recipient must match, and an attachment-bearing send is refused outright unless the list is configured. `imap_read_only` (default `false`) is a tighten-only knob that refuses the mutating IMAP operation kinds (`store`/`move`/`copy`/`expunge`) before any socket opens. Both ride the existing KEK-encrypted policy blob — no migration; pre-feature blobs load as `[]`/`false` — and both are set only through the trusted admin path: CLI `secret allow --recipient <pattern>` (repeatable, additive) and `--imap-read-only` / `--no-imap-read-only` (tri-state merge like `--network-isolation`), REST `PUT .../injection-policy` (whole-policy replace). A new `mail` connection-config group (`tls: { ca } | false`) carries the SMTP/IMAP TLS policy: `false` is the audited plaintext opt-out honored by **SMTP only**, since IMAP is implicit-TLS-only (an `imap` action under a `tls: false` mail config refuses before any socket) (Since 2026-09-02 the REST PUT requires every field — see the R3 entry under Changed; only the CLI's `secret allow` merge still fills an omitted field.)
- **Ten new error codes (#92–#101 → 101 total)** for the five contexts — attachment-policy, recipient-allowlist, IMAP mutation-not-allowed, SFTP and docker-registry operation failures and the rest of the per-context refusal vocabulary. Docker-registry and SFTP secrets running under `network_isolation` / `fs_isolation` are handled at the **engine level, before any injector**: the docker-registry context refuses outright under either isolation flag (the daemon, not the spawned CLI, does the registry I/O, so isolating the CLI would wrap the messenger rather than the actor). **No new migration, no new audit event type.**
- **XOAUTH2 for OAuth handles on both mail contexts.** SMTP delivers the spec's "XOAUTH2 for OAuth handles" (§4.2/§6.4) sourcing the mailbox account name from `action.from`; IMAP delivers it through the imap action's own optional **`account`** field (2026-08-20 — an imap action has no envelope to read an identity off, and the OAuth token record stores no account identity; this closes the "IMAP does not yet support OAuth handles" limitation the tranche originally shipped with). An OAuth-type secret used with an `imap` action authenticates via XOAUTH2 as `account`'s mailbox; without the field it still **refuses fail-closed** (`INVALID_INPUT`, message names the field) rather than putting the access token on the wire as an IMAP password — and the mirror image is refused too: `account` on a `username:password` secret would be silently dead (that arm's wire username comes from the secret value), and dead config refuses rather than drops. The identity lands on the audit trail as `auth_account` in the imap `secret.use` details. CLI: `secret use --account <addr>`; REST, MCP and the SDK widen automatically through the shared action union. Password-authenticated IMAP without the field is unchanged
- **A web interface for the vault — `@harpoc/web-ui`, served at `/ui`** — a Preact + Vite single-page application, strict TypeScript, in the default build/typecheck/test/lint pipeline like every other product package, mounted by the REST API through a new `uiDir` option (`CreateAppOptions.uiDir` / `ServerOptions.uiDir`) and launched with `harpoc server start --ui`. It carries three pages: a **dashboard** whose attention queue reports the secret counts by status, expiring secrets, OAuth tokens needing refresh, certificates nearing renewal and the most recent audit failures; a **secrets** list and detail view (metadata, the injection-policy editor including the interpreter-acknowledgement checkbox, OAuth and certificate status panels, and the create / rotate / delete forms); and an **audit** page (filterable feed plus chain verification). **Values are write-only, structurally**: the client carries no value-fetch method at all — there is nothing to call — and a new or rotated value is base64-encoded in the browser through a `TextEncoder` helper on its way to the existing routes, so the vault's no-read posture is the same on the web as it is on every other surface. `posture.test.ts` sweeps the whole source set, `index.html` included, for `localStorage`, for any `/value` route and for any external origin, so a regression on any of the three reds a test rather than shipping. `--ui` **requires `--rest`** (refused before the at-least-one-transport check, so the message names the missing flag rather than listing transports), resolves the built assets through `require.resolve("@harpoc/web-ui/package.json")`, mints an **admin** launch token capped at the 24 h `MAX_TOKEN_TTL_MS`, and prints `http://<host>:<port>/ui#token=<jwt>` to **stderr** with a warning that the link grants admin access until that token expires. The token rides in the URL **fragment**, never the query string: a fragment is never sent to the server, so it cannot land in a request line, an access log or a proxy trace. The browser keeps it in `sessionStorage` (never `localStorage`) and sends it as a Bearer header on every call; a 401 drops to a paste-token screen and a `VAULT_LOCKED` refusal to a sealed takeover naming `harpoc unlock`, which keeps the two degraded states distinct in remedy rather than only in wording. The static handler is deliberately **hand-rolled** rather than an adapter `serve-static` — the containment check is the security boundary and must not depend on `process.cwd()` or on adapter path semantics: the request path is `decodeURIComponent`-decoded (a malformed escape 404s), normalized and resolved against the root and refused unless it is the root or sits under it, and the extension must be in a content-type allowlist (an unknown extension 404s even when the file exists). Every response carries `default-src 'self'` (with `script-src` / `style-src` / `font-src` / `connect-src` `'self'`, `img-src 'self' data:`, `frame-ancestors 'none'`, `base-uri 'none'`, `form-action 'self'`) and `X-Content-Type-Options: nosniff`; hashed `assets/` are immutable-cached and everything else is `no-cache`; an extensionless path falls back to `index.html` for SPA routing. Like `/api/v1/health`, `/ui` sits **outside** the `/api/v1/*` middleware patterns — unauthenticated and un-rate-limited — which is what lets the launch URL load before any token exists. Dark-only palette at launch; the token-lifecycle page arrived with v1.4, and the light theme and the OAuth-refresh / cert-renew button pair arrived with v1.4.1. No new error code, no migration
- **Three API extensions the web interface reads** — `POST /api/v1/audit/verify` (scope `admin`) runs the audit chain verification the CLI's `harpoc audit verify` already performed and answers a **metadata-only** report — `{ valid, checked, legacy, first_broken_id }`. It deliberately does **not** return the chain tail: the tail is anchor material, and an anchor exported through the browser would live on the same disk it guards, so `harpoc audit anchor` stays the only export path. `GET /api/v1/audit` gains a `success=true|false` filter, parsed from the query string and validated by the shared `auditQuerySchema` (any other value is a `400`, not a silently ignored parameter) and pushed all the way down through `AuditQuery` into the store's `WHERE success = ?`, so "show me the failures" is a query rather than a client-side filter over a truncated page. `GET /api/v1/health/expiring` gains `oauth_refresh_needed` and `certificates_nearing_renewal` alongside its existing `data`, read from the same metadata-only, policy-filtered engine projections MCP's `check_secret_health` already reports (access tokens expiring within the hour; each certificate inside its own `renew_before_days` window) and scoped to the token's project and secret-name patterns exactly as the expiring list itself is — so the aggregates stay computed over the caller-addressable set. No new error code, no migration
- **`harpoc cert issue` chooses its key algorithm** — `--algorithm rsa|ec`, with `--bits 2048|4096` or `--curve P-256|P-384`, the same option triple `cert csr` already carried. Both commands now parse it through one shared module, so their value tables, their refusal messages and their pairing rule cannot drift apart: `--bits` only pairs with `rsa` and `--curve` only with `ec`, a mismatch is refused rather than silently ignored, and every value is range-checked before the vault opens, so an operator typo never spends a key-pair generation. The default stays **RSA-2048** — an operator who never types `--algorithm` gets exactly what `issue` produced before the flag existed — so what used to be a flag asymmetry between `csr` and `issue` is now only a _default_ asymmetry (`csr` still defaults to EC P-256, which makes a bare `--bits` valid on `issue` and refused on `csr`, and a bare `--curve` the other way round). `IssueOptions` gains `modulusLength` and `namedCurve`, which reach the certificate key only; the ACME account key stays EC. Issuance remains a CLI affordance — no REST, MCP or SDK surface changes, and no shared schema changes
- **A ceiling on concurrent OAuth authorization flows** — `OAuthManagerOptions.maxPendingAuthorizations` (default 32) caps how many authorization-code flows one manager keeps waiting on a browser leg, each of which holds an ephemeral loopback listener until its callback arrives or the five-minute timeout fires. Over the cap a start refuses with `RATE_LIMIT_EXCEEDED` — `429`, `Too many pending authorization flows`, on `POST /api/v1/oauth/authorize` — before anything binds. Device-code flows hold no socket and are exempt; restarting a flow that already holds one supersedes it instead of tripping the cap; and a refused start leaves the PENDING secret and its `oauth.authorize` row behind, resumable by a later POST, which is exactly what `create` scope already buys. The cap bounds _steady-state_ socket holding rather than instantaneous peak: the count is taken before the bind while registration follows the awaited start, so a simultaneous burst can overshoot the ceiling briefly — bounded in turn by the global 1000/min limiter
- **`createDefaultOAuthManager(engine)` exported from `@harpoc/rest-api`** — the OAuth manager `createApp` builds when the caller passes none is now a named factory rather than an inline construction, so a host can build that same manager, hand it in, and still hold the reference it needs to dispose of it. `harpoc server start --rest` does precisely that: it constructs through the factory and calls `cancelPendingFlows()` during shutdown, before `engine.destroy()`, so a pending flow's callback listener is released rather than left to the process exit. `createApp`'s signature is unchanged, and it still builds its own manager (ephemeral callback port) when none is supplied
- **SDK: `DirectClient.close()` and an `onBackgroundFlowError` option.** Direct-mode background OAuth failures — the deferred browser leg's token exchange, a device-code poll — previously vanished into the manager's internal catch, leaving the secret PENDING with no signal, and the auth-code callback server pinned the embedder's event loop for the 5-minute callback timeout with no cancel path. `DirectClientOptions.onBackgroundFlowError` now receives genuine failures (default: a stderr warning, mirroring the REST and MCP hosts), and `close()` aborts any pending flows — an abort is an expected cancellation and is deliberately not routed to the handler
- **OAuth and certificates across MCP, REST and the SDK — and the certificate renewal daemon** — the OAuth 2.1 proxy and the certificate manager, until now reachable only from the CLI, are wired into every remaining interface. **MCP** grows to nine tools. `start_oauth_flow` (scope `create`) provisions an OAuth provider secret **config-then-defer**: its input schema has no `client_secret` field at all — ten public metadata keys, and an undeclared one smuggled in is dropped rather than exchanged — so `authorization_code` stores the PENDING provider configuration and answers `pending_authorization` with the instruction to complete the browser leg via `harpoc oauth connect <name>` (that leg never runs from MCP), `client_credentials` collects the client secret through the existing out-of-band chain (URL-mode elicitation → controlling-terminal prompt on stdio launches → otherwise `pending` plus the CLI instruction) and completes in-process with the collected bytes zeroed in a `finally`, and `device_code` returns `auth_url` + `user_code` while the poll completes in the background. `renew_certificate` (scope `rotate`) takes `{ handle, http_port? }` (narrowed to `{ handle }` before release — see the breaking entry under Changed) and returns certificate metadata only, under `harpoc cert renew`'s refusals unchanged (http-01 only, known ACME account origins only). `check_secret_health` additionally reports `oauth_refresh_needed` (access tokens expiring within the hour) and `certificates_nearing_renewal` (each certificate inside its own `renew_before_days` window), both read from two new metadata-only, policy-filtered engine projections, so no encrypted column ever leaves core and the aggregates are computed over the caller-filtered set. No MCP tool accepts or returns a client secret, refresh token or private key. **REST** gains `/api/v1/oauth` — `POST /authorize` (`create`), `GET /:handle/status` (`read`), `POST /:handle/refresh` (`rotate`, → `{ refreshed: true, expires_at }`) — and `/api/v1/certificates` — `POST /import` and `POST /csr` (`create`), `POST /:handle/renew` (`rotate`), `GET /:handle/status` (`read`) — both mounted under the same rate-limit → audit → auth middleware as the secret routes. Unlike MCP, REST is a trusted administrative path and accepts an optional `client_secret` on `POST /authorize`; the route always answers **201** (a secret row was created or resumed) and the body's `status` differentiates the grants — `authorized` for client credentials, otherwise `pending_authorization` with `auth_url`, plus `user_code` for device code. Authorization-code flows start **non-blocking** and complete when the browser reaches **the OAuth proxy's own loopback callback server**, so the API deliberately carries **no** `GET /oauth/callback`; the default manager binds an ephemeral callback port (a fixed one would collide across concurrent or re-posted flows on a long-lived server), a re-POST resumes a still-pending flow, and a background failure surfaces as a stderr warning rather than a response nobody is waiting for. `POST /certificates/import` **requires** `certificate_pem`, answers `{ handle, secret_id }`, and refuses a passphrase-protected `private_key_pem` with `ENCRYPTED_KEY_UNSUPPORTED` (400) naming `harpoc cert import` — decrypt-at-import needs a hidden passphrase prompt, which no HTTP request can serve. `POST /certificates/csr` carries the CLI's pairing rules (EC P-256 by default; `bits` only with `rsa`, `curve` only with `ec`, a mismatch refused rather than silently ignored) and answers `{ handle, csr_pem }`. ACME issuance stays a CLI affordance — dns-01 is interactive and http-01 wants port 80 — so no issuance route ships; PEMs travel as plain JSON strings. **The SDK** gains seven `VaultClient` methods implemented in both clients — `startOAuthFlow`, `getOAuthStatus`, `refreshOAuthToken`, `importCertificate`, `generateCsr`, `renewCertificate`, `getCertificateStatus` — with the same per-grant semantics in REST and in-process modes, and the direct client deliberately opens no browser (the embedder decides); `@harpoc/oauth-proxy` and `@harpoc/cert-manager` become **optional** peer dependencies, dynamically imported inside the method bodies, so a consumer needing neither surface installs neither package and a missing one surfaces as Node's own module-not-found naming it. **The CLI** gains `harpoc oauth providers`, which lists the provider presets with their endpoints and default scopes (human listing by default, exact JSON under `--json`) from static data — it loads no vault and takes no token — and `harpoc server start --cert-renew [--cert-renew-port <p>]`, which runs the certificate `RenewalScheduler` inside the long-lived server process, mirroring `--oauth-refresh` in every respect: valid standalone as a renewal daemon, combinable with the other server flags, an hourly check whose first tick fires one interval after start, per-certificate failure quarantine with exponential backoff capped at 24 h, failures audited as a failed `cert.renew` alongside a stderr warning, and an in-flight renewal drained on shutdown before the vault seals. It renews **only certificates carrying `auto_renew: true`, and only inside their own `renew_before_days` window** — the moment the intent `--auto-renew` records finally acts, which is what the certificate-lifecycle entry below was still waiting for. No new error codes, no new audit event types, no migration
- **Certificate lifecycle management** — the vault now imports, requests, issues, renews and reports on X.509 certificates end to end. The engine gains eight certificate methods, which hold the whole storage and crypto boundary: `importCertificate` parses the leaf with `node:crypto.X509Certificate`, verifies the private key against it (`checkPrivateKey`) before anything is written, KEK-encrypts the key, and propagates the certificate's `notAfter` onto the secret's `expires_at` so the existing lazy-expiry path applies unchanged (a CSR-only import carries no certificate and therefore no expiry, and is refused unless it supplies both the CSR and the requested subject); `updateCertificate` completes a renewal or a first attachment, re-parsing the metadata, refreshing `expires_at` and transitioning a PENDING secret to ACTIVE; `getCertificateStatus` and `getCertificatePem` report health and hand back public material without decrypting anything, while `getCertificatePrivateKey` is audited as a `secret.read` carrying a `certificate_private_key` marker; `getExpiringCertificates` backs the renewal query; and `storeAcmeAccount` / `getAcmeAccount` KEK-encrypt the per-certificate ACME account blob under two new AAD domains, so no code outside the engine ever sees the KEK. The domain work lives in a new **zero-dependency `@harpoc/cert-manager` package** (`@harpoc/shared` + `@harpoc/core` only): a minimal DER writer and a PKCS#10 CSR builder on top of it (subject CN plus a SAN extension over dNSName and iPAddress entries), whose RSA output is _byte-identical_ to OpenSSL's for the same key — pinned by a committed golden vector and cross-checked with `openssl req -verify`; an in-house **RFC 8555 ACME client** on `fetch` and `node:crypto` JWS, signing ES256/ES384/ES512 or RS256 with the algorithm, key type and digest pinned together per curve (a mismatched triple fails closed rather than signing), pooling replay nonces with a bounded `badNonce` retry, **refusing redirects instead of following them** (which is what keeps the JWS `url` claim naming the endpoint that actually answered), and mapping problem documents onto `CERT_ACME_FAILED` with the ACME problem type and the target origin only — never key material, never the rest of the URL; the Let's Encrypt production and staging origins are pinned, and a stored account whose origin is unknown makes a renewal _refuse_ rather than silently fall back to production; http-01 (a temporary responder bound only for the challenge window, serving only `/.well-known/acme-challenge/<token>`) and dns-01 (the TXT value computed for manual placement) challenge solvers; and an hourly `RenewalScheduler` with per-certificate failure quarantine and exponential backoff — a library at this point, wired to a daemon by the entry above. Five CLI commands ship the surface: `harpoc cert import <name> --key <pem> --cert <pem> [--chain <pem>]` (an encrypted key takes the same single hidden-passphrase decrypt path as `secret set --from-file`), `cert csr <name> --subject <cn> [--sans a,b]` (key generated in-vault, CSR PEM written verbatim to stdout so it can be piped, secret stays PENDING until the issued certificate arrives; defaults to EC P-256), `cert issue <name> --domains <list> --email <addr> [--staging] [--dns] [--http-port <p>]` (a full ACME order — `--staging` targets the Let's Encrypt staging directory and `--dns` runs the manual TXT flow instead of binding an http-01 responder; always RSA-2048 for now), `cert renew <handle>` and `cert status <handle>` (health only — subject, issuer, validity window, renewal state; never key material). All five take `--token` / ambient `HARPOC_TOKEN` from day one under the same scopes their planned REST counterparts enforce — `read` for `status`, `rotate` for `renew`, `create` for `import` / `csr` / `issue` (`create` is not grantable per secret, so token scope alone governs the creation paths) — pinned by `token-parity.test.ts`, and a token-bearing call threads its caller into every engine read and write, so per-secret access policies apply and the creation and renewal audit rows name the requesting principal. Certificate secrets are now refused on the generic value, use and rotate paths with the new `CERT_VALUE_UNSUPPORTED` (HTTP 400, the 91st error code — up from 90): without it a CSR-pending certificate could be handed an unrelated payload and flipped ACTIVE, reporting itself issued while its certificates row still held no leaf, and an empty-payload certificate secret could be injected as a credential. The discriminator is the presence of a `certificates` row, not the secret type alone, so pre-existing generic `--type certificate` secrets carrying a real payload stay readable. The certificate-row transaction always logs `cert.issue` with an `{ acme: boolean }` provenance flag — the house rule that a mutation commits atomically with its audit row outranks an ACME-only mapping — renewal logs `cert.renew`, and `cert.revoke` stays reserved. No new audit event types and no migration: the `certificates` table shipped with the v1.0 schema. `--auto-renew` is opt-in on both `import` and `issue` (`--renew-before-days` defaults to 30) and **persists intent only** as far as this entry goes — the scheduler shipped here as a library, and `harpoc server start --cert-renew` (see the entry above) is what later wired it into a long-lived process; without that daemon, `harpoc cert renew` is the only thing that renews
- **Token scope on the full CLI surface** — `--token <jwt>` / ambient `HARPOC_TOKEN` extends from `secret use` to every CLI command with a REST counterpart: `secret get`/`list`/`set`/`rotate`/`delete`/`allow`/`mcp-server`/`connection`, `policy grant`/`revoke`/`list`, `audit` (+ `verify`/`anchor`) and `oauth status`/`refresh`. A supplied token _attenuates_ the unlocked session with the same three-dimensional scope predicate the REST routes use (permission × project × secret-name patterns; per-command permissions identical to the matching route — `read`/`list`/`create`/`rotate`/`revoke`/`admin`), engine-enforced per-secret access policies, and audit attribution under the `cli` interface; no token = the trusted local path, unchanged. Fail-closed edges: a present-but-empty token (flag or exported variable) is refused on every command, never treated as absent; refusals precede interactive prompts, value collection and engine reads; and the tokenless path never parses handles CLI-side, so the engine's denial audit rows are preserved. `policy revoke` gains `--secret <handle>` (required with a token — scope is checked against the secret the policy belongs to, with the same caller-less cross-secret membership check as REST's DELETE route). Engine: `refreshOAuthToken` and `getOAuthTokenStatus` accept an optional caller and enforce `rotate`/`read` per-secret policies — a denied refresh is refused _before_ joining an in-flight refresh (no `refresh_token` POST, no waiting on another principal's result), and OAuth refresh audit rows now carry the caller's principal and interface. The command→permission map is pinned by a 44-case parity test (`token-parity.test.ts`) plus a real-binary e2e round trip. Token lifecycle stays trusted-path-only (`auth token`, `auth revoke`, `oauth connect`). No new error codes, no new audit event types, no migration
- **Filesystem isolation for process-mediated spawns** — a per-secret `fs_isolation` flag on the injection policy denies filesystem writes to every child process the vault spawns with that secret: the process, Git and SSH contexts, mirroring `network_isolation` end to end (same `spawnCaptured` seam, applied after allowlist resolution, opt-in, no environment opt-out). Linux delivers it via `setpriv` chained with a Landlock ruleset (util-linux ≥ 2.40; writes to `/dev/null` are exempt), macOS via a `sandbox-exec` deny-write profile (blanket deny — no `/dev/null` exemption, a documented cross-platform asymmetry), and Windows is unsupported by design. Fail closed: a platform that cannot deliver refuses the use with the new `FS_ISOLATION_UNAVAILABLE` (HTTP 501, the 90th error code — up from 89) before any process is spawned, and the denial is audited. MCP stdio downstream servers already holding the secret are terminated when the flag is set (`mcp.terminate`, reason `fs_isolation_enabled`; when a policy update enables both `network_isolation` and `fs_isolation` at once, the network-isolation reason takes precedence and exactly one terminate is emitted); every subsequent stdio MCP use of an fs_isolation-enabled secret is then refused with `FS_ISOLATION_UNAVAILABLE` — the stdio transport cannot yet be isolated, so the child does not respawn isolated — MCP-over-HTTP is unaffected. Combined with network isolation, Linux chains both wrappers in one spawn (`unshare -rn -- setpriv ... --`) and macOS uses a single combined `sandbox-exec` profile (`(version 1)(allow default)(deny network*)(deny file-write*)`). Every process/git/ssh `secret.use` audit row now carries the new detail keys `fs_isolation` (posture) and, when a wrapper actually ran, `fs_isolation_mechanism` (`landlock` | `sandbox-exec`). Admin path only: CLI `secret allow --fs-isolation` / `--no-fs-isolation` (merge-aware, tri-state), REST `PUT .../injection-policy` (whole-policy replace; an omitted `fs_isolation` field resets to `false`). No new audit event type, no schema migration — the KEK-encrypted policy blob is extended; pre-feature blobs load as `false` (Since 2026-09-02 the REST PUT requires every field — see the R3 entry under Changed; only the CLI's `secret allow` merge still fills an omitted field.)

- **Secret-name patterns in token scopes** — the token's `secrets` claim (CLI `auth token --secrets`) now holds full-anchored name patterns with `*` wildcards (e.g. `db-*`; case-sensitive, `*` the only meta-character) instead of exact names. Patterns are validated at token creation (`INVALID_SECRET_NAME` before signing) and enforced by one shared linear matcher at all four sites — MCP scope checks and list filtering, REST scope middleware and list filtering; the project dimension stays exact-match

- **Windows session-key protection (DPAPI)** — the session file's `session_key` is wrapped with DPAPI at rest on Windows (scheme-tagged via a `key_protection` field; absent means none, so existing session files stay readable). Reads fail closed — a tampered, foreign-user, or scheme-mismatched file requires a fresh `unlock`; a write-time wrap failure falls back to file permissions with a CLI warning; `HARPOC_SESSION_KEYSTORE=off` opts out for new writes. The DPAPI call goes through the OS-shipped PowerShell host (pinned path, `shell:false`, base64 over stdin/stdout, no cmdlets or `Add-Type`) — no native addon; sliding-TTL updates operate on the stored form, so the keystore roundtrip (~150 ms) is paid once per session load. macOS Keychain and Linux Secret Service landed next (see below)

- **macOS Keychain / Linux keyring session-key protection** — the thesis §4.6 off-host session-file hardening now covers every desktop platform. A random 32-byte wrapping key lives in the platform keystore (hex-encoded, get-or-create, never rotated or deleted by the vault) and the session key is wrapped AES-256-GCM under it into a versioned blob with a scheme-bound AAD; `key_protection` gains `keychain`, `secret-service` and `keyring` schemes. macOS bridges via the OS-shipped `/usr/bin/security` in interactive mode (the command line, including the hex key, crosses on stdin — never argv); Linux selects one of two tiers at engine construction: Secret Service via `secret-tool` when a D-Bus session exists, else the kernel `@u` user keyring via `keyctl` (binaries resolved from `/usr/bin`/`/bin`, never PATH; absence disables the tier). Kernel-keyring keys die at reboot — the wrapped session then fails closed and a fresh `unlock` recovers, acceptable under the 24 h session ceiling. The DPAPI contract carries over unchanged: fail-closed reads on tamper/foreign-user/scheme-mismatch, write-time keystore failure falls back to file permissions with a CLI warning, `HARPOC_SESSION_KEYSTORE=off` opts out, and TTL slides never touch the keystore. No native addons, no new dependencies, no new error codes, no migration. CI gains a macOS leg (disposable unlocked test keychain) and enables both Linux tiers (keyutils + gnome-keyring under `dbus-run-session`)

- **Tamper-evident audit log** — audit `detail` blobs are now AAD-bound to their own row (v2, no legacy fallback: blobs written before the change render as unreadable detail instead of being silently trusted), and every audit row carries an HMAC chained over its predecessor (migration 010). The new `harpoc audit verify` command walks the chain and exits non-zero on a break. Residual: truncation of the chain tail is only detectable against an external anchor

- **CLI OAuth flows — `harpoc oauth connect` / `status` / `refresh` and `server start --oauth-refresh`** — the OAuth 2.1 proxy is now wired to shipped entry points. `harpoc oauth connect <name>` creates the OAuth secret and runs the provider flow end-to-end over the unlocked vault (PENDING → ACTIVE): authorization code + PKCE by default — the authorization URL is **printed** (to stderr) and `--open` additionally launches the browser — `--device` for the headless device-code flow (provider presets supply the device endpoint), `--client-credentials` for machine-to-machine. The client secret never travels via argv: the `HARPOC_OAUTH_CLIENT_SECRET` environment variable wins, otherwise a hidden prompt (empty = public client; refused for `--client-credentials`, which requires one). Ctrl+C cancels pending flows and leaves the secret PENDING for a re-run. `harpoc oauth status <handle>` reports token health without sensitive fields; `harpoc oauth refresh <handle>` forces a refresh immediately. `harpoc server start --oauth-refresh` runs the background token-refresh scheduler in the long-lived server process — valid standalone as a refresh daemon — surfacing per-token refresh failures as CLI warnings; shutdown stops the scheduler before the vault seals

- **File-based secret import and encrypted-key decryption at import** — `harpoc secret set` and `harpoc secret rotate` accept `--from-file <path>` (byte-exact, 1 MiB cap), enabling multi-line values such as PEM private keys, which the single-line hidden prompt cannot carry. When the value is a passphrase-protected **PKCS#8 or legacy-PEM** private key, the vault prompts once for the passphrase, decrypts the key **in memory** (`node:crypto` only — no new dependencies, no temp files), and stores the plaintext key under the vault's own encryption; the passphrase is never persisted, and a wrong passphrase exits non-zero with the new `KEY_PASSPHRASE_INVALID` without writing anything. `--no-decrypt` stores encrypted material verbatim. Encrypted **OpenSSH-format** keys remain unsupported (bcrypt-pbkdf is outside `node:crypto`) and are refused before any prompt with the new `ENCRYPTED_KEY_UNSUPPORTED`, whose message carries the per-key-type recovery: RSA/ECDSA convert in place with `ssh-keygen -p -f <keyfile> -m PKCS8` (passphrase kept; the converted key then imports with the prompt), while for ed25519 — where ssh-keygen silently ignores `-m PKCS8` — the passphrase is stripped with `ssh-keygen -p -f <keyfile> -N ''` and the resulting unencrypted OpenSSH container imports as-is. Use-time errors for encrypted keys now point at the same recovery instead of a dead end. The `use_secret` path is unchanged

- **Scheduled OAuth refresh honors `token_endpoint_auth_method`** — the stored token record gains a plain `token_endpoint_auth_method` column (migration 011, schema v11; provider metadata like the endpoint columns, nothing secret), persisted from the provider config at `oauth connect` time. The engine's refresh path — behind the refresh scheduler, on-use auto-refresh and `harpoc oauth refresh` alike — now builds `Authorization: Basic base64(urlencode(client_id):urlencode(client_secret))` per RFC 6749 §2.3.1 for `client_secret_basic` secrets and keeps the credentials out of the request body, closing the residual where a Basic-only provider authenticated at connect but failed every scheduled refresh. Legacy rows (column `NULL`) keep the exact pre-migration wire shape (`client_id` + `client_secret` in the body); one shared implementation (`applyTokenEndpointAuth`, relocated from the OAuth proxy to `@harpoc/shared`) now serves the three interactive flows and the refresh path. `harpoc oauth status` reports the configured method. No new error codes, no new audit events

- **Network isolation for process-mediated spawns** (thesis §4.5.3 layer 4) — a per-secret `network_isolation` flag on the injection policy strips the network from every child process the vault spawns with that secret: the process, Git and SSH contexts (all spawns go through the single `spawnCaptured` seam, where a vault-authored wrapper prefixes the argv **after** allowlist resolution — the pinned resolved path stays the audited command, and no agent input reaches the prefix). Linux uses `unshare -rn` (unprivileged user + network namespaces; loopback stays down, so even `127.0.0.1` — where the vault's own listeners live — is unreachable), macOS uses `sandbox-exec` with a constant deny-network profile (deprecated by Apple but functional; probed live, never assumed), and Windows is **unsupported by design** (real isolation needs an AppContainer native addon). Fail closed: when the policy demands isolation and the platform cannot deliver — Windows, restricted user namespaces, a missing wrapper — the use is refused with the new `NETWORK_ISOLATION_UNAVAILABLE` (HTTP 501) _before any process is spawned_, and the denial is audited; there is no environment-variable opt-out. MCP `stdio` downstream servers (spawned by the connection lifecycle, not the seam) are refused under an isolation policy until that transport can isolate; MCP-over-HTTP, `http` and `database` actions are request-mediated from the vault process (no child) and unaffected. Every process/git/ssh `secret.use` audit row now records `network_isolation` (and the live mechanism when isolated). Admin path only: CLI `secret allow --network-isolation` / `--no-network-isolation` (merge-aware; omitted flags keep the stored value), REST `PUT .../injection-policy` (whole-policy replace; omitted field resets to `false`). No migration — the KEK-encrypted policy blob is extended; pre-feature blobs load as `false`. Honesty note: isolation blocks the child's own sockets — a child can still write the value to a file that a _cooperating other process_ exfiltrates later (same residual family as the output-transform bypasses) (Since 2026-09-02 the REST PUT requires every field — see the R3 entry under Changed; only the CLI's `secret allow` merge still fills an omitted field.)

- **Per-secret access policies are now enforced at the engine** (thesis §4.6) — the stored `access_policies` rows, previously write-only, gate every credential operation arriving with a token-derived caller: `read` gates metadata/value reads, `use` gates `use_secret`, `rotate` gates rotation and pending-value set, `revoke` gates revocation, and `admin` implies all. Enforcement is presence-gated restriction, checked inside the engine before anything is decrypted, injected or mutated: a secret with at least one active (non-expired) policy row requires the caller to hold a matching grant; a secret with no rows stays governed by token scope alone. The caller's principal set is the token subject under its issued principal type — a new optional `principal_type` JWT claim (`agent` | `tool` | `user`, absent = `agent`; CLI `auth token --principal-type`) — plus a derived `project` principal from the token's `project` claim, so a grant to `(project, api)` covers every token scoped to that project. Policy denials are audited under the operation's event type with `success: false`, the requesting principal in the row's principal columns (their first production use; engine-level success and denial rows for caller-attributed operations now carry them too) and the required permission in the detail. The trusted local path — CLI, in-process SDK, stdio MCP explicitly started `--allow-tokenless` (see Changed) — carries no caller and is not subject to per-secret policies (the §4.7 administration-versus-operation split). No new error codes (`ACCESS_DENIED` reused, 403), no new audit events, no migration
- **Credential-access audit attribution — "by whom, through which interface"** (thesis §4.3.4) — every token-authenticated credential access now stamps the requesting principal onto its audit rows, including the rows written inside the six injectors: the **success row of every `use_secret` invocation** (HTTP, process, MCP, database, Git, SSH) plus injector-internal failure rows (SSRF/redirect refusals, spawn failures, host-key mismatches, …) carry `principal_type`/`principal_id` in the plaintext columns (chain-HMAC-covered, no migration — the columns exist since v1.0), the session id, and the access interface (`rest` | `mcp` | `mcp-http`) inside the encrypted detail. Engine-written caller rows (reads, rotations, revocations, denials) gain the interface tag too, and `mcp.spawn` is attributed to the invocation that injected the credential; `mcp.crash`/`mcp.terminate` stay deliberately unattributed (vault-initiated, no requesting principal). `harpoc audit` gains a **Principal** column (`type:id`, `-` for principal-less rows). Trusted-local operations (CLI, in-process SDK, stdio MCP explicitly started `--allow-tokenless` — see Changed) keep NULL principal columns and no interface tag by design — and NULL ⇒ trusted-local holds only for rows written from this release on; earlier rows predate attribution and are NULL regardless of caller. The interface tag is forensic only — policy matching ignores it (pinned by test). No new error codes, no new audit events, no migration
- **The tokenless MCP opt-out is now recorded in the audit trail** — starting the stdio MCP server with `--allow-tokenless` previously produced a warning on stderr and nothing else, so the vault's own tamper-evident log held no record that an unrestricted server had run: a session in which every tool ran without scope enforcement was indistinguishable from one governed by a scoped token, and a tokenless server that started but was never used left no trace at all. The waiver now writes a `server.start` audit event (30th event type) carrying `{ tokenless: true, transport: "stdio", tty_prompt }`, at the single `createMcpServer` choke point — so both stdio entry points and any programmatic `allowTokenless` embedder are covered. **Fail-closed**: if the row cannot be written, the unrestricted server does not start (the error propagates; the CLI exits 1) — no record, no unrestricted server. The row is deliberately unattributed (NULL principal columns, session id stamped): the operator at the console is the trusted local path, not a requesting principal. **Scope, so the row is not over-read**: only the tokenless waiver is audited — token-bearing stdio starts, `--mcp-http` (one `McpServer` per session), REST and `--oauth-refresh` write no row, because their operations are already attributed per access. Absence of `server.start` rows therefore means no unrestricted server started, subject to the usual chain caveat that tail truncation needs an off-host anchor. This reverses a decision taken with the token gate itself (which argued that NULL-principal rows already marked the mode): NULL is overloaded across CLI, in-process SDK and tokenless MCP, and inference needs activity a never-used server does not produce. No new error codes, no migration
- **Token-scoped `harpoc secret use`** — the CLI's `use` command accepts a scoped API token (`--token <jwt>`, or the `HARPOC_TOKEN` environment variable when the flag is absent; an explicit flag wins). With a token the call is no longer the trusted local path: the token is verified (expiry, revocation, vault binding), its three scope dimensions are enforced by the same predicate the REST route uses — permission, project, secret-name patterns — and the call carries a token-derived caller, so per-secret access policies apply and the audit rows are attributed to the token's principal with the new `cli` access interface. A refusal happens before the credential is decrypted or injected. **Without a token nothing changes**: the unlocked session remains the trusted administrative path, with no caller and principal-less audit rows. The token _attenuates_ the session; it does not replace `unlock`. Note that an exported `HARPOC_TOKEN` (previously ignored by `secret use`) now restricts it — restriction-only, so the worst case is a scope refusal rather than an escalation
- **`harpoc secret use --timeout-ms <ms>`** — all six action schemas accepted an execution timeout that no CLI flag could set; the flag now maps onto whichever context is selected (1..300000 ms)
- **Audit-chain external anchor — `harpoc audit anchor` and `verify --anchor`** — closes the tamper-evident audit log's documented residual: the HMAC chain catches row tampering, detail swaps and interior deletion, but deleting the newest N rows leaves a valid shorter chain. `harpoc audit anchor` exports the chain's tail link as a small JSON document (`format: "harpoc-audit-anchor/1"`; vault id, row id, timestamp, link HMAC in hex — nothing sensitive, the HMAC is already stored in plaintext) to stdout for piping off-host, or to a file with `--out`. `harpoc audit verify --anchor <file>` then additionally asserts the anchored row still exists with exactly that link — tail truncation and database rollback fail the check (exit 1), while rows appended after the anchor keep verifying; an anchor from a different vault is rejected by vault id. `verify` now always prints the current tail link for eyeball comparison and re-anchoring. **The anchor only means something stored off-host** (another machine, a sync target the attacker cannot write, or paper): an attacker with database write access can likely also modify sibling files, so the vault deliberately has no anchor-storage feature — and rows appended after the newest anchor are unprotected until the next one is taken, so re-anchor regularly. Engine surface: `getAuditChainTail()` and `verifyAuditChain({ anchor })`. No migration, no new error codes, no new audit events

- **`useSecret` checks the secret's status before its pre-decrypt guards, not after them.** Three guards run ahead of the value block — the docker-registry isolation refusal and the two v1.3 mail refusals (SMTP's STARTTLS × `tls: false`, IMAP's implicit-TLS and OAuth checks) — so an expired, revoked or not-yet-provisioned secret used in one of those contexts reported the guard's `INVALID_INPUT` instead of its own status, and an expired secret was not lazily transitioned at all: it stayed ACTIVE in the table and wrote no `secret.expire` row. `useSecret` now runs one status check on the row it already holds, immediately before the first guard, with the value block's exact failure semantics (the failed `secret.use` row and the downstream MCP child terminated). A vault-managed certificate secret keeps refusing `CERT_VALUE_UNSUPPORTED` ahead of the status check and of the three guards, exactly as it does on both value paths, so a refused use never transitions it out of the renewal census. **A caller matching on `INVALID_INPUT` for an unusable secret on the docker-registry, SMTP or IMAP contexts must adjust** (B21).

A helper bound the host cannot meet is a sweep that silently fails open — the 2026-08-26 finding again, one tier up — so the product bound moved rather than the test: `HELPER_TIMEOUT_MS` 10 → 20 s, `DESCENDANT_SWEEP_TIMEOUT_MS` 15 → 30 s (still 1.5× the helper, one listing plus the kills), pinned by a mocked-spawn bounds test. The tool now advertises exactly what is enforced (HTTPS-or-loopback endpoints, the 255-character name cap; `client_secret` still absent by design) and refuses at the schema boundary, and `renew_certificate` reuses the shared `http_port` bounds (superseded before release — see the breaking entry above: `renew_certificate` no longer declares `http_port` at all)
- **Breaking: the Argon2id key-derivation defaults flip to the RFC 9106 first recommended (high-security) profile — 2 GiB memory, 1 iteration, 4 lanes** (previously 64 MiB, 3 iterations, 4 lanes). The only adversary who ever faces the KDF is the offline attacker holding a copy of the vault database (backup, synced folder, restored storage), and against that adversary the memory cost per password guess is the entire security margin; the latency cost — roughly half a second on commodity desktop hardware — is paid once per session unlock under the 24 h ceiling. **The parameters are compile-time constants, not stored per vault: a vault created under the old profile derives a different master key under this release and can no longer be unlocked** (`INVALID_PASSWORD` — the KEK unwrap fails). Export any secrets you need with the previous release and re-`init`; there is no in-place migration. Unlocking now also requires ~2 GiB of free memory on the vault host
- **Breaking: the stdio MCP server requires a launch token by default.** `harpoc server start --mcp` and `harpoc-mcp` refuse to start without a launch token (`--token` or the `HARPOC_TOKEN` environment variable), exiting with the new `TOKEN_REQUIRED` error whose message names both recoveries. The previous silent full-access default — no scope enforcement, no per-secret policy checks, principal-less audit rows — survives only behind the explicit `--allow-tokenless` opt-in flag (programmatic: `CreateMcpServerOptions.allowTokenless`), which keeps the unrestricted-mode warning on stderr **and now writes a `server.start` audit row** (see Added); the flag requires `--mcp` and conflicts with a supplied token. Existing MCP client configurations that passed no token must add either a scoped token or the flag. The Streamable HTTP transport is unchanged (its per-request Bearer was always mandatory), and `harpoc-mcp` now also reads `HARPOC_TOKEN` for stdio launches (explicit `--token` wins; ignored with `--http`), matching `server start --mcp`
- **Behavioral: OAuth secret creation is attributed, and its refusals are now audited.** `createOAuthSecret` takes a caller (attribution only — `create` is not grantable per secret, so no policy gate is added), which lands on the `oauth.authorize` row of the fresh, the resumed (`resumed: true`) and the refused path alike, so an OAuth secret provisioned through REST or MCP names the requesting principal where it previously left the principal columns NULL; the trusted local path (CLI, in-process SDK) stays NULL-principal by design. A name collision with an **ACTIVE** secret — which still refuses as `DUPLICATE_SECRET` — now writes a **failed** `oauth.authorize` row instead of nothing at all (non-`VaultError` failures stay unaudited). Note for anyone reading the trail: OAuth creation has always audited as `oauth.authorize` and writes **no** `secret.create` row, so `secret.create` marks a plain secret creation only, and MCP's client-credentials flow writes **two** authorize rows — one for the configuration, one for the collect-and-complete step
- **Behavioral: `harpoc oauth connect` on a custom provider without a token endpoint now fails as `SCHEMA_VALIDATION_ERROR`** (previously a plain `Error`, surfacing as `UNKNOWN` under `--json`), and the message no longer names the `--token-endpoint` flag, since the same validation now serves the REST and MCP wire surfaces as well as the CLI. Two further consequences of reimplementing the blocking authorization-code start on top of the new non-blocking one: a failed browser leg now **also** reaches `onBackgroundFlowError` (previously only the awaited rejection carried it), and a second start for the same secret **supersedes** the first — the predecessor's callback listener is cancelled, so it can no longer drive the secret ACTIVE behind the caller's back
- **Behavioral: stored access-policy rows become live restrictions.** Policy rows granted in earlier releases were stored but never checked; from this release, any secret carrying at least one active policy row denies token-authenticated callers without a matching grant (`ACCESS_DENIED`, 403). Tokens issued before this release carry no `principal_type` claim and match as `agent` principals — an admin whose tokens were created with the CLI default subject grants to `(agent, cli-user)` (or the `--agent` subject they issued). CLI and SDK-direct access is unaffected
- **Behavioral: secret-scoped configuration is gated by the same policy rows.** The injection policy, downstream MCP-server config, connection config and the secret's own access-policy rows were governed by token scope alone, so a principal whose `rotate` was policy-denied could still rewrite the allowlists (or set `response_mode: "full"`, or drop the TLS/host-key pins) through REST, and a principal whose `read` was denied could still read them. From this release the engine checks the caller on those operations too: config reads require `read`, config writes require `rotate`, and `POST`/`DELETE` on `/:handle/policies` require `admin` — presence-gated exactly like the credential operations, so secrets without policy rows are unaffected. Denials are audited under `secret.read` (reads) or `policy.grant`/`policy.revoke` (writes) with the requesting principal. The first grant on a policy-free secret stays ungated by construction; the CLI remains the always-available recovery path if a REST principal locks itself out of a secret's policy administration
- **Behavioral: enumeration is gated by the same policy rows, and `create` is no longer a per-secret permission.** `list` and `create` were policy vocabulary no code path read: a secret whose `read` was policy-denied still returned its complete metadata row — name, type, project, status, version, timestamps, the payload `get_secret_info` refuses — through `GET /secrets`, `GET /health/expiring`, `list_secrets`, `check_secret_health` and the MCP secrets/health/projects resources. From this release the engine filters every listing by the caller's `list` grant (presence-gated as elsewhere: secrets without policy rows are unaffected, `admin` implies), and health/project aggregates are computed over the filtered set. **A principal granted only `use` (or only `read`) no longer sees that secret in a listing** — add `list` to the grant if the agent discovers handles by enumerating. Filtering is silent: enumeration writes no audit row, as before. The MCP resource `secret://vault/secrets/{name}` now serves its metadata through the gated `getSecretInfo` instead of answering out of an unfiltered listing, so it is subject to the `read` gate like every other metadata read. `create` cannot be granted per secret at all — a policy row attaches to an existing secret, so `grantPolicy` (CLI `harpoc policy grant`, REST `POST /:handle/policies`) now refuses a permission set containing it with `INVALID_INPUT`; it remains a token-scope permission (`harpoc auth token --scope create`). Rows stored earlier that contain `create` keep loading and stay inert. CLI and SDK-direct enumeration is unaffected
- The ephemeral in-process ssh-agent (SSH and Git-over-SSH contexts) is **reimplemented on `node:crypto`**, and `ssh2` — with its transitive `bcrypt-pbkdf` and `tweetnacl` — is **removed from `core`**. The vault now implements the OpenSSH agent protocol, SSH private-key parsing (traditional PEM and the `openssh-key-v1` container, via a hand-walked container → JWK → `node:crypto` KeyObject) and signature generation itself, so no third-party cryptographic library loads into the vault process — `node:crypto` plus Argon2id are the only cryptographic components (restores the single-exception property in the security model). Supported key types: **unencrypted** Ed25519, RSA and ECDSA (nistp256/384/521); RSA signs with `rsa-sha2-256`/`-512` per the agent's flags (never legacy SHA-1). Encrypted keys are rejected with a clear error at use time (the vault provides encryption at rest, and supporting them would re-introduce `bcrypt-pbkdf`; passphrase-protected PKCS#8/legacy-PEM keys are decrypted at import — see the encrypted-key import entry under Added); the prior `ssh2` path already required unencrypted keys, so realistic usage is unchanged. Validated against real OpenSSH (`ssh-add` parses the agent's identity blob) and by `node:crypto` signature verification across all key types and both encodings. The agent's public surface (`EphemeralSshAgent.start/authSock/dispose`) is unchanged; the SSH/Git injectors are untouched.
- The `use_secret` action dispatch and the interface-boundary result sanitizer are now **compile-time exhaustive**: the engine's six-context branch became a `switch` whose `default` arm funnels into a `never`-typed `assertNever`, and `sanitizeUseSecretResult` gained the same guard. Adding a seventh action or result type without an explicit arm is now a type error instead of a silent compile (verified by temporarily extending both unions). Runtime behavior for type-evading callers is unchanged for actions (`INVALID_INPUT`, same message) and **hardened** for results: an unknown result shape previously fell through the sanitizer silently — returning it unsanitized — and now throws `INVALID_INPUT` instead
- The shared type system is now **schema-derived**: every externally-validated shape — the six `use_secret` actions and their union, `InjectionConfig`, the injection policy, the downstream MCP server config, the connection configs, the session file and the OAuth provider config — has its TypeScript type derived from its Zod schema (`z.infer` beside each schema in `schemas.ts`), replacing the hand-written twin interfaces in `types.ts`; the validator and the type can no longer drift apart. Consequences: `InjectionConfig` is now the discriminated union the schema always enforced (`header` requires `header_name`, `query` requires `query_param`) instead of a loose all-optional interface, and `InjectionPolicy` now describes the policy the vault actually loads and returns (every field present, defaults applied) while the new `InjectionPolicyInput` (every field optional) is what `setInjectionPolicy` accepts across engine and SDK — matching the implementation's long-standing defaulting behavior. TypeScript-facing only; wire formats and stored blobs are unchanged
- **Breaking (SDK):** the SDK's input types are schema-derived too. `CreateSecretInput`, `GrantPolicyInput` and `HealthResponse` in `@harpoc/sdk` now derive from the shared Zod schemas (`createSecretInputSchema` → `CreateSecretRequest`, `accessPolicyInputSchema` → `AccessPolicyInput`, new `healthResponseSchema`) instead of duplicating them as hand-written interfaces. The inputs follow the wire shape: `GrantPolicyInput` is now `{ principal_type, principal_id, permissions, expires_at? }` (previously camelCase) and `CreateSecretInput` takes `expires_at` (previously `expiresAt`) — consistent with every other type the SDK exposes; `value` stays `Uint8Array` (the REST client base64-encodes it in transit) and the SDK remains zod-free (type-only imports). The shared `createSecretInputSchema` now covers the full create body (`value` as validated base64, `expires_at`), so `POST /api/v1/secrets` rejects malformed base64 in `value` with 400 instead of silently best-effort decoding it
- The MCP `create_secret` tool validates its `injection` argument against the canonical `injectionConfigSchema` instead of a hand-rolled looser copy: a malformed config such as `{type: "header"}` without a `header_name` is now rejected at the tool boundary (as REST always did) instead of being stored and failing only at first use (The create-time `injection` field was later removed entirely — see the Removed entry.)
- Windows batch files (`.cmd`/`.bat`) are now excluded by the **vault's own command resolution** instead of by the Node runtime. The resolver no longer probes `.cmd`/`.bat` when resolving bare command names, and any command whose symlink-resolved path is a batch file — including an explicitly allowlisted absolute path — fails with `COMMAND_NOT_ALLOWED` before anything is spawned. Rationale: spawning a batch file with `shell:false` is cmd.exe interpretation in disguise — Node versions before the CVE-2024-27980 fix silently wrapped such spawns in cmd.exe, an argument-injection surface that collapses the no-shell property and would let a `deploy.cmd` allowlist entry grant shell capability without ever tripping the interpreter-acknowledgement gate; patched versions refuse with EINVAL at spawn time, i.e. courtesy of the runtime. The vault now owns the exclusion deterministically on every Node version, at the same choke point that covers process actions, MCP stdio downstream launches and ssh/git resolution. Batch scripts remain runnable the explicit way: allowlist `cmd` with the interpreter acknowledgement and run `cmd /c script.cmd`. The exclusion is pinned by Windows-gated tests, including the symlink smuggle vector (a link named like a safe executable resolving to a `.cmd`); the symlink case requires file-symlink privilege (Developer Mode, elevation, CI runners) and skips where absent
- The session TTL now slides on **authenticated use**, not on process liveness. Every authenticated engine operation passes through a throttled expiry slide (at most one session-file write per 30 s per process — the cadence the background monitor used to produce), and `use_secret` slides again on completion, so a long-running action ends with a fresh idle window. The 30 s monitor no longer extends the session — it only enforces expiry: an idle-but-running MCP/REST server now seals about 15 minutes after its last use instead of keeping the session alive to the 24 h ceiling by mere liveness, and short-lived CLI commands — which exited long before the first monitor tick and therefore never slid at all — now genuinely extend the window on every command. Slides operate on the stored form (no keystore roundtrip), never fail the operation they ride on, and `lock()` settles an in-flight slide before the secure erase so a racing rename cannot resurrect the session file
- `harpoc secret allow` now **merges** into the stored policy: flag groups you omit keep their current values (previously every call replaced the whole policy, so a `--url`-only update wiped the command/host/env lists — and would have silently reset a `status_only` response mode back to `filtered`). The new `--clear` flag resets the policy to defaults before applying the other flags. REST `PUT /api/v1/secrets/:handle/injection-policy` remains a whole-policy replace; policy writes are audited with the effective response mode.
- The HTTP redirect loop now cancels the unread body of each followed redirect hop instead of leaving the connection pinned until garbage collection
- `wipeBuffer` now zeroes buffers (`Buffer.fill(0)`) instead of random-filling, matching the thesis's §4.6 memory-hygiene discipline; the session-file secure erase keeps its intentional random-byte overwrite
- **Breaking:** `use_secret` request shape changed from `{ request, injection, follow_redirects }` to `{ action }`, a discriminated union on `action.type` (`http` | `process` | `mcp` | `database` | `git` | `ssh`), across MCP, REST and SDK. Responses are discriminated too (`HttpResult` | `ProcessResult` | `McpResult` | `DatabaseResult` | `GitResult` | `SshResult`). The existing HTTP path is now `action.type: "http"`.
- The vault format-version compatibility check compares version components **numerically** and fails closed: a lexicographic comparison orders `1.10.0` before `1.2.0`, silently accepting a newer vault across a digit boundary; a malformed version string (empty, non-numeric component) now refuses to open instead of guessing
- The sliding session TTL is enforced for engines created by `init`/`unlock` too, not only for sessions re-attached via `loadSession`; a new `sessionTtlMs` engine option (capped at the 24 h ceiling) exposes the window as an operator knob, and an expiry-racing TTL slide can no longer resurrect an already-expired session file
- The shared OAuth endpoint schemas accept loopback HTTP (`localhost` / `127.0.0.1` / `[::1]`) in addition to HTTPS, matching the runtime SSRF validator that guards every OAuth fetch; non-loopback HTTP remains rejected at the schema boundary
- **Behavioral: the imap context's two refusals — a mail TLS opt-out and an OAuth-typed secret — now happen before any credential material is touched.** Both checks previously ran after the secret's value had already been decrypted (and, for an OAuth-typed handle, after the access token had potentially been fetched or auto-refreshed) for a `use` the refusal was about to reject anyway. Both checks now run first: a `tls: false` mail config and an OAuth-typed secret are rejected before decryption and before any token fetch or auto-refresh. Failed-row audit shape and the refusal messages are unchanged. That trade-off was closed in Wave 2 (B21): `useSecret` checks the secret's status before every pre-decrypt guard, so an expired, revoked or pending secret reports `SECRET_EXPIRED` / `SECRET_REVOKED` / `OAUTH_NOT_CONFIGURED` and an expired one still transitions.

### Removed

- **`secrets.sync_version`** — a never-built cloud-sync feature's column, always 0, dropped from the baseline DDL and from the shared `Secret` type (C45). The 012 agent backfill (`backfillAgentsFromPolicies`) and the 009 duplicate-name precheck (`assertNoLiveDuplicateNames`) are gone with the migrations they served; `updateCertificate` no longer accepts the writer-less `acme_account_*` fields (the account rides the certificate insert since Wave 2); `SqliteStore.insertAuditEvent(event, rowHmac)` now requires the chain link (the parameter was optional and defaulted to `NULL`).
- **`VaultEngine.storeAcmeAccount`** — the separate ACME-account write, superseded by the account riding the certificate's own import transaction (see Added). It had no product caller left and no re-key path behind it: `renewCertificate` re-uses the stored account and never rewrites it. The `policy.grant { config: "acme_account" }` audit row it wrote is gone with it, so a successful ACME issuance now writes one row fewer; reading the account (`getAcmeAccount`, with its explicit `secret.read` row) is unchanged.
- **`harpoc cert import --auto-renew`** — auto-renewal now requires an ACME-issued certificate, which an import by construction never produces (see Changed). REST and the SDK keep the `auto_renew` field so a sent `true` is refused rather than silently dropped, and `harpoc cert issue --auto-renew` is unchanged.
- `HKDF_INFO_SYNC` — the last HKDF context constant, reserved in 2026-07 for a cloud-sync feature that was never started and derived nothing in the meantime. This reverses the "`HKDF_INFO_SYNC` stays, reserved for cloud sync" note on the entry below; a future sync feature can declare its own context string when it exists.
- `AAD_AUDIT_DETAIL` — the v1 additional-authenticated-data constant for audit details, superseded by its `_V2` successor and referenced by nothing since. Only `_V2` remains, so there is one AAD per encrypted field rather than a live one and a decoy.
- The legacy unlock fallback that HKDF-derived the JWT/audit keys from the master key when a vault carried no wrapped keys, along with the one-time migration that back-filled them. The key hierarchy now has exactly one instantiation — random JWT/audit keys wrapped with the KEK — and a vault missing `wrapped_jwt_key`/`wrapped_audit_key` fails closed with `VAULT_CORRUPTED` before any key derivation runs, pinned by tests (missing keys refuse to unlock; a tampered wrapped key is rejected, never bypassed by a fallback). The fallback dated to the 2026-03-04 security-review migration from derived to random keys; every vault created since — including everything v1.0.0 produces — already stores wrapped keys, so no supported vault is affected. The now-dead `HKDF_INFO_JWT_SIGNING`/`HKDF_INFO_AUDIT` constants are gone (`HKDF_INFO_SYNC` stays, reserved for cloud sync)

### Fixed

- **The websocket context now enforces the secret's `url_allowlist`.** The v1.3 design named `url_allowlist` for it, but `executeWebsocketAction` ran only the SSRF pre-flight, so a `use`-holding caller could open a `wss://` handshake to any public host with the credential in the header whatever the allowlist said. The check runs after the tighten-only `response_mode` resolution and before any DNS or socket work; the refusal is audited as `URL_NOT_ALLOWED` on the `secret.use` row (compromise audit R1, research refinement).
- **A per-secret injection policy whose values fail the shared validators is refused at the engine write (`SCHEMA_VALIDATION_ERROR`) instead of being stored.** `VaultEngine.setInjectionPolicy` validated the policy's keys but not its values, so an in-process caller (`DirectClient.setInjectionPolicy`; the CLI and REST already gate their input) could store, say, an `env_allowlist` entry that is not an environment-variable name — and with the stored blob now parsed strictly on read (see the Breaking entry above), every later read of that secret's policy, the corrective write included, refused as `VAULT_CORRUPTED`, leaving the policy path unrecoverable short of deleting the secret. The engine now runs `injectionPolicyInputSchema` over the input before touching the vault; the refusal names the failing field's path and the rule it broke. **An SDK-direct caller that relied on the engine accepting an invalid list now gets `SCHEMA_VALIDATION_ERROR` at the write** (compromise audit R2, final review).
- **The Web UI and the SDK's REST client reset both v1.3 mail guards on every policy save.** `PUT /api/v1/secrets/:handle/injection-policy` replaces the whole policy, and both the Web UI's injection-policy editor and `RestClient.setInjectionPolicy` serialized only the eight pre-v1.3 fields — so any save through either surface silently dropped `smtp_recipient_allowlist` back to `[]` and `imap_read_only` back to `false`, loosening a configured SMTP recipient allowlist and an IMAP read-only pin without saying so. Both now round-trip the two fields, and a key-set check against the schema keeps them from drifting again. **Anyone who saved an injection policy through the Web UI or the SDK's REST mode since v1.3 should re-check those two fields** (N1, B18). (Since 2026-09-02 the PUT refuses an omitted field outright — R3.)
- **`createOAuthSecret` committed the base secret row before its OAuth row and its audit row.** A crash or a storage failure in between left a PENDING secret with no provider record and no `oauth.authorize` trail — a vault row nothing accounted for. Both paths are now single transactions (fresh: base row, OAuth row and audit row together; resume: delete, re-insert and audit together), so a failed create leaves no secret and exactly one failed `oauth.authorize` row (`error: INTERNAL_ERROR`, no `secret_id`) (N10, E74).
- **`maxPendingAuthorizations` could be overshot by simultaneous authorization-code starts.** The count was checked before the callback server bound and a flow registered only after the awaited start, so concurrent starts all passed a stale count and every one of them went on to hold a socket. A start now reserves its slot immediately after the cap check, and the predecessor it supersedes is aborted only once the new bind has succeeded — so the cap binds on the reservation while the released ephemeral port still cannot race the new bind. A failed bind restores the superseded predecessor, which therefore stays cancellable — unless the reservation was itself cancelled inside the window, in which case the predecessor is aborted with it — and a `cancelFlow` arriving during the bind window is honored instead of lost (E79).
- **Three audit rows never named the principal that caused them.** An `mcp.terminate` written because a caller revoked a secret, the `policy.grant` row for a stored ACME account, and the set-value `secret.create` row behind MCP's `create_secret` all committed without principal columns, so the trail recorded the effect and not the actor. All three are now attributed from the requesting caller. Vault-initiated terminations — `closeAll` on a seal path, and the lazy session-expiry hook — stay unattributed and carry only the session stamp, because no principal drove them; `mcp.crash` is unchanged (E75c/d/e).
- **A `use_secret` against a secret with no usable OAuth token wrote two failed audit rows.** The token fetch audited the denial and the `use` path audited it again, so one refusal appeared twice, one of them caller-less. The inner row is gone: a refused OAuth use now writes exactly one failed `secret.use` row with `error: OAUTH_NOT_CONFIGURED`, attributed like every other refusal (E75h).
- **The vault database file was created under the process umask and `chmod`ed afterwards.** Between creation and the `chmod` the file was readable by whatever the umask allowed — a window on every fresh `harpoc init`. A file-backed store now pre-creates the file with mode `0600` before SQLite opens it; `:memory:` and other special targets are excluded, and an existing file's mode is still never touched (D55).
- **The CLI stringified every imported secret value to look for PEM armor.** Armor detection only concerns key-shaped input, but the check ran on all of them, so importing any credential made an extra JavaScript string copy of it — a copy no `wipeBuffer` can reach. The value is now prefiltered on the buffer and only key-shaped input is stringified (N14).
- **The three-character floor below which a username is not redacted was a literal duplicated at five sites.** Nothing held the copies together, so a change at one site would have loosened redaction at the others without a failing test. The threshold is now `MIN_REDACTABLE_FRAGMENT` in `@harpoc/shared` and every site reads it; the value is unchanged, so no output changes (E68c).
- **The Web UI theme toggle stuck on `light` when `sessionStorage` refused the write.** The nav's three-state toggle (system → light → dark) read its current position back out of storage, so in a browser that refuses `setItem` — private mode — the write was swallowed, every click read "no preference" and advanced to `light` again, and the dark step was unreachable. `cycleTheme` now reads the applied `data-theme` attribute, which is set whether or not the write lands, so the cycle keeps turning and only the memory across reloads is lost — which is all a refusing storage can honestly offer. Two presentation fixes ride along: the toggle's muted label brightens on hover (the generic button hover rule only changes the background, which the toggle's own colour then overrode), and at the narrow-viewport breakpoint, where the nav rail becomes a horizontal row, it sits at the end of that row instead of still carrying the vertical rail's `margin-top: auto`
- **A declined confirmation left the previous action's notice or error on screen.** The secret detail page's _Renew certificate_ prompt and the agent detail page's _Delete agent_ prompt ran in their click handlers, ahead of the shared `run` helper that clears the two banners — so cancelling the prompt left the last action's outcome standing beside a page state it no longer described. `run` now takes the confirmation message itself: it clears the banners, prompts, and raises the busy flag only once the operator has agreed, so a declined prompt leaves the page idle and blank rather than idle and stale. The tokens page's _Revoke_ prompt carried the same shape without a shared helper, and now clears its error banner before it prompts
- **`DirectClient.close()` during an in-flight peer load left an uncancelled OAuth manager behind.** `close()` cancels the manager the client is holding, but a lazy `@harpoc/oauth-proxy` load already in flight completed afterwards and built a fresh `OAuthManager` — with its own callback server — that nothing then cancelled, so the very call meant to release the embedder's event loop could be followed by a new listener pinning it. A load that resolves after `close()` now cancels the manager it built, and refuses the call that asked for it (see Changed)
- **CLI numeric flags accepted forms an operator never types.** `Number()` coerces `0x10`, `1e2`, `5.0`, `+5`, a space-padded `5` and the empty string to integers, and every numeric option parsed through it took them: `server start --port`, `--mcp-http-port` and `--cert-renew-port`, `server start --ui-token-ttl`, and every `parseIntOption` consumer (`oauth connect --callback-port` / `--timeout`, `cert import` / `cert issue --renew-before-days`, `cert issue` / `cert renew --http-port`). The empty string was the visible case — `--callback-port ""` parsed as `0` and silently asked for an ephemeral port. All of them now require plain decimal digits and refuse anything else with the same message and exit code they already used for an out-of-range value, before the vault is opened.
- **`RestClient.queryAudit` silently dropped the `success` filter.** The option is part of `AuditQueryOptions` and typechecked at every call site, but the REST client never put it on the query string, so `queryAudit({ success: false })` returned the unfiltered page in REST mode while the same call filtered correctly in direct mode — a client asking for failures got successes and no way to tell. It is forwarded now, alongside the new `principal_type` / `principal_id` parameters, and empty-string values are omitted from the query string rather than sent as an empty filter
- **The http-01 challenge server's bind failure echoed the errno and the bind interface.** `http-01 challenge server failed to start: Error: listen EADDRINUSE: address already in use 0.0.0.0:8080` told every caller — CLI, REST, SDK and the renewal daemon alike — whether a local port was occupied, permission-denied, or something else entirely. The message is now cause-free — `http-01 challenge server failed to start on port 8080` — so only the caller-supplied port, which the caller already knows, survives, and `EADDRINUSE`, `EACCES` and any other bind error are indistinguishable. The cause is discarded rather than routed to a log, because the solver runs inside the vault process on every one of those surfaces
- **Certificates with `renew_before_days` above 365 silently escaped both the renewal daemon and the health census.** The census and the scheduler query certificates expiring within a fixed 366-day net and then apply each row's own window — but the CLI accepted `--renew-before-days` up to 3650 (the REST schema always capped at 365), so a row whose window exceeded the net was reported healthy by `check_secret_health` and never auto-renewed, despite being inside its configured window. The engine now refuses `renewBeforeDays` outside 1–365 on every import path (`INVALID_INPUT`, audited like every other import refusal, before anything is written) and the CLI cap matches, so the 366-day net is strictly wider than any storable window again. Done now deliberately: the feature shipped unreleased, so no vault can yet hold an out-of-range value — after one could, the validation would be a breaking change
- **`DirectClient.importCertificate` crashed with a raw `TypeError` on malformed input.** A missing `private_key_pem` or `certificate_pem` died inside the PEM helpers instead of refusing; the method now gates on `certificateImportSchema` before the passphrase guard — `SCHEMA_VALIDATION_ERROR` with the same message shape as REST and as its sibling `generateCsr` — and it hands the parsed output (the schema's `false` / `30` defaults) to the manager, exactly as REST does (2026-08-27; the earlier discard is reversed)
- **`startMcpHttpServer().close()` left background device-code polls running against a destroyed engine.** The shared OAuth manager's pending flows are now cancelled first in `close()`, as the CLI path already did on SIGINT — the shipped entry points exit the process, but a programmatic embedder of the HTTP server does not
- **Security (code review 2026-07-15) — tightening `network_isolation` on an MCP secret left the already-running downstream child un-isolated.** The stdio refusal only gated _new_ invocations; a live child spawned before the policy change kept the credential and full network egress until seal. `setInjectionPolicy` now terminates the secret's live connection when the flag is set (covers REST/MCP sharing one process), and the use-time refusal terminates before throwing (the backstop for a policy tightened from a separate CLI process — its engine cannot reach the server's in-memory registry, so the child dies on the next invocation attempt at the latest; both audited as `mcp.terminate`)
- **A rotated OAuth refresh token could be lost on `server --oauth-refresh` shutdown.** `stop()` only cleared the interval, so shutdown closed the store while a tick's token-endpoint round-trip was in flight — with a rotation-enforcing provider the old token was already invalid and the new one never persisted (permanent `invalid_grant` until re-connect). `stop()` is now async with a bounded drain (default 35 s since 2026-08-27 — it outlives one 30 s token-endpoint POST; the certificate scheduler keeps 10 s) and shutdown awaits it before `engine.destroy()`
- **`secret set`/`secret rotate --from-file` silently dropped certificate blocks from combined PEM bundles.** A cert-chain + encrypted-key file (the nginx/haproxy layout) classified as an encrypted key and stored only the decrypted key. Bundles are now refused _before_ the passphrase prompt with the new `KEY_BUNDLE_UNSUPPORTED` error (import the key alone, or `--no-decrypt` stores the bundle verbatim); the import classifier and the use-time loader guard now share one detection module so they cannot drift
- **`secret set`/`secret rotate` left resolved plaintext (including just-decrypted private keys) unwiped when the engine load failed.** The vault is now opened _before_ the value is resolved — a sealed vault fails before any value/passphrase prompt — and the buffer's whole lifetime sits inside a wiping `finally`; invalid `--type` is rejected before any prompt too
- **A transient network-isolation probe failure was cached for the process lifetime.** One 5 s probe timeout under load permanently refused every isolation-demanding spawn (`NETWORK_ISOLATION_UNAVAILABLE`) until the vault restarted. Only successful resolutions are cached now; a rejected probe re-probes on the next spawn (concurrent callers still coalesce)
- **Re-running `oauth connect` after a cancelled/failed flow always died on `DUPLICATE_SECRET`** — the printed "re-run 'oauth connect'" recovery was dead because the PENDING secret occupied the name. A name collision with a PENDING OAuth secret now resumes it: the provider config is replaced wholesale and the same secretId proceeds (audited with `resumed: true`); ACTIVE or non-OAuth collisions still refuse
- **`oauth connect --device` ignored `--timeout`** and blocked until the provider's `expires_in` (typically 15 min). The device wait is now raced against the timeout, the poll is cancelled, and the secret stays PENDING — recoverable by re-running
- **`oauth connect --open` aborted the whole authorization-code flow when the browser launch failed** (headless hosts, WSL) even though the URL was already printed — the callback listener died and pasting the URL hit a dead port. A failed launch now warns and keeps waiting
- SSH/Git-SSH host-key-mismatch denial audit rows now carry the `network_isolation` posture like every other post-spawn `secret.use` row — filtering the trail on isolation no longer misses exactly the security denials
- **Security (code review 2026-07-07) — hidden prompt echoed the master password.** `promptHidden` (CLI `init`, `unlock`, `secret set`, `secret rotate`) attached a `readline` interface to a TTY output while a manual raw-mode scanner did the actual read; in a real terminal readline's line-editing echoed every keystroke, printing the password in cleartext (and leaving it in scrollback). The vestigial `readline` interface is removed — the raw-mode scanner is the sole reader, so nothing echoes. (Non-TTY/piped input was never affected, which is why prior tests missed it; a TTY-flagged output-stub test now guards it.)
- **Security — re-running `harpoc init` on an existing vault destroyed all secrets.** `initVault` unconditionally rewrapped the KEK, orphaning every secret's DEK (wrapped under the old KEK) with no recovery and no warning. `init` now refuses when a vault already exists — `initVault` throws the new `VAULT_ALREADY_EXISTS` error (HTTP 409) and the CLI checks for the vault before prompting for a password, pointing at `harpoc unlock`. There is intentionally no `--force`: re-initialization is irreversible, so starting over is the explicit act of deleting the vault directory.
- **Security — `GET /api/v1/health/expiring` and MCP `check_secret_health` leaked out-of-scope secret metadata.** Both aggregated over the full secret list with no token scoping, so a project- or name-pattern-scoped token (or, for the REST route, a token without `list` permission) could enumerate every secret's name/project/expiry across the vault; the REST route's `days` was also unbounded. The REST route now enforces the `list` permission, applies the token's project + name-pattern filtering (parity with `GET /secrets`), and bounds `days` to `1..365`; the MCP tool aggregates over `scopeGuard.filterByScope(...)`.
- **Security — ReDoS in the secret-name scope matcher.** `matchesSecretNamePattern` compiled a token's `secrets` pattern to a regex by joining wildcard segments with `.*`, which backtracks exponentially: a token minted with `secrets: ["*a*a*a…"]` made every subsequent scope check burn unbounded CPU (~15 s at 10 wildcards, effectively unbounded at the 255-char limit) — a single-token denial of service of the vault process. Matching is now a linear prefix/suffix + ordered-`indexOf` segment walk with no backtracking; behavior is verified identical to the previous matcher across an exhaustive differential test.
- **Robustness — an invalid secret name broke `listSecrets` vault-wide.** `createSecret` inserted the row before validating the name, so `harpoc secret set "bad.name"` left an unaddressable phantom row that made every subsequent `list` (CLI, MCP, REST) throw. Name and project are now validated before anything is written (`createOAuthSecret` inherits the fix).
- **Security — database SSRF was DNS-rebinding-bypassable.** The database injector resolved and SSRF-checked the host but then passed the raw hostname to the driver, which re-resolved it — so a name that passed the pre-flight lookup as a public address could resolve to an internal one at connect time (and with `tls_mode: "disable"` no certificate check would catch it). The validated IP is now the dial target: `pg` connects to the pinned address with `ssl.servername` set to the hostname (SNI and certificate verification stay on the name), and `mysql2` dials the pinned IP through a custom socket factory with `verifyIdentity: true` (its hostname check is otherwise a no-op). Unpinned targets (literal IPs, loopback) are unchanged.
- **Security — the MCP-over-HTTP proxy had no connection pinning and followed downstream redirects unchecked.** `validatingAuthFetch` validated the URL but then used the global `fetch` with default redirect-following, leaving a DNS-rebinding window and letting a compromised downstream server redirect the credential-bearing request to an arbitrary address. Every outbound request now routes through a per-connection pinned `undici` `Agent` (reusing the HTTP injector's validated-address lookup), and downstream redirects are refused outright — `redirect: "manual"`, any 3xx cancels the body unread and throws `REDIRECT_POLICY_VIOLATION` (the downstream endpoint is admin-configured and exact, and redirect semantics break JSON-RPC anyway).
- **Security — MCP `create_secret` skipped the secret-name scope check.** The tool called `scopeGuard.checkAccess(permission, project)` without the name, so a token scoped to `secrets: ["api-*"]` could create `admin-backdoor`, and a project-scoped token could create a global (project-less) secret — both outside the declared scope. The name is now passed to `checkAccess`, matching the REST create route; a project-scoped token must supply its project on create.
- **The create-time `injection` config was accepted and silently discarded — the field is removed.** `harpoc secret set --injection/--header-name/--query-param` and the MCP `create_secret` tool's `injection` parameter promised a stored default injection configuration, but nothing ever persisted or read it: users believed they had configured injection behavior that did not exist, while every `use_secret` call continued to require its own per-call `injection` object (unchanged, and still required). The dead field is gone from the CLI flags (now rejected as an unknown option instead of ignored), the MCP tool schema, the REST create body (a legacy body carrying it is still accepted — the key is stripped, matching the previous effective behavior) and the engine/SDK input types. Setting injection-related configuration at create time via MCP also contradicted the rule that such configuration is set only through the trusted admin path (CLI/REST `secret allow`); a genuine per-secret default-injection feature, if ever wanted, belongs on the injection policy
- **Security — denied secret access and lazy-expiry transitions left no audit trail.** Every engine operation logged its audit entry only after success, so a scoped token probing revoked, expired or nonexistent secrets — the reconnaissance an audit trail exists to catch — was completely invisible, and the lazy-expiry status write (ACTIVE → EXPIRED on access) was an unaudited vault mutation with a `secret.expire` event type that had been defined since v1.0 but never emitted. Denied reads, rotations, revocations and `use_secret` value resolutions now produce a `success: false` entry carrying the error code (the same pattern as the existing URL-allowlist denial), and the lazy-expiry transition emits `secret.expire` exactly once — at both transition sites (regular secrets and OAuth access-token reads)
- **Security — the POSIX session file was world-readable during the write.** The session file — which on POSIX holds the raw session key that unwraps the KEK (keystore wrapping is Windows-only) — was created with default permissions (typically 0644) and tightened to owner-only 0600 only _after_ fsync and rename, with a chmod failure silently swallowed: another local user could read the key during the write window, or indefinitely after a failed chmod. The temp file is now created with mode 0600 from the first instant (the rename preserves it, and umask can only tighten it), so the window no longer exists; the trailing chmod remains as a repair whose failure now fires the session-protection fallback callback, so the CLI warns instead of staying silent
- **Security — the MCP-over-HTTP body-size cap only protected the initialize request.** The vault's own 4 MiB reader guarded initialize, but requests carrying a valid `Mcp-Session-Id` were handed unread to the SDK transport, which buffers the body with no size limit — any client holding a valid session (any valid token) could POST an arbitrarily large JSON body and exhaust vault memory. Every body-carrying request now goes through the capped reader, and the parsed body is handed to the SDK so its unbounded read never runs. The reader also no longer destroys the request stream on an oversized body (which could reset the connection before the `413` was delivered); it drains and discards the remainder so the error response reaches the client
- **`harpoc audit verify --json` silently ignored the flag.** The parent `audit` command declares `--json` too, and commander binds a post-subcommand `--json` to the parent — so `verify --json` always took the plain-text branch. The subcommands now read the flag through the merged option view (`optsWithGlobals`), and `audit verify --json` / `audit anchor --json` behave as documented
- **Security — OAuth token refresh failures were invisible in the audit trail.** Every failure branch of the refresh path threw before the audit line, so a scheduler repeatedly retrying a revoked grant left no trace. Failed refreshes now produce an `oauth.refresh` entry with `success: false` and the error code, matching the denied-access audit pattern
- **Security — the Git dangerous-argument denylist missed `--template` (clone-time code execution).** `action.args` is agent-controlled and spliced into the git argv; the denylist rejected `-c`/`--config`/`--upload-pack`/`--receive-pack`/`--exec` but not `git clone --template=<dir>`, which copies the template directory's `hooks/` into the new repo and runs the non-`.sample` hooks during the clone — local code execution for an agent that already holds a file-write primitive. The denylist now also rejects `--template` and `--separate-git-dir` (matched by name prefix, so both the `--opt=value` and `--opt value` forms are caught), and blocks the `-u` upload-pack shorthand for `clone` only, leaving `push -u` (`--set-upstream`) working.
- CLI hidden prompts (`init`, `unlock`, `secret set`, `secret rotate`) now work with piped/non-interactive stdin. The prompt previously treated every stdin `data` chunk as a single keystroke, so a piped line like `printf 'pw\n' | harpoc unlock` never matched the Enter check — the prompt hung and, on EOF, the process **exited 0 without executing the command**. Input is now scanned per character regardless of chunking, input after the line terminator is pushed back for the next prompt (`printf 'pw\npw\n' | harpoc init` answers both prompts), EOF terminates the line (an empty value still fails loudly), and a prompt can no longer leave the process exiting successfully with nothing done
- Redirect hops are now re-validated against the secret's **URL allowlist**, not just the scheme/SSRF floor. The allowlist previously ran once at the engine against the initial URL only, so with `follow_redirects: "any"` a credential-bearing request could follow a cross-origin redirect to a non-allowlisted origin — and in `same-origin` mode a (credential-stripped) request could still reach one. Every hop is now checked against the same patterns before it executes: a non-matching hop fails with `URL_NOT_ALLOWED` (audited, `success: false`) and the redirect target is never fetched. Empty allowlists remain unenforced (the optional-atop-floor posture is unchanged); with an allowlist configured, hop enforcement applies in **every** `follow_redirects` mode, including path-restricted patterns on same-origin hops
- HTTP DNS-rebinding IP pinning now actually executes. The pin branch was dead code: the validator only ever returned a resolved address for public hostnames — which must be HTTPS — while the branch additionally required plaintext `http:` (loopback-only), so the two conditions were mutually exclusive and **no request was ever pinned**; rebinding protection silently rested on TLS certificate validation alone. The pre-flight lookup now resolves **all** A/AAAA addresses (each checked against the SSRF policy — a single private address among the results blocks the request), and every request — the initial one and each redirect hop after its own re-validation — connects through a per-request `undici` `Agent` whose connection-time DNS lookup serves only the validated addresses. Pinning at the socket layer keeps the URL's hostname intact, so the `Host` header and TLS SNI/certificate validation are unaffected, and the mechanism now covers HTTPS (where it previously could never apply). `ValidatedUrl.resolvedAddress` (singular) became `resolvedAddresses`; `undici` — the engine behind Node's own `fetch` — is now an explicit `core` dependency
- Concurrent session-file writers can no longer collide on a shared temp file: the atomic write-then-rename now uses a per-write temp name (pid + counter). Previously all same-process writers shared `.session.json.tmp.<pid>`, so an expiry slide racing `changePassword`'s session rewrite could fail with `EPERM` on Windows; the engine additionally settles an in-flight slide before rewriting the session
- **`harpoc secret delete` no longer exits 0 without acting on closed/piped stdin.** The confirmation prompt used a readline callback that never fires on EOF, so `printf '' | harpoc secret delete x` exited successfully having neither deleted nor aborted, and `printf 'y'` (no newline) did the same. The prompt now uses the same chunk-independent scanning as the hidden prompts: EOF acts as Enter (`printf 'y'` confirms; an empty answer is the default No), a stream error settles the promise, and every outcome either deletes or prints "Aborted."
- **`harpoc secret connection` no longer silently drops stored endpoint-auth pins.** The command previously rebuilt the whole config from the provided flags, so `--db-tls require` after an earlier `--db-ca-file` discarded the CA pin (silently downgrading database certificate verification to system trust) and any DB flag wiped the SSH `known_hosts` pins. It now merges per field — omitted flags keep their stored values, provided `--known-host`/`--known-hosts-file` flags replace the stored SSH list — with a new `--clear` flag to reset, matching `secret allow`'s semantics
- `harpoc audit --since <unparseable date>` now fails with a clear error instead of silently returning the full unfiltered list (`NaN` was dropped by the store's falsy filter check); `harpoc policy grant --principal-type <invalid>` now fails with a clean validation message instead of a raw SQLite constraint error
- **Bearer tokens no longer have to travel via argv:** `harpoc server start --mcp` and `harpoc auth revoke` read the new `HARPOC_TOKEN` environment variable when `--token` is not given (an explicit flag wins; an ambient variable without `--mcp` is ignored). Command-line arguments are visible to every local process and land in shell history — the env var closes that exposure
- **Security — the username half of `user:password` secrets was never redacted.** Database and Git-over-HTTPS output sanitization redacted only the password: the username — credential material — survived in stdout/stderr, query result rows and error detail. Both halves are now redacted across all output channels (raw + base64/base64url/hex/percent forms); usernames shorter than 3 characters stay unredacted (they would shred unrelated output)
- **Security — SSH host/user argv hardening.** `action.host` was passed as a bare positional to `ssh` with no leading-dash guard and a schema that permitted `-host`-shaped values (option smuggling surface; no working RCE — the charset forbids `=`, space and `/`). Three layers now close it: the schema anchors the first character to an alphanumeric, the injector refuses `-`-prefixed host/user before any other work, and the argv carries a `--` end-of-options separator before the host positional
- Host:port validation now bounds the embedded port: `db.example.com:70000` is rejected at the schema (`hostPattern`) and again by the database injector's `parseHostPort` (defense in depth), matching the standalone `port` field's 1–65535 range
- HTTP action and MCP downstream-server URLs now reject non-http(s) schemes (`javascript:`, `file:`, `ftp:`, …) at the schema boundary instead of one layer down in core's SSRF validator; caller-supplied HTTP headers are validated at the boundary (name charset, 8 KiB value cap with CR/LF/NUL rejected, 64-header cap)
- The SDK `RestClient` now times out (default 30 s, configurable via `timeoutMs`) instead of hanging forever on an unresponsive vault server, and `DirectClient.revokePolicy` enforces the same policy-belongs-to-secret ownership check as the REST route (contract parity; previously the handle argument was ignored)
- **OAuth `CallbackServer` no longer leaks its timer and listener:** every terminal branch (success, provider error, missing params, invalid state) now clears the up-to-5-minute timeout, settles the callback promise exactly once, and closes the server after the browser response is flushed; the timer is `unref`'d so a pending flow cannot block process exit
- **Device-code background polling is now abortable and observable:** `OAuthManager` tracks each background poll's `AbortController` (`cancelFlow(secretId)` / `cancelPendingFlows()`), the poll-loop timer is `unref`'d (a pending device flow no longer blocks CLI exit for up to 15 minutes), and a background completion failure — previously swallowed — is surfaced through the new `onBackgroundFlowError` callback option
- **Failed OAuth refreshes now back off exponentially** instead of being retried every scheduler tick forever: a per-secret in-memory quarantine doubles the retry interval per consecutive failure (capped at 1 hour), clears on success, and is bypassed by an explicit `refreshNow`
- **OAuth provider presets: `client_secret_basic` support and the Google device endpoint.** The provider config accepts `token_endpoint_auth_method` (`client_secret_post`, the default, or `client_secret_basic` — `Authorization: Basic` with form-urlencoded credentials, kept out of the request body) honored at the authorization-code exchange, client-credentials grant and device-code poll; the `google` preset gains `device_authorization_endpoint`, so `google` + `device_code` works out of the box. (The residual — the core refresh path kept authenticating via `client_secret_post` because the stored token record carried no auth-method column — is resolved by the scheduled-refresh entry below, migration 011.)
- The MCP server's per-secret rate-limit bucket eviction actually evicts now: the sweep tested the stored token count against the limit, but every access decrements after refill and idle buckets are never refilled, so no bucket ever qualified and the map grew unboundedly across distinct secrets. The sweep now computes the idle-time refill, evicting buckets whose idleness would fully refill them
- **Security — concurrent `createSecret` calls could both pass the uniqueness check (TOCTOU).** The name-uniqueness check and the insert now run in one transaction backed by a partial unique index over live secrets' `name_hmac` (migration 009), so the race loses cleanly with `DUPLICATE_SECRET` instead of storing two secrets under one name
- Key-buffer hygiene: decryption and unwrap failure paths now wipe intermediate key material in `catch`/`finally`, a repeated `unlock` wipes the previous key set first, and `unlock()` no longer leaks an open store handle on its failure paths; `changePassword` now shares `unlock`'s lockout accounting and `INVALID_PASSWORD` semantics (previously divergent)
- **Security — OAuth token and device endpoints were fetched without URL validation.** Every oauth-proxy fetch — the authorization-code exchange, the client-credentials grant, and the device-flow start and poll — now runs the vault's URL validator (HTTPS requirement + SSRF policy) before the request, placed ahead of the flow's own error handling so `SSRF_BLOCKED`/`URL_HTTPS_REQUIRED` surface unrewrapped; loopback HTTP remains allowed for local providers
- **Concurrent OAuth refreshes no longer replay the same refresh token.** A scheduler tick racing an on-demand refresh sent the same `refresh_token` twice — providers with rotation detection revoke the whole token family on replay. Refreshes are now coalesced per secret (all callers share a single in-flight refresh, cleared on completion and on key wipe), and the scheduler skips a secret whose refresh is already running

- **A credential nested inside a JSON document that was itself carried as a string field of another was not redacted** (2026-08-15) — a routine webhook `data`/`payload` envelope, where the reflecting document sits one JSON-serialization layer inside the outer response body. Both the literal pass and the escape-tolerant class matcher (review 2026-08-14, F1) decode exactly one escape layer, so a credential escaped twice — once by its own document, once by the envelope wrapping it — passed through untouched, the residual the F1 fix wave characterized rather than closed. `redactSecretEncodings` now performs a structural pass after the two flat ones: when the response contains a backslash and looks like JSON, it parses the document and walks every string leaf and key, re-parsing a leaf that is itself JSON, to at most four levels of parse depth — not four `JSON.parse` calls in total; a document with many sibling leaves at one level costs one parse per leaf, so the actual call count scales with the document's shape — enough to reach a credential nested five JSON documents deep (the document naming it directly, wrapped in as many as four further envelopes). A credential wrapped a fifth envelope deeper (six documents total), or carried in a body over the descent's size guard (roughly 4 million characters, not bytes), is still not reached — characterized, not claimed closed, and the e2e harness is kept deliberately deeper (six `JSON.parse` calls) so the evaluation can still observe that band. Re-serialization happens only on an actual hit: a clean body is returned byte-identical. Only credentials containing `"`, `\` or non-ASCII were exposed by the original gap for a purely alphanumeric value, whose nested rendering is byte-identical to the raw one so the literal pass already matched it at any depth. A base64 value is not automatically exempt: its alphabet includes `/`, and a backend that escapes the solidus (PHP's `json_encode` by default) renders it differently depending on nesting depth — the same bypass the JSON-escaping-class fix below closes for a single escape layer, reproduced here at the second layer (`aB3/xY9+zQ==` nested two documents deep matched none of the five needles before this fix)
- **A credential echoed into a JSON response body was not redacted** (2026-08-13) — output sanitization matched the raw value, its base64, base64url, hex and percent-encoded forms, but not its **JSON-escaped** form. A response body is normally JSON, so an endpoint reflecting the credential hands it back with quotes as `\"` and backslashes as `\\`; the raw needle then does not occur in the body as contiguous bytes and the value passed through untouched, one `JSON.parse` away from the model. Thesis §6.2.7 names JSON escaping as an echo-bypass class. The gap was unobservable rather than unnoticed: for a credential drawn from `[a-z0-9-]` the escaped form is byte-identical to the raw one, so it only exists once a value contains a quote or a backslash — and no test credential ever had. Found by the Phase 4 response-channel-echo arm, which uses one that does. The partial-echo and chunking classes remain characterized residuals: they defeat contiguous-pattern matching by construction and no filter fixes them. The first fix matched one convention — V8's, which does not escape `/`. A backend using another valid JSON escaping (PHP's `json_encode` escapes the solidus by default, Python's `json.dumps` emits `\uXXXX` for every non-ASCII character under the default `ensure_ascii=True`) still passed the credential through, including its base64 form, whose alphabet contains `/`. Sanitization now matches the escaping **class** at one serialization level, and the harness detects it through a separate implementation, so a form one side misses is visible to the other. Both matchers decode exactly one escape layer on their own: a credential inside a JSON document that is itself a string field of another JSON document (a routine webhook `data`/`payload` wrapper) sits behind two escape layers. That nesting case is fixed separately — see the entry above (2026-08-15), which adds a structural pass on top of both matchers rather than changing either of them (review 2026-08-14, F1)
- **`harpoc secret use` treated a supplied-but-empty token as no token at all** (review 2026-08-13) — `--token ""`, or an exported `HARPOC_TOKEN=` that a shell script left empty, fell through to the trusted local path: no scope enforcement, no per-secret access policies, no attribution, and no message saying so, while the operator believed the session had been attenuated. It is the one place where an unusable token failed **open** rather than closed (`server start --mcp` refuses with `TOKEN_REQUIRED`). An empty or whitespace-only token is now refused before the credential is decrypted or injected, naming both recoveries; omitting the flag entirely is still the trusted local path, unchanged
- **`harpoc secret use --token` did not carry the argv-exposure warning its sibling token flags carry** — `auth revoke --token` and `server start --token` both direct the operator to `HARPOC_TOKEN` because command-line arguments are visible to other local processes; the newer `secret use --token` did not, so the one token flag most likely to be typed interactively was the one that did not say where the token should really go
- **Git-over-SSH did not work on Windows** — the SSH transport passes the ssh binary and its options to git through `GIT_SSH_COMMAND`, and git runs that string through its bundled `sh`, which treats a backslash as an escape character. An unconverted Windows path such as `C:\Windows\System32\OpenSSH\ssh.exe` therefore arrived as `C:WindowsSystem32OpenSSHssh.exe` and failed to exec, taking the `-i` identity and `UserKnownHostsFile` paths down with it, so a `use_secret` clone or fetch over `ssh://` or a scp-like remote failed with a non-zero git exit on Windows (the request-mediated HTTPS transport and the dedicated `ssh` context, which spawns ssh directly without a shell, were unaffected). The vault now normalizes the `GIT_SSH_COMMAND` paths to forward slashes on Windows, which git accepts in every position; POSIX paths carry no backslashes and are untouched
- **`GIT_SSH_COMMAND` and the ssh `UserKnownHostsFile` option broke for paths carrying spaces or shell-expandable characters** (review 2026-08-12, follow-up to the forward-slash fix) — two quoting layers were missing. First, git runs `GIT_SSH_COMMAND` through its bundled `sh`, which word-splits unquoted whitespace and expands `$` and backticks even inside double quotes: a profile or temp path like `C:/Users/Stefan G/…` or `C:/Users/svc$deploy/…` arrived split or mangled, so the ssh binary, the `-i` identity or the known_hosts pin was wrong and every git-over-ssh operation failed for that user. Each part is now single-quoted for sh unless entirely shell-neutral (single quotes make whitespace, `$`, backtick and embedded double quotes all literal). Second — affecting the dedicated `ssh` context too — ssh's own readconf re-tokenizes option **values** on whitespace after argv is built, so an unquoted `UserKnownHostsFile=C:/Users/Stefan G/…` read as two filenames, neither existing, and strict host-key checking refused a correctly pinned host with a misleading mismatch error. The value now rides inside readconf double quotes (verified against Win32-OpenSSH 9.5p2 and OpenSSH 10.0p2: quotes group the value, backslashes stay literal, `$` is never expanded). A real-sh round-trip test pins the composed string splitting back into the exact intended argv
- **HTTP `use_secret` audit rows carried no `detail.context`** — the other five injectors stamp the execution context on every row they write, and the HTTP context's own _failure_ rows do, but its success row did not. Context-keyed audit forensics (`which contexts did this principal exercise?`) therefore silently missed every successful HTTP injection, and each consumer had to special-case the one context. All three HTTP rows now stamp `context: "http"`; the detail blob is encrypted JSON, so no migration is involved
- **Overlapping REST middleware registrations ran auth, audit and rate limiting twice on the secrets collection route** — `app.use("/api/v1/secrets/*", …)` already matches the bare `/api/v1/secrets` path in Hono, so the additional `app.use("/api/v1/secrets", …)` registration made every middleware run a second time on `GET`/`POST /api/v1/secrets`: the token was verified twice, the request audit line was written twice (a duplicated entry per collection request in the operational log), and the global rate-limit bucket was charged **two tokens per request**, so that route exhausted at half its documented allowance. Each middleware is now registered once, on the pattern that covers both shapes. Found while pinning rate-limit enforcement (test-quality finding T8); the effect was stricter-than-documented limiting rather than a bypass, but the duplicated audit lines misrepresented request volume
- **`harpoc auth revoke` could write a revocation that expires before the token it revokes** (full-repository review 2026-07-25, M1) — the CLI read `exp` out of whatever JWT `--token`/`HARPOC_TOKEN` supplied without checking that it was the token being revoked, and `revokeToken` stored the supplied value verbatim. `verifyToken` prunes revocation entries whose `expires_at` has passed **before** consulting them, so an unrelated ambient token with an earlier expiry silently shortened — or entirely nullified — the revocation while the CLI printed `Token revoked`. The expiry is now used only when the JWT's `jti` matches the revocation target (a mismatch warns), and the stored lifetime is clamped to at least the maximum token TTL, which no token can outlive
- **Nulling `row_hmac` let a database-writing attacker rewrite the audit log undetected** (review 2026-07-25, M2) — a row with no chain link was counted as a pre-migration legacy row and skipped, and nothing enforced that such rows may only be a _prefix_. An attacker with write access to the vault file (the exact adversary the HMAC chain exists for — they hold no audit key) could run `UPDATE audit_log SET row_hmac = NULL WHERE id >= N` and then insert, delete and edit those rows freely, with `harpoc audit verify` reporting OK and exiting 0. The documented residual covered only tail _truncation_, which the off-host anchor addresses; silent insertion and modification were not covered. Verification now fails on a NULL link that follows any chained row, and on a wholly unlinked log when the audit key is present; a genuine legacy prefix followed by chained rows stays valid
- **MySQL TLS accepted any certificate from a trusted CA for IP-literal targets** (review 2026-07-25, M3) — `verifyIdentity` was set only when the target was a hostname, and without it mysql2 replaces `checkServerIdentity` with a no-op: for an IP target the certificate _name_ was never checked at all, so any certificate from any trusted CA, for any name, was accepted and a pinned `ca_pem` degraded from "this endpoint" to "anything holding a cert from this CA" — with the credential (and, under `caching_sha2_password` full auth, the cleartext password) going to whoever presented it. Identity verification is now unconditional, and because neither driver supplies an SNI name for an IP literal, the check is explicitly bound to the logical host — via the socket the vault dials for mysql2, and via an explicit `checkServerIdentity` for `pg`, which had the mirror-image bug of verifying against Node's `"localhost"` default
- **A surviving grandchild could hang a process-mediated invocation forever** (review 2026-07-25, M4) — the timeout killed only the immediate child and the promise settled only on `'close'`, which Node emits once every stdio stream is closed; a grandchild that inherited stdout/stderr keeps them open, and there was no second timer. The caller's `finally` then never ran: the plaintext stayed in memory unwiped, the ephemeral ssh-agent socket and the identity/known-hosts temp files were never disposed, and the request never returned. The timeout now kills the child's whole process group (POSIX process group; `taskkill /T` on Windows), settlement follows the child's own exit with a bounded flush grace, and a post-kill backstop settles even if the kill does not take. A timed-out result reports as killed on every platform
- **Downstream MCP stdout was uncapped and a framing error could spin forever** (review 2026-07-25, M5) — the read buffer had no size limit (stderr and post-parse results both do), and the drain loop `continue`d on a parse failure, which makes no progress when the failure is thrown before the buffer advances (a line too large to even stringify). Being synchronous, that loop blocked the vault's event loop permanently — one oversized or malformed line from a downstream server, hostile or merely buggy, was enough. Unframed stdout is now capped at 4 MiB (over it the connection fails visibly and is audited as a crash), and each line is consumed before it is parsed, so progress is structural
- **Abandoned MCP Streamable HTTP sessions were never reclaimed** (review 2026-07-25, M6) — a session left the table only on an explicit `DELETE /mcp` or on shutdown, so every client that died without one (crash, sleep, network drop) leaked a slot, and sessions whose pinned token had expired or been revoked were refused per request but never evicted. The least-privileged token in a deployment could deliberately consume all 128 slots with cheap initializes and lock out every other principal, `admin` included, until the daemon restarted. Sessions now carry a last-seen timestamp and are reclaimed on an idle TTL, on token expiry and on revocation; at capacity the quietest session is given up rather than the new client refused, unless the whole fleet is actively in use
- **Read-then-write transactions could fail with an unretryable `SQLITE_BUSY_SNAPSHOT`** (review 2026-07-25, M7) — the store used a deferred `BEGIN`, so a transaction whose first statement is a SELECT (the audit chain's select-last, `createSecret`'s duplicate check) took a WAL read snapshot and only then tried to upgrade to a write. If another connection committed in between, SQLite returned `SQLITE_BUSY_SNAPSHOT`, which `busy_timeout` deliberately does not retry — a spurious failure in the documented multi-process deployment (a `server start` daemon alongside CLI commands), and under the atomic-audit semantics the whole operation rolled back. Write transactions now take the write lock at `BEGIN`
- **A downstream MCP child could be orphaned with the plaintext credential in its environment** (review 2026-07-25, M8) — nothing tore the child down when something failed after the spawn but before the connection reached the registry (a refused audit write is enough, audit being fail-closed), and a connect that resolved after the vault had sealed published its entry into a registry the seal had already walked. Either way the child outlived the keys that authorized it with no path left to reach it. Post-spawn failures now kill the child, and a connect that resolves after a seal tears its child down instead of publishing it
- **The `mcp.crash` audit row could durably store a downstream server's leaked credential** (review 2026-07-25, M9) — the recorded stderr tail passed only through pattern-based sanitization, which cannot recognize an arbitrary credential; a downstream server that echoes its own environment to stderr (a common debug-logging accident) had its credential persisted in the trail and served to admin-scoped MCP clients, which otherwise have no path to any secret value, surviving client-token rotation. The tail now passes through exact-value redaction against the value injected into that child, as the result path already did
- **Value collection: a short URL token could crash the vault, and collectors were unbounded** (review 2026-07-25, M10) — `timingSafeEqual` throws on unequal lengths and the token length check was the only thing between that and an unhandled exception escaping a synchronous `node:http` handler; nothing limited how many URL-mode collectors could be live at once, each pinning a loopback listener and a five-minute timer, and the two tools that open them were bounded only by the very generous global rate-limit tier. The handler now has an explicit error boundary alongside the length check, concurrent collectors are capped (reaching the cap degrades to the terminal prompt or deferred entry), and `create_secret`/`rotate_secret` are bucketed into the per-secret rate-limit tier
- **The process context could re-spawn the Git and SSH binaries with unfiltered arguments** (full-repository review 2026-07-25, C1) — the Git and SSH contexts require their binary in the secret's `command_allowlist` (that entry is what pins `git`/`ssh` to a resolved absolute path), but `command_allowlist` is a single context-agnostic field and `use_secret` dispatches on the caller-chosen `action.type`. Any caller holding `use` on a Git- or SSH-configured secret could therefore send `action.type: "process"` with `command: "git"` and arbitrary `args`, where the vault inspects no argument at all: `git -c 'alias.x=!<command>' x` and `ssh -oProxyCommand=<command> host` execute an arbitrary command with the credential in the child's environment, bypassing the git dangerous-argument denylist and the ssh hardening argv entirely. No configuration could enable the Git or SSH context without also granting this. The process context now refuses any binary that has a dedicated injection context — new error `DEDICATED_CONTEXT_REQUIRED` (403), audited before any spawn, fail-closed with no environment opt-out — checked against the resolved, symlink-followed path so an alias to `git` is refused too. The capability is routed, not lost: `action.type: "git"`/`"ssh"` do the same work under vault-authored arguments. Interpreters are deliberately not covered here — `node`/`bash`/`npx` remain the acknowledgement gate's business, since allowlisting one is already an explicit audited administrator decision, whereas `git` and `ssh` carried no such acknowledgement
- **The git dangerous-argument denylist was bypassable with git's own option abbreviations** (review 2026-07-25, H1) — `assertSafeArgs` matched arguments against full option names, but git resolves any unambiguous prefix of a long option: `--templ=<dir>` reaches `--template` and `--conf=k=v` reaches `--config` while starting with neither denied string. Verified against real git 2.51 — `git clone --templ=<dir>` installs hooks from `<dir>` and runs `post-checkout` during the clone, with the injected credential readable from the hook's environment, reopening the clone-time hook execution closed as M5 in the 2026-07-07 review. Denial now also rejects any argument whose option name is a _prefix_ of a denied option, the same rule git applies when expanding it; legitimate arguments that merely share a leading substring (`--tags`, `--set-upstream`, `--depth=1`, …) are pinned as still permitted
- **HTTP refusal messages could carry the credential back to the model** (review 2026-07-25, H2) — a refused redirect hop was reported as `Redirect target blocked: <full URL>`, and that URL is authored by the endpoint which had just received the credential: a hostile or compromised target answers `302 Location: https://10.0.0.1/leak/<the token>` and the refusal message hands the value straight back. A thrown error is a model-visible channel no result-shaped redaction touches — the MCP SDK turns it into the tool result text, and the REST error handler returns `err.message` — so `response_mode` (including `status_only`) offered no protection. Two independent fixes: refusals now name only the hop's **origin**, and every error thrown out of the HTTP injector passes through credential redaction on the way out, so no future code path can leak through a message either. Each is pinned by its own test (the origin rule by the absence of the endpoint-authored path; the redaction backstop by a credential reflected into the hop's _hostname_, where reporting the origin alone would not help)
- **Credential redaction skipped JSON object keys** (review 2026-07-25, H3) — `mapStringLeaves`, the walker both redaction layers use for MCP and database results, rebuilt objects with `result[key] = …` so the redactor never saw a key. The party choosing key names is the downstream MCP server (or a SQL column alias), so a result carrying the credential as a `structuredContent` key reached the model verbatim while the identical string in value position was redacted. Keys are now mapped like values, with collision-safe suffixing when redaction collapses two keys onto one name
- **An empty `?project=` bypassed a token's project scope on `GET /api/v1/secrets`** (review 2026-07-25, H4) — the empty string is falsy but not nullish, so it slipped past the cross-project check and then survived `?? token.project`, and the engine's own `project ? … : undefined` turned it into "no filter at all": a token scoped to one project enumerated every secret in the vault, including other projects and global secrets. Fixed at both levels — the route treats an empty parameter as absent, and the engine treats an explicit empty project as a filter matching nothing (fail closed). The previously untested project dimension of `checkTokenScope` is now covered, including the cross-project denial and the "project-scoped token may not reach a global secret" remediation
- **A single oversized database row hung the whole vault process** (review 2026-07-25, H5) — the result-set byte cap halved with `Math.ceil`, so at one row `Math.ceil(1/2) === 1` left the set unchanged and the `while` loop spun forever. The loop is synchronous, so one agent-chosen query (`SELECT repeat('x', 2000000)`) blocked the event loop permanently, taking every other client, the session monitor and the OAuth refresh scheduler with it. Halving now strictly shrinks the set and a row that cannot fit on its own is dropped with `truncated: true`
- **Git-over-HTTPS enforced target control on a string and then let git roam** (review 2026-07-25, H6) — `runHttps` validated the supplied repository URL (SSRF floor, optional URL allowlist) and then handed git an askpass helper that answered _every_ prompt regardless of the host in it, with redirect following left at git's default. A `30x` on the initial request moved the base URL — and the credential prompt — to a host the vault never resolved, validated or allowlisted, and a hostile repository's `.gitmodules` did the same via submodules. The vault now forces `http.followRedirects=false`, binds the credential to the validated host (the helper compares the host git names in the prompt and refuses anything else, including a prompt naming no recognizable URL), and denies `--recurse-submodules`/`--recursive` on every operation
- **A revoked launch token kept full access on a running stdio MCP server** (review 2026-07-25, H7) — the stdio transport verifies its launch token once, at construction, and `ScopeGuard` re-checked only `exp` afterwards, so `harpoc auth revoke <jti>` had no effect on the server that token launched: the compromised token kept its full scope until expiry (up to 24 h) or process exit. The guard now re-consults the revocation store on every check (new `VaultEngine.isTokenRevoked`), and the recheck runs ahead of the permission check so a revoked `admin` token does not pass either. The HTTP transport already re-verified per request; the same hook is a redundant second line there
- **The git askpass helper answered password prompts with the username** — classification used `prompt.includes("user")`, but git's password prompt embeds the username (`Password for 'https://git-user@host': `), so for any username containing "user" the helper returned the username where the password was asked for and authentication failed. Found while pinning the H6 host binding; classification is now on the prompt's leading word
- **Downstream MCP server dying mid-write no longer risks crashing the vault process** — `StdioChildTransport` never attached an `'error'` listener to the child's stdin, so an EPIPE emitted when a downstream server exited while the vault was writing to it (observed as an unhandled-error crash on macOS CI, where a fast-exiting child races the initialize write) escaped as an unhandled `'error'` event; `send()` could also wait forever on a `'drain'` that never comes. Stdin stream errors are now swallowed at the stream (exit forensics still arrive via `'close'`, and the crash path still surfaces as `MCP_CONNECT_FAILED`/`MCP_SERVER_CRASHED`), and `send()` resolves or rejects through the write callback — a dead pipe rejects instead of hanging
- **SSH and Git-over-SSH authentication actually works now: the ephemeral agent's key was never offered under `IdentitiesOnly=yes`** — the hardening argv restricted ssh to _file-backed_ identities (ssh*config(5): agent identities are used "unless IdentitiesOnly is enabled"), but the vault's key exists only in the in-process agent, so ssh fell back to the host user's default `~/.ssh/id**`files — failing authentication where none exist and, worse, offering the host user's ambient personal keys where they do. Live-reproduced against a real SSH server (OpenSSH 9.5/10.0:`Permission denied (publickey)`, the agent identity absent from every `Will attempt key:` line). The vault now writes the ephemeral identity's **public** line (`EphemeralSshAgent.publicKeyOpenssh`) to a per-invocation 0600 temp file — public material only, the private key still never touches disk — and passes it as `-i`, which both makes the agent-held key eligible (ssh fetches the signature from the agent when the private half is absent locally) and *drops* the default `~/.ssh/id\_*`candidates: ssh offers exactly the vault identity, nothing else. Applies to both the SSH context argv and the Git-over-SSH`GIT_SSH_COMMAND`. Pinned by a new live-authentication e2e (`ssh-live-auth.test.ts`: real OpenSSH client + real ephemeral agent + production argv against an in-process SSH server, `ssh2` as a test-only counterparty) whose companion test permanently pins the vulnerability — the pre-fix argv still fails with the agent key never offered
- **Win32-OpenSSH's `ssh.exe` exits 255 with no output when `ProgramData` is missing from the environment** — the clean child environment (`buildSshEnv`) passed only `PATH`, `SystemRoot`, `SSH_AUTH_SOCK` and allowlisted vars, so on Windows every SSH/Git-over-SSH spawn died at startup (before any connection attempt) and surfaced as `SSH_CONNECT_FAILED`. `ProgramData` is now passed through on Windows alongside `SystemRoot`. Note the companion constraint verified while fixing this: on Windows the agent's named-pipe `SSH_AUTH_SOCK` is consumed by the **native** Win32-OpenSSH client only — an MSYS build (e.g. Git-bundled ssh) silently finds no agent, so the per-secret command allowlist should pin `C:\Windows\System32\OpenSSH\ssh.exe`
- **Audit entries now commit in the same SQLite transaction as the operation they record** — previously every mutation (create/set/rotate/revoke, policy and config writes, OAuth create/complete/refresh, token revocation, lazy-expiry transitions, password change) committed first and its audit row in a separate transaction, so a crash or kill between the two left a completed-but-unaudited operation. All fifteen mutation call sites now wrap the state write(s) and the audit insert in one transaction (nested audit-chain transactions run as SQLite savepoints; the chain stays linear, `audit verify` and anchors unaffected). Semantics change, fail-closed: an unwritable audit log now **rolls the operation back** instead of letting it proceed unaudited. The same pattern also fixes a latent crash-consistency bug in `changePassword`, whose five `vault_meta` writes were separate autocommit statements — a crash between the salt and wrapped-KEK writes left them from different generations, bricking master-password unlock for the old and the new password alike; they now commit as one generation

- **Database column names and the command tag were the one unredacted result channel** (review 2026-07-25, L1) — `rows` was passed through credential redaction but `fields[].name` and `command` were returned verbatim, so an attacker-chosen column alias (`SELECT 1 AS "<credential>"`) carried the value into the model's context past both redaction layers. Both now go through the same redactor as the rows
- **A downstream MCP child outlived the credential it was spawned with** (review 2026-07-25, L2) — revoking a secret, or its lazy expiry, left any stdio downstream server the vault had spawned running with the revoked plaintext in its environment until the vault locked, was destroyed or the session TTL expired (and use-driven slides push that out indefinitely). Revocation and expiry now terminate the secret's live downstream connection (audited `mcp.terminate`), and a use refused because the secret is no longer usable tears the child down as well — which covers the cross-process case, where a CLI revoke cannot reach the server process's registry
- **`secret.create` rows read as trusted-local operations** (review 2026-07-25, L3) — `createSecret` took no caller, so every REST and MCP create wrote NULL principal columns, which is the documented marker for the trusted local path (CLI, in-process SDK). It was the only mutating credential operation with no attribution; the row now carries the requesting principal and the access interface like the other five. `create` remains ungrantable per secret — this is attribution, not a new gate
- **`harpoc audit --secret <id>` omitted the successful operations on that secret** (review 2026-07-25, L4) — the six credential-lifecycle success rows (create, read, get_value, set_value, rotate, revoke) left `audit_log.secret_id` NULL while denials, `secret.use`, `secret.expire`, policy/config and OAuth rows all stamped it, so filtering by secret returned the failures and hid the successes. All six now carry the resolved secret id, and a denial row carries it too once the handle resolved
- **`loadSession` skipped the vault-version guard** (review 2026-07-25, L5) — `unlock` fails closed when the vault's `vault_version` is newer than the binary supports, but every entry path that reuses a session file (i.e. all of them except `init`/`unlock`) went around that check, so an older binary opened and wrote a newer-format vault. The guard now runs on the session path too, with the same `VAULT_CORRUPTED` error
- **A transient session-file read error sealed a live vault** (review 2026-07-25, L6) — every `readFile` rejection was mapped to "session absent", and both consumers treat that as proof the session ended: the monitor wiped the KEK, closed the database and killed downstream children, while the on-disk session was intact and unexpired. An EMFILE, EIO, EACCES or EBUSY was enough. Only ENOENT-class failures now mean absence; anything else raises `SESSION_FILE_ERROR`, on which the monitor skips the tick and the expiry slide leaves the session untouched
- **`POST /:handle/rotate` accepted a malformed base64 value and rotated the credential to garbage** (review 2026-07-25, L7) — the route only checked that `value` was truthy, and `Buffer.from(value, "base64")` silently discards invalid characters, so a typo'd value irreversibly replaced the secret while the API answered `200 {rotated:true}`. The body is now validated exactly like the create route's, and a malformed value is a 400 before the engine is touched
- **REST per-secret rate limiting silently stopped being enforced past 1000 buckets** (review 2026-07-25, L8) — the eviction sweep deleted the bucket currently being checked before its token was consumed, and tested stored tokens instead of computing the idle refill (stored tokens never reach the limit, so the map never shrank either). This is the twin of a bug already fixed in the MCP rate limiter; the REST one now carries the same rule
- **The Windows session-file ACL step shelled out and hid its failures** (review 2026-07-25, L9) — `icacls` was invoked through `execSync` as a cmd.exe string with the vault path interpolated into it, against the project's own "never a shell; arguments are data" doctrine, and every failure was swallowed while the POSIX `chmod` sibling reported through the protection-fallback callback. That matters precisely on the DPAPI write-failure path, whose remaining protection _is_ file permissions. The ACL is now set through the pinned `System32\icacls.exe` with `shell:false` and the path as an argument (the account name comes from the process, since `%USERNAME%` was a shell expansion), and a failure surfaces as a protection-degraded warning
- **Behavioral: audit reads honour the token's project and secret-name scope** (review 2026-07-25, L10) — the audit surfaces (`GET /api/v1/audit`, MCP `secret://vault/audit/recent`) checked only the permission dimension of the 3-dimensional token scope, so a project- or name-pattern-scoped admin token read audit detail — handles, names, principals, configuration changes — for every secret in the vault, with `?secret_id=` as a targeted oracle. This is the same "metadata row by another name" pattern that was closed for listing and health. Unrestricted admin tokens, the CLI and SDK-direct access are unaffected
- **`harpoc secret use` skipped the interface-boundary result sanitizer** that the REST route and the MCP tool both apply — the CLI printed the injector result with only the engine's exact-value redaction behind it, so the defense-in-depth pattern guard (`Bearer …`, `Basic …`, `api_key=…` shapes that are _not_ the secret's own value, such as a credential a target echoes back or a second token in a response body) never ran on that path. - **The vault directory and database were created with umask-dependent permissions** (review 2026-07-25, L11) — typically world-readable on POSIX, while the session file beside them is deliberately `0600`. `harpoc init` now creates the vault directory `0700` (with a repair for a pre-existing directory) and the database is restricted to `0600` when opened. - **The evaluation harness could report a defence it had not delivered** (review 2026-08-14) — three latent defects in the measurement and artifact layers, none of which was an active exploit against the committed runs, all of which could have made a future Chapter 6 table overstate the result. The opacity scanner shared the vault's V8-only JSON-escape needle, so neither side could see the class the other missed; it now scans with a separate implementation held to a superset relation by test, and descends into serialized JSON so a credential at two escape levels — where a body echo actually lives — is no longer read as absent. - **SDK: concurrent first calls to the lazy OAuth/certificate manager loaders no longer each build their own manager.** `DirectClient`'s OAuth and certificate methods lazy-load `@harpoc/oauth-proxy`/`@harpoc/cert-manager` on first use; two unawaited first calls previously each constructed a manager, and `close()` cancelled only the last one built — the other's callback listener kept pinning the event loop for the full callback timeout. The first call's promise is now memoized so concurrent callers share it, and a rejected load (a missing optional peer) clears the memo instead of poisoning it, so the next call genuinely retries the import

Every JSON route now refuses a string/number/boolean/null/array body outright with `SCHEMA_VALIDATION_ERROR` (400) `Request body must be valid JSON`, the same code and message `readJsonBody` already used for unparseable JSON
- **SFTP: an exit-255 sftp client failure now classifies as `SSH_CONNECT_FAILED`, not the generic `SFTP_OPERATION_FAILED`.** Exit 255 is the sftp client's own code for a connection, authentication or protocol-level failure — the same convention ssh uses — but the SFTP injector previously mapped every non-zero exit alike, so a bad password or an unreachable host read identically to a failed `get`/`put`. A pinned host-key mismatch is still checked first and wins over the exit-code classification
